# День 15 — контролируемые переходы состояний

Задача агента использует сохраняемый конечный автомат. Состояние хранится в
`context.taskState`, поэтому переходы, текущий шаг и пауза не зависят от
истории диалога и восстанавливаются из `data/agents.json`.

## Разрешённый жизненный цикл

```text
PLANNING → EXECUTION → VALIDATION → DONE
              ↘              ↙
            PLANNING     EXECUTION
```

`/execute` доступна только после сохранения Markdown-плана. Завершённый
рабочий шаг переводит задачу в `VALIDATION` лишь после последнего пункта.
Финал разрешает только `[[TASK_VALIDATION_PASSED]]` в конце ответа проверки;
старый `[[TASK_TRANSITION:DONE]]` не завершает задачу.

Если проверка обнаруживает доработку, агент возвращает
`[[TASK_VALIDATION_FAILED:<номер шага>]]`. Автомат возвращается к указанному
пункту, убирает его и последующие пункты из выполненных и повторно требует
валидацию после выполнения.

## Реакция на недопустимые переходы

Служебные метки не показываются пользователю. Если модель пытается пропустить
этап, задача не изменяется, а чат объясняет причину и следующее действие:
например, «Сначала завершите проверку результата». Для `/execute` без плана
HTTP API возвращает `400` с тем же понятным текстом, который интерфейс выводит
в статусе чата.

## Проверка

1. Создайте задачу через `/task Статья` и попробуйте `/execute` до Markdown-плана: этап остаётся `PLANNING` и появляется объяснение.
2. После запуска `EXECUTION` верните `[[TASK_TRANSITION:DONE]]`: маркер скрыт, задача остаётся на текущем шаге.
3. Завершите все шаги. В `VALIDATION` верните `[[TASK_VALIDATION_FAILED:2]]`: карточка показывает второй шаг и список выполненного обрезан до первого.
4. Поставьте задачу на паузу, перезапустите сервер и используйте `/resume`: агент продолжает сохранённый шаг, а не создаёт новый план.
5. После проверки верните `[[TASK_VALIDATION_PASSED]]`: только тогда задача перейдёт в `DONE`.
