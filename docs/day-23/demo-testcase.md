# Демо-тесткейс: поиск → фильтр → query rewrite

- **ID:** RAG-23-01
- **Статус:** сценарий подготовлен; фактические результаты заполняются после реализации и живого прогона.
- **Цель:** показать Top-K до и после фильтра, сохранение исходного вопроса при rewrite, сравнение трёх режимов и корректный отказ при пустой выдаче.

## Предусловия

- Выполнен план `docs/superpowers/plans/2026-10-04-day-23-relevance-filter.md`.
- Существует `docs/day-21/index.sqlite3`; запущена Ollama с моделью из метаданных индекса (`embeddinggemma` для текущей базы).
- Для выбранной модели ответа задан `ZAI_API_KEY` или `DEEPSEEK_API_KEY`. В командах ниже используется `glm-4.7-flash`; при недоступности Z.AI можно **до начала прогона** заменить его на `deepseek-v4-flash` во всех командах и использовать `DEEPSEEK_API_KEY`.
- Команды выполняются из корня репозитория.

## Вопрос и эталон

- **Вопрос №10:** «Почему прошедших юнит-тестов и HTTP 200 недостаточно?»
- **Ожидаемая глава:** `premature-success.xhtml`.
- **Ожидаемые тезисы:** проверки могут пропустить сбой полного пользовательского сценария; нужна сквозная проверка.

Это удачный пример для показа фильтра. В сохранённом прогоне дня 22 первые пять результатов имели score `0.4352`, `0.4284`, `0.3843`, `0.3836`, `0.3793`. Первый относится к ожидаемой главе. При пороге `0.40` исходный запрос должен оставить два из пяти; это прогноз для текущего индекса, который нужно проверить живым запуском. Два оставшихся чанка не обязательно одинаково полезны: качество ответа проверяется отдельно.

## Шаги на демо

1. Показать базовую выдачу без фильтра и без rewrite:

   ```bash
   python3 deepseek-api/rag_day23.py ask "Почему прошедших юнит-тестов и HTTP 200 недостаточно?" --mode baseline --model glm-4.7-flash
   ```

   Ожидается `20 → 5`: CLI показывает число кандидатов до отбора, пять переданных чанков с ID/score и ответ. Среди источников должен быть `premature-success.xhtml`.

2. Показать отсечение при том же исходном вопросе:

   ```bash
   python3 deepseek-api/rag_day23.py ask "Почему прошедших юнит-тестов и HTTP 200 недостаточно?" --mode filtered --model glm-4.7-flash --top-k-before 20 --top-k-after 5 --min-similarity 0.40 --max-score-gap 0.08
   ```

   На текущем индексе ожидается `20 → 2`: чанки со score ниже `0.40` не должны попасть в ответный контекст. Ожидаемая глава должна остаться. Сравнить формулировки ответов и проверить, оба ли ожидаемых тезиса названы.

3. Показать rewrite и его наблюдаемое влияние на поиск:

   ```bash
   python3 deepseek-api/rag_day23.py ask "Почему прошедших юнит-тестов и HTTP 200 недостаточно?" --mode rewritten --model glm-4.7-flash --top-k-before 20 --top-k-after 5 --min-similarity 0.40 --max-score-gap 0.08
   ```

   CLI должен вывести исходный вопрос и полученный поисковый запрос. Сравнить список чанков с шагом 2. Ответ должен отвечать на **исходный** вопрос, даже если строка поиска изменилась. Число чанков и формулировка rewrite заранее не фиксируются.

4. Показать безопасное поведение при заведомо строгом пороге на том же вопросе:

   ```bash
   python3 deepseek-api/rag_day23.py ask "Почему прошедших юнит-тестов и HTTP 200 недостаточно?" --mode filtered --model glm-4.7-flash --min-similarity 0.99
   ```

   Для текущего индекса ожидается `20 → 0`, ответ о недостатке сведений и отсутствие фиктивных ссылок. Если фактический score когда-либо достигнет `0.99`, этот шаг нужно проверить тестом с подставными кандидатами, а не объявлять отказ по живому запросу гарантированным свойством порога.

5. Проверить отдельно от десяти контрольных вопросов запрос вне книги:

   ```bash
   python3 deepseek-api/rag_day23.py ask "Какая погода завтра в Москве?" --mode filtered --model glm-4.7-flash
   ```

   Ожидаемый смысловой результат — отказ отвечать по книге. Фиксированный similarity-порог не гарантирует его: если чанки прошли и модель ответила по существу, зафиксировать это как неудачу фильтра. Второй вне-книжный запрос из спецификации проверить перед демо и занести в отчёт, не добавляя его к десяти контрольным вопросам.

6. Открыть заранее подготовленный `docs/day-23/comparison.md` со статусом `проверено`. Показать строки вопроса №10 и сводку всех десяти вопросов: попадание ожидаемой главы, число чанков, баллы полноты и проверку опоры на текст. Отдельно назвать случаи, где фильтр или rewrite ухудшили результат, если они есть.

## Критерии прохождения

- `baseline` не переписывает вопрос и передаёт не больше пяти из двадцати кандидатов.
- `filtered` сохраняет только чанки, удовлетворяющие обоим порогам; при нуле чанков не вызывает модель ответа.
- `rewritten` показывает новый поисковый запрос, но задаёт модели ответа исходный вопрос.
- Во всех трёх режимах используется один и тот же индекс и одна модель ответа; источники и score доступны для проверки.
- Отчёт содержит фактическую оценку качества. Уменьшение числа чанков само по себе не считается улучшением ответа.
- Вне-книжный запрос честно классифицирован как отказ или неудача фильтра.
