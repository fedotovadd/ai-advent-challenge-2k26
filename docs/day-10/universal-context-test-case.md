# Тест-кейс: «Соседская полка — два варианта запуска»

Цель: сравнить Sliding Window, Facts и Branching по качеству ответов, сохранению требований, расходу токенов и удобству работы.

Это 15 одинаковых запросов для всех трёх стратегий. Первая часть проверяет память, вторая — работу с двумя вариантами ТЗ и возврат к прежнему варианту.

Branching управляет независимыми историями, поэтому отдельно сравниваем сохранение требований и удобство работы с вариантами.

## Подготовка

Создайте три чистых агента с одинаковой моделью и настройками генерации:

- Sliding Window: N = 6 сообщений.
- Facts: N = 6 сообщений, обновление фактов после каждого запроса.
- Branching: история активной ветки без дополнительного сжатия.

Не исправляйте ответы и не напоминайте потерянные требования во время основного прогона. Отправляйте каждый запрос отдельным сообщением.

Одинаковый системный промпт:

```text
Ты помогаешь собирать техническое задание.
На обычное сообщение отвечай одним предложением до 20 слов.
Не повторяй ранее сообщённые требования без просьбы.
Учитывай только утверждённые решения; гипотезы не являются решениями.
Явное изменение заменяет предыдущее значение.
Отменённое значение без замены становится неизвестным.
Независимые варианты наследуют общие требования, но не изменения друг друга.
На контрольные вопросы отвечай в запрошенном формате.
Неизвестные значения обозначай null. Не угадывай.
Все ответы пиши на русском языке.
```

## Запросы 1–10: общие требования

### 1. Название и назначение

```text
Собираем ТЗ проекта «Соседская полка»: сервис бронирования бумажных книг в районной библиотеке. Аудитория — жители одного района.
```

### 2. Платформа и язык

```text
В MVP делаем только веб-сайт, удобный на телефоне. Отдельного мобильного приложения не будет. Язык интерфейса — только русский.
```

### 3. Бюджет и срок

```text
Утверждённый бюджет — 120000 рублей. Дата запуска — 15 декабря 2026 года.
```

### 4. Ограничения

```text
Бронирование бесплатное, онлайн-оплаты не будет. Для регистрации достаточно email. Телефон не запрашиваем и не храним. Уведомления отправляем только по email, без SMS.
```

### 5. Функции и размещение

```text
Нужны поиск книги по названию, фильтр по автору и экспорт активных броней в CSV. Сервер размещаем в инфраструктуре библиотеки.
```

### 6. Изменение договорённостей

```text
Утверждаем бюджет 180000 рублей вместо 120000. Прежнюю дату запуска отменяем; новую пока не определили. Остальные требования сохраняются.
```

### 7. Дополнительные функции

```text
Пользователь может отменить свою бронь в личном кабинете. Сотрудник библиотеки видит список активных броней и находит бронь по номеру.
```

### 8. Гипотеза, которую нельзя запоминать как решение

```text
Коллега предложил бюджет 500000 рублей, платное бронирование и SMS. Это только гипотеза для обсуждения, ничего из предложенного не утверждаем.
```

### 9. Контрольная точка общей памяти

```text
Покажи действующие общие требования. Верни только JSON с ключами project, purpose, audience, platform, language, payments, registration, phone, budget_rub, launch_date, notifications, hosting. budget_rub — число, launch_date — дата YYYY-MM-DD или null. Остальные значения — короткие строки или null. Не угадывай.
```

### 10. Критерии приёмки

```text
Добавь критерии приёмки: один экземпляр нельзя одновременно забронировать двум пользователям; при отсутствии свободных экземпляров бронирование недоступно. Лист ожидания в MVP не делаем.
```

После ответа на запрос 10 **в агенте Branching сохраните checkpoint «Общее ТЗ» и создайте от него две ветки: A и B**. Обе должны начинаться именно от этого checkpoint.

В Sliding Window и Facts продолжайте тот же диалог: там варианты разделяются названиями в сообщениях.

## Запросы 11–12: вариант A

В Branching переключитесь на ветку A.

### 11. Изменения для A

```text
Создаём независимый вариант A на основе общего ТЗ. Только для A утверждаем бюджет 240000 рублей и запуск 1 февраля 2027 года. Остальные общие требования сохраняются. Эти изменения не меняют общее ТЗ и будущий вариант B.
```

### 12. Проверка A

```text
Покажи действующее ТЗ варианта A. Верни только JSON с ключами project, purpose, audience, platform, language, payments, registration, phone, budget_rub, launch_date, notifications, hosting. Неизвестные значения — null.
```

## Запросы 13–14: вариант B

В Branching переключитесь на ветку B, созданную от «Общего ТЗ», а не от A.

### 13. Изменения для B

```text
Теперь создаём независимый вариант B на основе общего ТЗ, без изменений варианта A. Только для B утверждаем бюджет 160000 рублей и два языка интерфейса: русский и английский. Остальные общие требования сохраняются. Вариант A не меняем.
```

### 14. Проверка B

```text
Покажи действующее ТЗ варианта B. Верни только JSON с ключами project, purpose, audience, platform, language, payments, registration, phone, budget_rub, launch_date, notifications, hosting. Неизвестные значения — null.
```

## Запрос 15: возврат к A

В Branching переключитесь обратно на A.

```text
Возвращаемся к ранее согласованному варианту A. Покажи его ТЗ: сначала JSON с ключами project, purpose, audience, platform, language, payments, registration, phone, budget_rub, launch_date, notifications, hosting. Неизвестные значения — null. Затем предложи план запуска из пяти пунктов, соблюдая ограничения именно варианта A. Не переноси в него решения других вариантов.
```

## 1. Качество ответа

На каждом контрольном запросе — 9, 12, 14 и 15 — начисляйте по одному баллу за каждое правильное поле: максимум **12 баллов за ответ**.

Если назначение сервиса оказалось внутри `project`, а `purpose=null`, фиксируйте отдельно:

- информация сохранилась;
- структура ответа нарушена, балл за `purpose` не начисляется.

Дополнительно оцените финальный план: по одному баллу за каждый критерий, максимум **5**.

- Ровно пять понятных действий.
- План учитывает бюджет 240000 рублей.
- План учитывает запуск 1 февраля 2027 года.
- Не противоречит ограничениям A: без приложения, платежей, телефона, SMS и английского интерфейса.
- Включает проверку запрета двойного бронирования.

Новые действия в плане допустимы как предложения; они не должны выдаваться за ранее утверждённые требования.

## 2. Стабильность

Сравните ответы на запросы 12 и 15. Между ними требования A не менялись.

Зафиксируйте:

- сколько полей A были правильными на шаге 12, но стали ошибочными на шаге 15;
- появились ли в A бюджет 160000 или английский язык из B;
- появилась ли в B дата запуска из A;
- вернулись ли отменённая дата или старый бюджет;
- стали ли гипотезы про SMS, оплату и 500000 рублей утверждёнными решениями.

Для проверки повторяемости проведите три полных прогона с чистыми агентами. Один прогон показывает отдельный результат, но не устойчивость стратегии.

## 3. Расход токенов

Считайте фактические токены всех вызовов:

```text
Всего = входные токены основных ответов
      + выходные токены основных ответов
      + входные и выходные токены обновления памяти.
```

Для Facts обязательно включайте вызовы извлечения фактов.

Для Branching складывайте **фактически выполненные запросы за весь тест**. Не складывайте накопленные счётчики A и B напрямую: общий участок диалога может учитываться в обоих.

Общий префикс оплачивается повторно, когда он снова отправляется модели, но само создание checkpoint или переключение ветки не расходует токены, если не вызывает модель.

Запишите отдельно расход:

- на общую часть, запросы 1–10;
- на варианты, запросы 11–15;
- на весь тест.

## 4. Удобство для пользователя

Во время основного прогона не делайте исправлений. После него оцените:

- сколько дополнительных действий потребовалось: checkpoint, создание и переключение веток;
- понятно ли, какой вариант сейчас активен;
- можно ли проверить, что агент помнит;
- можно ли вернуться к A без повторного ввода его требований.

Если хотите измерить восстановление после ошибок, проведите отдельный этап: добейтесь правильного ТЗ A и запишите число дополнительных сообщений и токенов. Не включайте их в основные 15 запросов.

## Краткие выводы по критериям

- **Качество ответа.** Facts и Branching правильно воспроизвели все 12 полей ТЗ на каждой контрольной точке; Sliding Window — только 2–3 поля. Финальные планы слабее самих ТЗ: Sliding Window и Facts получили 4/5, Branching — в среднем 4,3/5. Основной недочёт — отсутствие явной проверки двойного бронирования; также встречались нарушения формата JSON.
- **Стабильность: сохранение важных деталей.** Во всех трёх прогонах Facts и Branching сохранили общие требования и не смешали решения A и B. Sliding Window с N = 6 стабильно терял ранние детали: уже на шаге 9 правильными оставались только бюджет и отменённая дата. Отсутствие дальнейшего ухудшения при возврате к A не означает сохранность полного ТЗ. Эти выводы относятся к трём прогонам данного сценария; технические сбои API учтены отдельно.
- **Расход токенов.** В среднем за полный сценарий: Sliding Window — около 13,1 тыс., Branching — 16,6 тыс., Facts — 33,4 тыс. с учётом обновления памяти. Sliding Window оказался самым экономным, но потерял большую часть требований. Branching сохранил ту же полноту ТЗ, что и Facts, при примерно вдвое меньшем расходе. В этом сценарии обновление Facts после каждого запроса не дало экономии токенов.
- **Удобство для пользователя.** Sliding Window прост в управлении, но потерянные требования придётся вводить заново — оценка 2/5. Facts позволяет видеть сохранённые факты и вести один диалог, однако варианты нужно явно обозначать в сообщениях — 4/5. Branching удобен для работы с вариантами: активная ветка видна, к A можно вернуться без повторения требований; цена этого удобства — шесть дополнительных операций с checkpoint и ветками — 4/5. Оценки удобства субъективны.

### Технические сбои и повторяемость

Первая попытка второго Sliding Window прервалась на шаге 15 с HTTP 502; первые 14 шагов и состояние ошибки сохранены отдельно в `results/failed-attempt-run-2-sliding_window.json` и `results/failed-attempt-state.json`. Повтор был начат на чистом агенте и прервался на шаге 11 с HTTP 502. Состояние ошибки сохранено в `results/failed-attempt-2-state.json`. Приложение скрывает причину исключения провайдера; по этим данным нельзя достоверно определить, был ли это сетевой сбой или другая ошибка API. В обоих случаях usage отсутствует, поэтому расход не принимается за ноль.

Во втором зачтённом прогоне восстановлен точный snapshot после шага 10 и отправлены шаги 11–15 через тот же класс Agent. Неудачный пользовательский запрос, который приложение успело записать, в восстановленное состояние не вошёл. Требования и ответы не редактировались. После этого все оставшиеся вызовы завершились успешно. Это три полных логических прогона, но второй содержит техническое возобновление; результаты не следует описывать как три бесперебойных запуска.

### Интерфейс и сохранённое состояние

На [http://127.0.0.1:8010](http://127.0.0.1:8010) оставлены три агента третьего прогона: **Sliding Window · Соседская полка**, **Facts · Соседская полка**, **Branching · Соседская полка**. В Branching активна A; checkpoint «Общее ТЗ» содержит ровно первые 10 ходов, A и B созданы от него. Возврат в A не требует повторного ввода требований.

Шесть дополнительных операций Branching — сохранить checkpoint, создать A, создать B, переключиться в A, затем в B и обратно в A. Это число смысловых операций, не отдельных кликов и вводов текста; в прогоне они вызваны программно. При отдельной проверке интерфейса активная ветка и переключение проверены без дополнительных запросов к модели. Для Facts виден словарь памяти. У Sliding Window доступны только оставшиеся сообщения, полную утраченную память проверить невозможно.

Состояние для обычного запуска лежит в `deepseek-api/data/agents.json` и исключено из Git по правилам проекта. Его копия — [results/run-3-agents.json](results/run-3-agents.json). Полные 15 запросов и ответов каждого агента, факты на каждом шаге и фактический usage сохранены в девяти файлах `results/run-N-STRATEGY.json`. В интерфейсе Sliding Window и Facts видны только последние шесть сообщений — штатное поведение стратегий. В Branching видны 26 сообщений A или 24 сообщения B.

Температура всех тестовых запросов — 0, что видно в сохранённых payload. Ползунок температуры в текущем интерфейсе не сохраняется между загрузками страницы и после обновления может показывать 1; это настройка следующей отправки, а не значение уже выполненного теста.

Контрольные ответы для чтения: [results/control-answers.md](results/control-answers.md). Оценки по полям: [results/evaluation.json](results/evaluation.json). Дополнительных сообщений для исправления качества после теста не отправлялось; стоимость восстановления качества отдельно не измерялась.
