# День 10: показательные сценарии проверки контекста

Это готовые примеры для ручного тестирования Sliding Window, Facts, Branching и Summary.
Реплики ниже ещё не прогонялись через модель: эталоны описывают правильные ответы,
а прогнозы — гипотезы, которые нужно проверить.

Начните со сценария 1. Он лучше всего подходит для демонстрации задания.
Сценарий 2 проверяет не только запоминание, но и корректность обновления памяти.
Сценарий 3 демонстрирует пользу и изоляцию веток.

## Подготовка честного сравнения

1. Для каждого сценария создайте **четырёх новых агентов**, по одному на режим.
   Не переключайте режимы внутри уже пройденного сценария: удалённая история не
   восстановится, а сохранённые facts могут повлиять на следующий опыт.
2. Выберите одну и ту же модель и одинаковые настройки ответа. Для оконных режимов
   установите **N=6**. Это шесть отдельных сообщений, не шесть пар вопрос–ответ.
   У Summary собственное окно в 10 сообщений и пакетное обновление; N=6 к нему не применяется.
3. Оставьте учебный лимит контекста пустым, режим переполнения выключенным,
   стоп-последовательность пустой. Для основных ответов можно оставить лимит токенов
   пустым, чтобы обрезанный ответ не выглядел как потеря памяти. Формат — обычный текст:
   итоговый JSON будет запрошен отдельной репликой.
4. Поставьте одинаковую температуру. Для DeepSeek V4 основные вызовы сейчас используют
   thinking по умолчанию: параметр temperature в этом режиме не действует. Поэтому
   даже одинаковое значение не гарантирует одинаковые ответы.
5. Отправляйте каждый пронумерованный блок **отдельным сообщением**, дожидаясь ответа.
   Не отправляйте модельному агенту эталоны и объяснения из этого документа.
6. Если агент задаёт дополнительные вопросы, не меняйте сценарий: отправляйте следующую
   готовую реплику. Иначе режимы получат разные условия.

Одинаковый **System prompt** для всех четырёх агентов:

```text
Ты помогаешь собирать требования и фиксировать решения пользователя.
На обычное сообщение отвечай одним коротким предложением, до 20 слов.
Не повторяй весь список ранее сообщённых требований и не добавляй собственных решений.
Предложения и гипотезы не считай утверждёнными решениями.
Последнее явное изменение пользователя заменяет прежнее решение.
Если пользователь отменил договорённость без замены, считай вопрос открытым.
На контрольный вопрос отвечай в запрошенном формате.
Если сведений нет в доступном контексте, укажи null, не угадывай.
```

Короткие промежуточные ответы нужны, чтобы ассистент не переносил всю старую историю
в каждое новое сообщение. Иначе длинные ответы сами превращаются в дополнительную память
и скрывают разницу между стратегиями.

В текущем Summary первая сводка обычно появляется перед **11-м пользовательским
сообщением**, если каждый предыдущий ход завершился одним ответом. Сценарий из пяти
реплик не продемонстрирует сжатие. В 15-ходовых сценариях ниже оно успевает сработать.

## Сценарий 1. «Соседская полка»: помнит ли агент исходное ТЗ?

**Что проверяем:** ранние ограничения, изменение бюджета, качество итогового ТЗ и
сохранение сведений между двумя контрольными вопросами.

**Порядок:** одинаковые 15 сообщений всем четырём агентам. Для Branching здесь просто
продолжайте основную ветку, без создания дополнительных веток: это контроль с полной историей.

### Реплики

**1.**

```text
Собираем ТЗ проекта «Соседская полка». Это сервис бронирования бумажных книг в небольшой районной библиотеке. Аудитория — жители одного района.
```

**2.**

```text
Нужен только веб-сайт, удобный на телефоне. Отдельное мобильное приложение в MVP не входит. Интерфейс только на русском языке.
```

**3.**

```text
Бронирование бесплатное. Онлайн-оплаты не будет. Для регистрации достаточно email; номер телефона не запрашиваем и не храним.
```

**4.**

```text
На MVP выделено 120000 рублей. Запуск — 15 декабря 2026 года. Уведомления отправляем только по email, без SMS.
```

**5.**

```text
В каталоге нужны поиск по названию и фильтр по автору. Карточка книги содержит обложку, автора и короткое описание.
```

**6.**

```text
Утверждено изменение: бюджет увеличен до 180000 рублей вместо 120000. Дата запуска и остальные решения не меняются.
```

**7.**

```text
Пользователь может отменить свою бронь в личном кабинете. Сотрудник библиотеки видит список активных броней.
```

**8.**

```text
Нужен экспорт активных броней в CSV. Сервер размещаем в инфраструктуре самой библиотеки.
```

**9 — первая проверка.**

```text
Проверь текущие договорённости. Верни только JSON с ключами project, purpose, audience, platform, language, payments, registration, phone, budget_rub, launch_date, notifications, hosting. budget_rub — число, launch_date — строка YYYY-MM-DD. Остальные значения — короткие строки. Для неизвестных сведений используй null. Не добавляй новых решений.
```

**10.**

```text
На главной странице показываем новые поступления. Пользователь может открыть список книг выбранного автора.
```

**11.**

```text
В личном кабинете разделяем активные и завершённые брони. У каждой брони виден её текущий статус.
```

**12.**

```text
Для сотрудников нужен поиск брони по номеру. Номер брони показывается пользователю сразу после её создания.
```

**13.**

```text
Если свободных экземпляров нет, кнопка бронирования недоступна. Лист ожидания в MVP не делаем.
```

**14.**

```text
Добавь критерий приёмки: система не позволяет одновременно забронировать один и тот же экземпляр двум пользователям.
```

**15 — итоговая проверка.**

```text
Собери итоговое ТЗ по всем действующим договорённостям. Сначала верни JSON с ключами project, purpose, audience, platform, language, payments, registration, phone, budget_rub, launch_date, notifications, hosting. budget_rub — число, launch_date — строка YYYY-MM-DD. Для неизвестных сведений используй null. После JSON предложи пять пунктов плана запуска. План должен соблюдать наши ограничения. Не заполняй пробелы догадками.
```

### Эталон: 12 проверяемых полей

| Поле | Правильное содержание на ходах 9 и 15 |
|---|---|
| project | Соседская полка |
| purpose | Бронирование бумажных книг в районной библиотеке |
| audience | Жители одного района |
| platform | Веб-сайт для телефона; отдельное приложение исключено из MVP |
| language | Только русский |
| payments | Бесплатно, без онлайн-оплаты |
| registration | По email |
| phone | Не запрашивается и не хранится |
| budget_rub | 180000; прежние 120000 не являются действующим бюджетом |
| launch_date | 2026-12-15 |
| notifications | Только email, без SMS |
| hosting | Инфраструктура библиотеки |

Для каждого поля ставьте 1 балл, только если смысл сохранён полностью и нет
противоречия. Формулировки могут отличаться. Например, «адаптивный сайт» без указания,
что приложение не входит в MVP, — неполное сохранение соответствующего поля.

**Практическое качество:** отдельно оцените пять пунктов плана запуска. Хороший план
связан с библиотекой и бронированием, учитывает актуальные бюджет/срок и не предлагает
оплату, SMS, сбор телефонов или мобильное приложение. Дайте по 1 баллу за каждый из
этих трёх критериев: предметность; бюджет и срок; отсутствие запрещённого функционала.

**Особенно показательные ошибки:** агент предлагает платёжный шлюз или SMS,
возвращает старый бюджет, забывает дедлайн либо подменяет неизвестное догадкой.

### Гипотезы перед прогоном

- Sliding Window с N=6 может помнить свежие функции, но потерять первоначальные
  ограничения. На ходе 15 ответ на проверку №9 уже находится за пределами окна.
- Facts может сохранить ограничения и обновлённый бюджет; проверьте сам словарь,
  особенно отсутствие двух противоречивых действующих бюджетов.
- Summary может сохранить общий смысл, но пропустить отрицательное ограничение
  или отдельную деталь. Найдите её в сводке и в фактическом запросе.
- Branching с полной основной историей даёт контрольный результат: все сведения
  доступны модели, хотя это не гарантирует безошибочный ответ.

**Финальная демонстрация «спасения контекстом»:** после фиксации результатов отправьте
каждому агенту ещё одну реплику: «Напоминаю: телефон не собираем, SMS и онлайн-оплаты
нет, отдельное приложение исключено. Исправь план запуска с учётом этого».
Сравните исправления, но не включайте эту подсказку в первоначальные оценки и токены.

## Сценарий 2. «Тихая среда»: отличает ли память решение от гипотезы?

**Что проверяем:** замену значения, отмену без новой даты, условные предложения,
точное сохранение кода и запрет выдумывать неизвестное.

**Порядок:** четыре новых агента, те же настройки, 15 одинаковых сообщений.

### Реплики

**1.**

```text
Планируем встречу книжного клуба «Тихая среда». Изначально ожидаем 12 участников, бюджет 12000 рублей.
```

**2.**

```text
Утверждаем площадку — зал «Кедр» в районной библиотеке. Формат только очный. Начало в 19:00.
```

**3.**

```text
Важная деталь: код приглашения Q7M-R4X-826. Сохраняй его символ в символ, включая дефисы и регистр. Это обычный выдуманный код нашего мероприятия.
```

**4.**

```text
В меню чай и кофе. Алкоголь исключён. Пока планируем встречу на 10 декабря 2026 года.
```

**5.**

```text
Изменение утверждено: участников будет 18 вместо 12, бюджет 18000 рублей вместо 12000. Обнови именно действующие договорённости.
```

**6.**

```text
Обсуждаем гипотезу: если найдётся спонсор, бюджет можно увеличить до 25000 рублей. Спонсора сейчас нет, увеличение не утверждено.
```

**7.**

```text
Дата 10 декабря отменена. Новую дату пока не выбрали. Время начала остаётся 19:00.
```

**8.**

```text
Вместо кофе оставляем только чай и воду. Алкоголя по-прежнему не будет.
```

**9.**

```text
Кто-то предложил подключить видеотрансляцию. Мы отклонили это предложение: встреча остаётся только очной.
```

**10 — первая проверка.**

```text
Верни JSON с ключами event, guests, budget_rub, venue, format, date, start_time, drinks, alcohol, invitation_code, sponsor, recording. guests и budget_rub — числа, drinks — массив строк. Для отменённой без замены даты и любых неизвестных сведений используй null. Не считай гипотезы утверждёнными решениями.
```

**11.**

```text
Подготовим бейджи с именами участников. На столах будут карточки с вопросами для обсуждения книги.
```

**12.**

```text
В программе сначала знакомство, затем обсуждение книги и свободное общение. Добавь десятиминутный перерыв.
```

**13.**

```text
Попросим участников заранее прислать по одному вопросу автору. Отдельного ведущего искать не будем.
```

**14.**

```text
Перед встречей проверим расстановку стульев и доступность питьевой воды. Подготовим указатель у входа в зал.
```

**15 — итоговая проверка.**

```text
Выдай окончательные действующие договорённости: JSON с ключами event, guests, budget_rub, venue, format, date, start_time, drinks, alcohol, invitation_code, sponsor, recording. guests и budget_rub — числа, drinks — массив строк. Для неизвестного — null. Не восстанавливай отменённые значения, не утверждай гипотезы и не придумывай ответы.
```

### Эталон: 12 проверяемых пунктов

| Поле | Правильное содержание на ходах 10 и 15 |
|---|---|
| event | Тихая среда |
| guests | 18 |
| budget_rub | 18000; ни 12000, ни гипотетические 25000 |
| venue | Зал «Кедр» в районной библиотеке |
| format | Только очный, без видеотрансляции |
| date | null — прежняя дата отменена, новая не выбрана |
| start_time | 19:00 |
| drinks | Чай и вода; без кофе |
| alcohol | Исключён |
| invitation_code | Q7M-R4X-826 — точное совпадение |
| sponsor | Сейчас отсутствует; достаточно явного «нет»/«не найден» |
| recording | null — запись мероприятия вообще не обсуждалась |

Здесь `date=null` означает отмену решения, а `recording=null` — отсутствие сведений.
Оба ответа правильные, но по разным причинам. Отказ от трансляции не равен запрету
записи: если агент запрещает запись, он придумал дополнительное решение.

**Что смотреть в Facts:**

- Действующее число участников — 18, бюджет — 18000.
- Возможность бюджета 25000 допустимо сохранить как условную гипотезу, но не как
  утверждённый бюджет.
- Действующая дата удалена или явно обозначена как невыбранная. Сам по себе
  исторический факт «10 декабря отменено» не является ошибкой памяти.
- В меню нет действующего решения о кофе; отклонённая трансляция не становится планом.
- Код приглашения не изменился.

**В Summary** проверьте те же различия по смыслу. Наличие старого числа в сводке
допустимо, если ясно сказано, что оно отменено. Ошибка — использовать его как актуальное.

**Самый наглядный разбор:** откройте одновременно итоговый ответ, facts/summary и
«Отправлено в API». Если верный факт был в запросе, а модель ответила неправильно,
это ошибка использования контекста. Если факт отсутствовал в запросе, проблема
возникла при выборе или преобразовании памяти.

## Сценарий 3. «Листок»: две несовместимые версии одного проекта

**Что проверяем:** копирование общего состояния, отсутствие влияния соседней ветки,
возврат к прежнему ответу и восстановление после перезапуска.

**Настройки:** новый агент, режим Branching. Не сравнивайте стоимость двух веток с
одним линейным диалогом: это разное количество работы.

### Общий префикс: 8 сообщений

**1.**

```text
Проект «Листок»: сервис записи на мастер-классы студии керамики. Делаем MVP для взрослых новичков.
```

**2.**

```text
Общий бюджет 200000 рублей. Запуск планируем на 20 ноября 2026 года.
```

**3.**

```text
Базовая версия — мобильный веб-сайт на русском языке. Уведомления отправляем по email.
```

**4.**

```text
У пользователя есть каталог мастер-классов и форма записи. В форме только имя и email, без телефона.
```

**5.**

```text
В базовом варианте онлайн-оплаты нет: посетитель платит в студии.
```

**6.**

```text
Администратор задаёт количество мест. Когда группа заполнена, запись закрывается.
```

**7.**

```text
Нужна выгрузка записей в CSV. Пользователь должен уметь отменять свою запись.
```

**8.**

```text
Базовые договорённости зафиксированы. Дальше хотим исследовать два разных варианта проекта, сохраняя исходный вариант отдельно.
```

Теперь в интерфейсе:

1. Введите название **«Общее ТЗ»** и нажмите **«Сохранить checkpoint»**.
2. Выберите эту точку, создайте ветку **«Экономный»**.
3. От той же точки создайте ветку **«Расширенный»**.
4. Убедитесь, что доступны **Основная**, **Экономный**, **Расширенный**.
   Создание ветки автоматически её не выбирает — используйте список «Активная ветка».

### Ветка «Экономный»: 4 сообщения

Выберите «Экономный» и отправьте:

**А1.**

```text
Только для этого варианта меняем бюджет на 90000 рублей, запуск — 1 ноября 2026 года. Базовый бюджет и срок в этой ветке заменены.
```

**А2.**

```text
Онлайн-оплаты в этом варианте нет. Оставляем только веб-сайт; мобильное приложение не разрабатываем.
```

**А3.**

```text
Внутренний маркер этого варианта — «Сосна». Это утверждённое обозначение. Остальные общие требования сохраняются.
```

**А4.**

```text
Верни только JSON с ключами project, audience, budget_rub, launch_date, platform, payments, notifications, phone, export, marker. Используй исключительно текущие договорённости; неизвестное обозначай null.
```

Сохраните ответ А4 для последующего сравнения.

### Ветка «Расширенный»: 4 сообщения

Переключитесь на «Расширенный». **До отправки** убедитесь, что в её чате нет А1–А4.
Затем отправьте:

**Б1.**

```text
Только для этого варианта меняем бюджет на 350000 рублей, запуск — 10 декабря 2026 года. Базовый бюджет и срок в этой ветке заменены.
```

**Б2.**

```text
В этом варианте утверждаем онлайн-оплату. Делаем веб-сайт и отдельное мобильное приложение. Это явное изменение базового варианта.
```

**Б3.**

```text
Внутренний маркер этого варианта — «Клён». Это утверждённое обозначение. Остальные общие требования сохраняются.
```

**Б4 — тот же вопрос, что А4.**

```text
Верни только JSON с ключами project, audience, budget_rub, launch_date, platform, payments, notifications, phone, export, marker. Используй исключительно текущие договорённости; неизвестное обозначай null.
```

### Эталон различий

| Пункт | Основная | Экономный | Расширенный |
|---|---|---|---|
| Бюджет | 200000 | 90000 | 350000 |
| Запуск | 2026-11-20 | 2026-11-01 | 2026-12-10 |
| Платформа | Мобильный веб-сайт | Только веб-сайт | Веб-сайт + отдельное приложение |
| Оплата | В студии, без онлайн-оплаты | В студии, без онлайн-оплаты | Онлайн-оплата включена |
| Маркер | Не задавался, null | Сосна | Клён |

Общие требования во всех трёх вариантах: «Листок», взрослые новички, уведомления по
email, телефон не собирается, экспорт CSV. Для каждого ответа это ещё пять проверок.

### Проверки изоляции: 6 пунктов

1. В «Расширенном» нет сообщений А1–А4, а в фактическом запросе Б4 нет маркера «Сосна».
2. В ответе Б4 — бюджет 350000, дата 10 декабря, онлайн-оплата, приложение и «Клён».
3. Вернитесь в «Экономный» **без отправки нового сообщения**: прежний ответ А4 и его
   метрики остались теми же. Переключение не делает вызов к модели.
4. Повторите вопрос А4 в «Экономном»: действуют его собственные значения, не значения Б.
   Это дополнительный контрольный вызов — записывайте его стоимость отдельно.
5. Перейдите в «Основную» и отправьте вопрос А4: исходные бюджет/дата/оплата сохранены,
   маркер не задан. Этот контрольный вызов тоже учитывайте отдельно.
6. Перезагрузите страницу, а затем отдельно перезапустите сервер. Checkpoint, ветки и
   переписка должны сохраниться. После перезапуска выберите обе ветки и проверьте
   последние сообщения. Простое обновление страницы не заменяет проверку перезапуска.

**Сравнение удобства с другими режимами:** у них нет отдельного механизма альтернатив.
Можно создать по два независимых агента и вручную отправить общий префикс в каждый,
после чего продолжить А и Б. Это контрольный ручной способ: запишите лишние сообщения
и время, но не называйте его встроенным ветвлением.

**Сравнение расхода:** метрики каждой ветки включают общий префикс. Если есть ровно
две ветки и по основному диалогу после checkpoint не было новых вызовов:

`расход обеих веток = итог А + итог Б − расход общего префикса`.

Возьмите накопленные значения в общей точке и после А4/Б4. Считайте и токены, и стоимость
по одной формуле. Дополнительные проверки №4–5 записывайте отдельно. Не складывайте
показатели всех трёх веток: общий префикс будет посчитан несколько раз.

## Как сравнивать результаты

Используйте [шаблон протокола](results-template.md).

### 1. Качество ответа

Для сценария 1: полнота 12 полей + практический план 0–3 балла. Для сценария 2:
12 проверяемых пунктов. Для веток: по 10 полей А4 и Б4 плюс 6 проверок изоляции.
Любые выдуманные решения и противоречия записывайте явно.

Разделяйте **сохранение смысла** и **соблюдение формата**. Если цель написана в поле
project, а поле purpose пусто, смысл мог сохраниться, хотя JSON заполнен неправильно.
Сначала поставьте балл за поле по правилам, затем отдельно отметьте эту особенность.

### 2. Стабильность памяти внутри диалога

Сравните два контрольных ответа по каждому полю. Посчитайте, сколько правильно
отвеченных пунктов первой проверки осталось правильными во второй. Не ограничивайтесь
общей суммой: 5/12 → 5/12 может скрывать потерю одних и приобретение других фактов.

Для проверки повторяемости выполните сценарий три раза с новыми агентами. Запишите
диапазон баллов и средний расход. Три прогона дадут предварительное представление,
а не статистическое доказательство превосходства стратегии.

### 3. Токены и стоимость

После финального ответа запишите строку **«Все вызовы в истории этой ветки, включая
память»**. Она включает основной диалог и служебные обновления facts/summary.
Метрики последнего запроса и обычные метрики чата сами по себе не включают весь расход
служебной памяти. Для Facts отдельно запишите число обновлений и их токены; для Summary
— расход summary и число сжатых сообщений. Отмечайте, где API usage, а где оценка.

Не сравнивайте только последний ответ: экономия на входе может оказаться меньше затрат
на обновление памяти. Более дешёвый прогон с потерянными требованиями не равен лучшему.
Если произошли ошибки или повторы, запишите их: сетевые сбои без usage могут оставлять
часть фактического расхода неизвестной.

### 4. Удобство

Запишите измеримые вещи: сколько требований пришлось напомнить, сколько дополнительных
реплик потребовалось, сколько ручных действий нужно для альтернатив, удалось ли
найти причину ошибки в facts/summary/запросе. При желании поставьте субъективную оценку
1–5, обязательно с коротким объяснением.

## Короткий план демонстрации

1. На сценарии 1 показать ранние ограничения, а затем итоговые планы четырёх режимов.
2. Показать реальные блоки facts/summary и отправленные запросы.
3. На сценарии 2 показать бюджет 18000, неутверждённые 25000 и отменённую дату.
4. На сценарии 3 переключить «Экономный» → «Расширенный» → «Экономный» и показать разные решения.
5. Закончить таблицей качества, утраченных фактов, полного расхода и удобства.

Не требуется, чтобы какая-то стратегия обязательно ошиблась. Если все справились,
это тоже результат: сравните расход и усилия пользователя. Для дополнительной нагрузки
повторите весь сценарий с новыми агентами и N=4 в обоих оконных режимах. Менять N только
у одного режима или посреди прогона нельзя, если цель — сопоставимое сравнение.
