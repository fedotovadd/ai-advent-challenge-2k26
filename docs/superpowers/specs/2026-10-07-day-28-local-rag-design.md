# День 28 — полностью локальный RAG и сравнение моделей

## Цель и исходное состояние

Пользователь задаёт вопрос по книге *Agentic Design Patterns* и получает ответ с проверенными источниками и цитатами. В локальном режиме построение вектора запроса, поиск, повторное ранжирование и генерация выполняются на этом компьютере. Для сравнения тот же набор вопросов и те же найденные фрагменты передаются облачной модели, если доступен её ключ. Результат дня — работающий без облачных ключей RAG-сценарий и отчёт о качестве, скорости и стабильности на фактических прогонах.

Готовый индекс Недели 6 — `docs/day-21/index.sqlite3`: SQLite, 603 чанка двух стратегий, модель эмбеддингов `embeddinggemma`, размерность 768, SHA-256 EPUB `4fec2775f38facf660ce9b2801fea833a565193e00e549af5df3b9f07534fab8`. Используется структурная стратегия; индекс и EPUB не пересобираются. `document_index.search_index` уже обращается к локальной Ollama для эмбеддинга вопроса. `rag_day24.answer_question_day24` ищет Top-20, локальным cross-encoder отбирает до пяти чанков с порогом 0,50, а затем проверяет JSON, ссылки и дословность цитат. Сейчас его список допустимых моделей в `rag_citations.MODELS` состоит только из облачных моделей. День 27 уже добавил маршрут `providers.ask_model` для `qwen2.5:1.5b` к `http://127.0.0.1:11434/v1/`, без облачных ключей и автоматических повторов.

`rag_chat.py` дня 25 выполняет **два** вызова выбранной LLM на ход: подготовка самостоятельного поискового запроса и изменений памяти, затем ответ по найденному контексту. Поэтому локальный режим чата считается готовым только тогда, когда оба вызова идут в Ollama. Веб-чат дня 27 — обычный чат без поиска; один лишь выбор локальной модели в нём не выполняет задание дня 28.

## Рассмотренные варианты

| Подход | Выгода | Ограничение |
|---|---|---|
| Расширить RAG дня 24 и переиспользовать адаптер дня 27 **(выбран)** | Сохраняются индекс, поиск, порог, проверка цитат и единый контракт ответа; проще контролировать сравнение | Нужны отдельный сценарий сравнения и проверка локальности reranker |
| Использовать только `rag_agent.py` дня 22 | Минимум изменений | Нет машинной проверки цитат и отказа при слабой опоре |
| Написать новый RAG-пайплайн | Полная свобода интерфейса | Дублирование поиска и проверки, выше риск сравнить разные пайплайны |

Основной пользовательский интерфейс — CLI одного вопроса поверх дня 24. Существующий CLI-чат дня 25 получает поддерживаемый локальный режим через ту же модель; отдельный веб-интерфейс для RAG не нужен.

## Пользовательский сценарий и поток данных

1. Пользователь заранее устанавливает зависимости и один раз загружает в локальное хранилище Ollama `embeddinggemma` и `qwen2.5:1.5b`; модель cross-encoder `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` также доступна из локальных файлов. Подготовка может требовать интернет, сам RAG-запрос — нет.
2. Запускает `rag_day24.py ask "<вопрос>" --model qwen2.5:1.5b` из корня проекта. Команда читает готовый индекс, создаёт вектор вопроса через локальный `/api/embed`, ищет структурные чанки в SQLite, ранжирует локальным cross-encoder и отправляет выбранные фрагменты локальной модели через `providers.ask_model`.
3. CLI печатает `Ответ`, `Источники`, `Цитаты`. Для содержательного ответа все цитаты проходят имеющуюся проверку `chunk_id` и точного вхождения в переданный текст. При пустом контексте или обоснованном отказе печатается существующее «Не знаю» и `Источники: нет`, `Цитаты: нет`.
4. Пользователь может запустить `rag_chat.py chat --session <имя> --model qwen2.5:1.5b`. И подготовка запроса/памяти, и ответ используют локальную модель; поиск и reranking остаются локальными. Формат существующего SQLite-хранилища чата не меняется.

Поток: `вопрос → Ollama embeddinggemma → SQLite-индекс дня 21 → локальный cross-encoder → до 5 фрагментов → Ollama qwen2.5:1.5b → валидатор цитат → ответ`. В облачном сравнении изменяется только последний генеративный провайдер. Если порог отсёк все чанки, генеративная модель не вызывается в обоих режимах.

## Функциональные требования

- Добавить точное имя `qwen2.5:1.5b` в допустимые модели RAG и CLI, сохранив прежние облачные варианты. Для локального выбора использовать готовый маршрут `providers.ask_model`; облачные ключи не требуются. Не допускать имён Ollama с суффиксом `:cloud` и скрытого перехода на другую модель.
- Сохранить общий для моделей системный промпт, текст вопроса, порядок и состав выбранных чанков, температуру 0, порог 0,50 и действующие правила проверки цитат. Ограничить длину генерации локального ответа конечным `max_tokens` (начальное значение 768, включая ответ JSON); фактический параметр записывать в результаты. Для сравнения облачной модели использовать то же ограничение, если провайдер его поддерживает. Перед генерацией ограничить каждый передаваемый фрагмент первыми 600 символами **для обеих моделей**; валидатор цитат должен проверять именно эти 600 символов. Сохранить точный текст сформированного промпта и настройки запроса. Адаптер должен возвращать `finish_reason` и доступные счётчики токенов: `length` или превышение проверенного лимита контекста считаются ошибкой, а не успешным ответом. Эффективный контекст Ollama проверяется перед живым прогоном; если его нельзя подтвердить, это ограничение явно отмечается в отчёте.
- Для локальной модели запрашивать JSON-режим поддерживаемого Ollama OpenAI-совместимого API. Если облачный API допускает тот же режим, использовать его в парном прогоне; иначе зафиксировать различие настроек как ограничение сравнения. Существующий валидатор остаётся обязательным: JSON-режим сам по себе не доказывает правильность цитат. На невалидный ответ допускается прежняя одна попытка исправления с теми же фрагментами; после второй ошибки вернуть ошибку, не выдавая неподтверждённый текст.
- В локальном режиме URL для эмбеддингов должен быть loopback Ollama на том же компьютере; адрес генерации уже зафиксирован как `127.0.0.1:11434`. Указать понятную ошибку для отсутствующего индекса, остановленной Ollama, отсутствующей embedding/генеративной модели, недоступного локального reranker, timeout, пустого или невалидного ответа. Не скрывать сбои как `no_evidence`.
- Cross-encoder должен загружаться только из заранее подготовленных локальных файлов: при локальном запуске запретить неявную загрузку из Hugging Face Hub (`local_files_only` либо проверенный локальный путь). Если файлов нет, команда завершается с инструкцией подготовить их заранее. В режиме локального запроса нельзя обращаться к DeepSeek, Z.AI, Ollama Cloud или другому внешнему сервису.
- Для CLI-чата дня 25 прогнать двухходовый сценарий на русском, включая вопрос со ссылкой на предыдущую реплику. Состояние памяти и поисковый запрос после первого вызова модели проверяются существующим валидатором; ошибка подготовки или ответа не фиксирует незавершённый ход в истории и не вызывает облачный fallback. Если компактная модель не проходит этот сценарий, исправить локальные инструкции/формат ответа в рамках текущего контракта, а ограничение качества отразить в отчёте.

## Сравнение и измерения

Базовый набор — десять вопросов из `docs/day-22/control_questions.json`. Для каждого вопроса поиск и reranking выполняются **один раз**; полученные `chunk_id`, порядок, переданный текст и score фиксируются до генерации. Все три прохода стабильности обеих моделей повторно используют **этот же** снимок retrieval для вопроса. Локальная и облачная модели получают один и тот же вопрос, промпт и фрагменты. В отчёте указываются точные имена и идентификаторы моделей, версии Ollama и библиотек, ОС/процессор/память, хеш индекса, параметры поиска/генерации и доступность облачного ключа. Старые ответы дня 24/25 можно использовать только как исторический ориентир: они не заменяют парный прогон.

| Критерий | Как измерить и записать |
|---|---|
| Качество | Для каждого вопроса сохранить оба исходных ответа, статусы и цитаты. Вручную оценить полноту по ожидаемым тезисам (0/1/2), смысловую опору значимых утверждений на цитаты (`да/частично/нет`), уместность отказа и ошибки фактов. Автоматически отметить валидность JSON, долю ответов с проверенными цитатами, попадание ожидаемой главы в общий retrieval. Дословная цитата сама по себе не считается доказательством смысла. |
| Скорость | Монотонными часами измерить отдельно embedding + поиск, reranking, генерацию (включая исправляющий вызов), суммарное время и число вызовов LLM. Прогрев и первый холодный запрос записать отдельно. Для десяти пар показать время каждого вопроса, медиану и максимум; не трактовать разницу как чистую скорость моделей, если сеть или формат ответа различаются. |
| Стабильность | Выполнить по три одинаковых прохода набора для доступных моделей с температурой 0. Записать успешные ответы, обоснованные отказы, сбои соединения/timeout, невалидный первый и итоговый JSON, число исправлений и различия статуса/существенных тезисов между повторами. Отдельно остановить Ollama и подтвердить ошибку без облачного fallback, затем восстановить сервис и повторить запрос. |

Облачный кандидат — `deepseek-v4-flash`, уже используемый чатом дня 25; его вызовы допустимы только в явном режиме сравнения с `DEEPSEEK_API_KEY`. Если ключ недоступен, локальный RAG всё равно реализуется и проверяется; в отчёте облачная часть помечается «не проверено: нет ключа», а сохранённые прежние ответы могут сопровождаться только качественной, непарной иллюстрацией. Нельзя заполнять отсутствующие измерения ожидаемыми числами.

Результаты дня 28 сохраняются отдельно от существующих артефактов: машинные записи прогонов и `docs/day-28/comparison.md`. Для каждого вопроса нужны общий снимок контекста, отдельные локальный/облачный результаты или явный статус пропуска, времена стадий, ошибки и ручная оценка. Промежуточные результаты сохраняются после каждого вопроса, чтобы обрыв сравнения не стирал уже полученные данные. Файлы дней 21–27 не перезаписываются.

## Изменения и проверка

- `deepseek-api/rag_citations.py` и `rag_day24.py`: допуск локальной модели, одинаковый для пар промпт, ограничение длины ответа, локальные ограничения адреса и подготовка результатов для сравнения; текущий валидатор цитат сохраняет смысл и контракт.
- `deepseek-api/rag_reranker.py`: явная загрузка cross-encoder из локальных файлов для локального режима, без неявного сетевого скачивания. Обычный облачный режим не должен ломаться.
- `deepseek-api/rag_chat.py`: поддержка локальной модели на обоих LLM-вызовах; при необходимости узкая корректировка промпта подготовки для JSON компактной модели.
- `deepseek-api/rag_day28.py compare` и `docs/day-28/`: команда принимает `--results` и `--report` (по умолчанию `docs/day-28/results.json` и `docs/day-28/comparison.md`), сохраняет общий retrieval и парные результаты без изменений прежних отчётов; при отсутствии `DEEPSEEK_API_KEY` фиксирует пропуск облачных вызовов. `deepseek-api/README.md`: подготовка моделей, команда локального запроса/чата, команда сравнения и признаки полностью локального запуска.
- Тесты с подставными embedder, reranker и провайдерами проверяют единый контекст для пары, отсутствие облачных ключей/запросов в локальном режиме, проверку цитат, отказ без вызова LLM, две локальные генерации в ходе чата, ошибки и сохранение результатов. Живой прогон с выключенными облачными ключами и внешним доступом проверяет весь путь от вопроса до цитат; профилированные тесты и полный `unittest` проверяют регрессии.

## Критерии приёмки

1. На готовом индексе дня 21 локальная команда даёт хотя бы один фактический содержательный ответ с источником и дословной проверенной цитатой; вопросы без оснований дают явный отказ. Ответ по существу вручную сверен с книгой.
2. Локальный запрос и двухходовый чат завершаются при отсутствии `DEEPSEEK_API_KEY` и `ZAI_API_KEY` и без внешней сети. Все сетевые обращения в этих сценариях ограничены loopback Ollama; reranker не пытается скачать модель. Остановка Ollama даёт явную ошибку без облачного fallback.
3. Для всех десяти вопросов сохранены реальные локальные результаты, времена стадий, ошибки и ручная оценка. При доступном ключе сохранены парные облачные результаты с тем же контекстом и указанными различиями настроек; без ключа отсутствие сравнения отмечено явно.
4. Отчёт содержит обоснованный вывод по качеству, скорости и стабильности, включая слабые места компактной модели, долю исправлений JSON и ограничения размера выборки. Ни один невалидный или неподтверждённый ответ не показан как успешный RAG-ответ.

## Текущий статус

Это спецификация, а не отчёт о выполнении дня 28. Наличие индекса и кода проверено в репозитории; прошлые результаты подтверждают загрузку моделей в дни 26–27. Текущая доступность Ollama из ограниченного окружения не подтверждена: запрос к `127.0.0.1:11434` вернул `operation not permitted`. Перед реализацией и живым прогоном доступность сервиса следует проверить в разрешённой локальной среде. Каталог кэша cross-encoder найден, но полнота файлов и офлайн-загрузка пока не проверены.
