# День 28 — локальная LLM в существующем RAG

## Цель

Подключить локальную генерацию к RAG-пайплайну книги *Agentic Design Patterns* и получить ответ с проверенной цитатой без облачных ключей и внешней сети. На одном наборе вопросов сравнить локальную и, если доступен ключ, облачную модель по качеству, скорости и стабильности.

## Что уже есть и что переиспользуем

- Готовый индекс Недели 6: `docs/day-21/index.sqlite3`. Он содержит 603 чанка двух стратегий и создан локальной моделью `embeddinggemma` с размерностью 768. Для поиска используется структурная стратегия. Индекс, EPUB и эмбеддинги чанков **не пересоздаются**.
- `document_index.search_index` получает эмбеддинг нового вопроса через локальную Ollama и ищет по готовому SQLite-индексу. Создание вектора вопроса при каждом поиске не означает пересоздания индекса.
- `rag_day24.answer_question_day24` выполняет поиск Top-20, локальный reranking, отбор до пяти чанков с порогом 0,50 и проверку JSON, ссылок и дословных цитат. Этот путь остаётся основой RAG.
- `providers.ask_model` уже направляет точное имя `qwen2.5:1.5b` в локальную Ollama по `http://127.0.0.1:11434/v1/`. Облачный кандидат для сравнения — `deepseek-v4-flash`.

Основной интерфейс дня 28 — CLI одного вопроса и команда сравнения. Доработка чата дня 25 и веб-интерфейса не входит в задачу.

## Локальный сценарий

После однократной подготовки `embeddinggemma`, `qwen2.5:1.5b` и файлов cross-encoder пользователь запускает из корня проекта:

```bash
PYTHONPATH=deepseek-api python -m deepseek_app.rag.rag_day28 ask "<вопрос>"
```

Поток данных: `вопрос → локальная Ollama embeddinggemma → готовый SQLite-индекс → локальный cross-encoder → до 5 фрагментов → локальная Ollama qwen2.5:1.5b → существующий валидатор цитат → ответ`.

CLI показывает ответ, источники и цитаты. Если порог отсёк все чанки, LLM не вызывается и возвращается существующий отказ «Не знаю». Отказ модели также отображается как отказ. Сбой Ollama, отсутствие модели или файлов reranker, timeout, нехватка контекста модели и невалидный ответ считаются ошибками, а не отказом из-за отсутствия сведений. Облачного fallback нет.

Во время локального запроса URL эмбеддингов допускает только loopback Ollama; маршрут генерации уже зафиксирован в `providers.ask_model`. Cross-encoder загружается из заранее подготовленных локальных файлов с `local_files_only=True` или по проверенному локальному пути. Загрузка моделей и зависимостей может потребовать интернет **до** запуска RAG; сам запрос его не требует.

## Минимальные изменения

1. Добавить `qwen2.5:1.5b` в допустимые модели `rag_citations.py` и CLI `rag_day24.py`, сохранив прежние облачные варианты. Использовать существующий `providers.ask_model`; имена Ollama с суффиксом `:cloud` не принимать.
2. Для локального режима запретить произвольный внешний `--ollama-url` и неявную сетевую загрузку cross-encoder. При отсутствующих локальных файлах дать инструкцию по предварительной подготовке.
3. Сохранить текущие Top-20 → Top-5, порог 0,50, температуру 0, системный промпт, лимит фрагмента 1800 символов и действующий валидатор. Не сокращать фрагменты до 600 символов и не менять индекс. Для локальной генерации запросить JSON-режим; для облачного сравнения применять его, если API поддерживает, и записать различие, если нет. При невалидном ответе разрешена существующая одна попытка исправления по тем же фрагментам; после неё вернуть ошибку.
4. Выделить из пути дня 24 переиспользуемые шаги получения контекста и генерации по готовому контексту, чтобы команда сравнения не повторяла retrieval отдельно для каждой модели. Не дублировать поиск, reranking и проверку цитат в новом коде.
5. Добавить `python -m deepseek_app.rag.rag_day28 compare` и краткие команды подготовки и запуска в `deepseek-api/README.md`. Результаты записывать в `docs/day-28/results.json` и `docs/day-28/comparison.md`; артефакты дней 21–27 не перезаписывать.

## Парное сравнение

Базовый набор — десять вопросов из `docs/day-22/control_questions.json`. Для каждого вопроса один раз построить вектор, найти и ранжировать чанки. Сохранить снимок: `chunk_id`, порядок, score и точный текст, переданный генератору. Обе модели получают одинаковые вопрос, системный промпт и снимок контекста; различаются модель и необходимые настройки провайдера. Если контекст пуст, обе генерации пропускаются.

Для каждого вопроса выполнить **три прохода всего** по одному сохранённому снимку; первый проход входит в эти три. При пустом контексте каждый проход фиксирует отказ без вызова модели. Облачные вызовы в сценарии дня 28 выполняются только командой `compare` при наличии `DEEPSEEK_API_KEY`. Без ключа записать для них статус «не проверено: нет ключа»; локальные измерения и отчёт всё равно выполняются. Прежние ответы дней 24–25 не заменяют парные результаты.

| Критерий | Что записать |
|---|---|
| Качество | Исходный ответ и статус каждой модели; ручную оценку ответа на заданный вопрос (0/1/2), смысловой опоры на найденные фрагменты (`да/частично/нет`), уместности отказа и фактических ошибок. Тезисы контрольного набора помогают при сверке, но дополнительные сведения из главы не считаются обязательными, если вопрос их не запрашивает. |
| Скорость | Монотонными часами отдельно измерить embedding + поиск, reranking и каждую генерацию, включая исправляющий вызов. Для первого локального запроса показать измеренное полное время; для повторов — время генерации на сохранённом контексте. Указать время по вопросам, медиану и максимум. Не представлять повторно использованный retrieval как заново измеренное время каждого повтора. |
| Стабильность | Для трёх запусков записать успешные ответы, отказы, ошибки, невалидные первые и итоговые ответы, число исправлений и различия существенных тезисов между повторами. Температура — 0, но одинаковый результат не гарантируется. |

Сохранять снимок контекста до вызовов моделей, а прогресс — после каждого результата или ошибки, чтобы сбой облачного вызова или прерывание не стирали локальные ответы. При возобновлении сверять индекс и настройки с сохранёнными и использовать тот же снимок. Отчёт строится только по реально полученным данным. Записать имена моделей, ключевые настройки, версию Ollama и используемых библиотек, идентификатор или хеш индекса и ограничение сравнения, если форматы запросов провайдеров различаются.

## Проверка и критерии приёмки

- Тесты с подставными embedder, reranker и провайдерами проверяют общий снимок контекста для пары, отсутствие облачных вызовов в локальном режиме, проверку цитат, отказ без генерации, ошибку вместо неподтверждённого ответа и сохранение результатов после каждого вызова.
- Живой локальный запрос выполняется с удалёнными `DEEPSEEK_API_KEY` и `ZAI_API_KEY` и без внешнего доступа. Все его сетевые обращения ограничены loopback Ollama; reranker не пытается скачать файлы. Остановка Ollama даёт явную ошибку без fallback.
- На готовом индексе получен хотя бы один содержательный ответ с источником и дословной проверенной цитатой; его смысл вручную сверен с книгой. Вопрос без достаточного основания даёт явный отказ.
- Для всех десяти вопросов сохранены реальные локальные результаты трёх проходов и измерения выполненных стадий. При наличии ключа сохранены парные облачные результаты; без него отсутствие облачного сравнения указано явно.
- `docs/day-28/comparison.md` содержит вывод по качеству, скорости и стабильности, включая ограничения маленькой выборки. Ни один невалидный или неподтверждённый ответ не отмечен как успешный.

## Предварительные условия

Наличие индекса и нужного кода проверено в репозитории. Прошлые результаты подтверждают загрузку моделей в дни 26–27, но доступность Ollama в текущем окружении и полнота локальных файлов cross-encoder должны быть проверены перед живым прогоном. Если подготовка не завершена, результатом проверки служит конкретная ошибка и инструкция, а не предполагаемые измерения.
