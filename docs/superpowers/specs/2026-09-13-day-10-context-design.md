# День 10: четыре режима управления контекстом

Продолжение day-09 в отдельной ветке day-10. Переключатель contextStrategy:
sliding_window (по умолчанию), facts, branching, summary; windowSize=10 (1–100).

Sliding Window физически оставляет последние N сообщений user/assistant; текущий
user входит в N. System prompt не входит. Увеличение N не восстанавливает удалённое.
Facts обновляются отдельным JSON-вызовом после каждого принятого user: patch set/delete
по текущим facts и последнему окну. Исправления заменяют старые значения, удаление
явное. Это ограниченный словарь фактов, а не пересказ. Ошибка extraction видима;
не теряем прежние facts, не продолжаем с неподтверждённой памятью. Расход extraction
сохраняется отдельно, включая успешную extraction перед ошибкой основного ответа.

Branching отправляет полную историю только активной ветки. Checkpoint — неизменяемая
копия состояния, от неё создаются две или больше веток. Ветки изолируют сообщения,
facts, метаданные и метрики; переключение не вызывает модель. Настройки модели и
стратегии общие для агента. Ветки/checkpoints переживают перезапуск. При переходе
в оконный режим история активной ветки обрезается; явные checkpoints сохраняются.

UI: выбор стратегии/N, видимый словарь facts и его расход, checkpoint/создание/
переключение веток. Блокировать смену контекста во время отправки. Старые настройки
и история загружаются с миграцией; по уточнению пользователя Summary сохранён четвёртым режимом; сводка передаётся только в нём.

Сравнение Sliding Window, Facts и Branching описано в
[универсальном тест-кейсе](../../day-10/universal-context-test-case.md):
15 запросов, общая часть для проверки памяти и два независимых варианта ТЗ.
Качество и сохранение требований оцениваются по эталону, токены — по фактическим
вызовам с учётом памяти, удобство — по дополнительным действиям пользователя.
Один прогон не является статистической оценкой стабильности модели.
