# Контролируемые переходы задачи — дизайн

## Цель

Сделать жизненный цикл задачи явным и недопускающим пропуск этапов: `PLANNING → EXECUTION → VALIDATION → DONE`. Ассистент должен объяснять недопустимый переход и подсказывать следующий допустимый шаг, не изменяя сохранённое состояние.

## Границы

Изменение развивает существующий автомат задачи из Дня 13 и использует модель памяти из Дня 11. `TaskContext` остаётся данными в `context.taskState` и сохраняется в `data/agents.json`; работа не зависит от неявной истории чата.

В область работы входят код автомата, обработка команд и маркеров ответа, тесты и пользовательская документация. Интерфейс карточки задачи и формат хранимого `TaskContext` не меняются.

## Модель переходов

`task_state.py` объявляет единственный граф переходов:

| Из состояния | Допустимые целевые состояния | Условие |
| --- | --- | --- |
| `PLANNING` | `EXECUTION` | До команды `/execute` сохранён валидный Markdown-план с 1–24 шагами; успешный `/execute` является единственным утверждением плана. |
| `EXECUTION` | `PLANNING`, `VALIDATION` | Возврат в планирование — только по `/planning`; валидация — только после завершения всех шагов. |
| `VALIDATION` | `EXECUTION`, `DONE` | Доработка возвращает к выполнению; завершение допускается только после успешной проверки. |
| `DONE` | — | Задача неизменяема; можно создать следующую. |

Новая единая функция проверяет каждую смену этапа. Она получает текущую задачу, целевой этап и причину перехода, проверяет граф и условия, затем возвращает структурированный результат: `accepted`, копию `task`, `reason` и `nextAction`. Команды и служебные маркеры не меняют `stage` напрямую.

Для `VALIDATION → DONE` добавляется отдельное подтверждение `[[TASK_VALIDATION_PASSED]]`. Оно разрешено только в `VALIDATION`, означает, что агент завершил проверку результата, и только оно запускает конечный переход. Старый маркер `[[TASK_TRANSITION:DONE]]` больше не даёт модели завершить задачу сам по себе.

Для явной доработки из `VALIDATION` используется `[[TASK_VALIDATION_FAILED:<номер шага>]]`, где номер находится в диапазоне от 1 до общего числа шагов. Контракт переводит задачу в `EXECUTION`, удаляет из `done` выбранный шаг и все следующие, выставляет `step`, `current` и `expectedAction` на выбранный шаг. После доработки задача повторно проходит `EXECUTION → VALIDATION`; это исключает дублирование завершённых шагов.

## Реакция на ошибку

При попытке перейти в недопустимое состояние автомат сохраняет исходную задачу без изменений. Пользователь получает краткое объяснение причины и ближайшее действие. Обработчик агента добавляет `reason` в видимый ответ и не поглощает ошибку перехода.

| Недопустимое действие | Реакция и следующее действие |
| --- | --- |
| `/execute` без плана | «Нельзя начать выполнение без утверждённого плана. Подготовьте план и используйте `/execute`.» |
| Переход к `VALIDATION` до завершения шагов | «Сначала завершите текущий шаг плана.» |
| Завершение из `PLANNING` или `EXECUTION` | «Сначала завершите все шаги и пройдите валидацию.» |
| Завершение без `[[TASK_VALIDATION_PASSED]]` | «Сначала завершите проверку результата.» |
| `[[TASK_VALIDATION_FAILED:<номер>]]` вне `VALIDATION` или с неверным номером | «Нельзя вернуть задачу на доработку: укажите существующий шаг после начала валидации.» |
| Любой переход из `DONE` | «Задача уже завершена. Создайте новую через `/task Название`.» |
| Метка `[[TASK_STEP_DONE]]` вне `EXECUTION` | «Текущий этап не позволяет завершить шаг. Следуйте ожидаемому действию задачи.» |

Все распознанные служебные метки (`[[TASK_STEP_DONE]]`, `[[TASK_TRANSITION:DONE]]`, `[[TASK_VALIDATION_PASSED]]`, `[[TASK_VALIDATION_FAILED:<номер>]]`) удаляются из текста для пользователя независимо от положения и допустимости. Для недопустимой метки возвращается отказ из таблицы, а исходный `TaskContext` остаётся без изменений. Это исключает утечку технических токенов и не позволяет модели обойти правила через текст ответа.

## Пауза и продолжение

`/pause` остаётся разрешённой операцией в незавершённых этапах, но не является сменой этапа. Она сохраняет `stage`, `step`, `current` и ожидаемое действие. `/resume` снимает только флаг паузы; следующий вызов продолжает сохранённый текущий этап и шаг, а не создаёт новый план и не перепрыгивает в другой этап.

## Интеграция и тестирование

Новый контракт используется для `/execute`, `/planning`, маркера завершённого шага, перехода к `VALIDATION` и маркера успешной валидации. Тесты на уровне `task_state` закрепят граф, предусловия, неизменность состояния при отказе, причины отказа и очистку служебных маркеров. Интеграционные тесты агента подтвердят, что понятный отказ возвращается в чат и сохраняется корректное состояние после паузы и продолжения.

Ключевые сценарии:

1. `/execute` без плана отклоняется с объяснением и остаётся в `PLANNING`.
2. Метка `DONE` в `EXECUTION` отклоняется, скрывается из ответа, состояние и прогресс не меняются.
3. Последний завершённый шаг переводит задачу только в `VALIDATION`; `DONE` возможен только после `[[TASK_VALIDATION_PASSED]]`.
4. `[[TASK_VALIDATION_FAILED:2]]` возвращает задачу ко второму шагу, очищает завершённый суффикс и требует снова пройти валидацию.
5. Пауза в `EXECUTION`, сохранение и восстановление продолжают тот же шаг после `/resume`.
