# День 23 — фильтрация релевантности и query rewrite

## Цель и границы

Добавить к RAG дня 22 второй этап после векторного поиска: из Top-20 структурных чанков отбирать не более Top-5 по порогу косинусного сходства. Добавить переписывание вопроса для поиска и сравнить три режима на тех же десяти вопросах. Итогом являются работающий CLI, машинные результаты и отчёт с ручной оценкой ответов.

Веб-интерфейс, состав EPUB, чанкинг, модель эмбеддингов и SQLite-схема не меняются. Данные и отчёт дня 22 сохраняются. Отдельный cross-encoder не добавляется: задание допускает фильтр релевантности, а существующий индекс уже возвращает cosine similarity.

## Основание для порога

В `docs/day-22/results.json` ожидаемая глава присутствует в Top-5 всех десяти вопросов. Значения score у её чанков заметно различаются: например, 0,435 для вопроса №10 и 0,752 для вопроса №8. Поэтому порог 0,50 заведомо удалил бы полезный источник для вопроса №10. Начальные значения фиксируются до нового прогона: `min_similarity=0.40`, `max_score_gap=0.08`. Они являются параметрами эксперимента, а не доказанной универсальной границей релевантности.

## Режимы и поток данных

| Режим CLI | Запрос для поиска | Получение кандидатов | Контекст для ответа |
|---|---|---|---|
| `baseline` | Исходный | Top-20 | Первые Top-5 без фильтра; эквивалентно RAG дня 22 |
| `filtered` | Исходный | Top-20 | Пороговый отбор, затем не более Top-5 |
| `rewritten` | Переписанный LLM | Top-20 | Тот же пороговый отбор, затем не более Top-5 |

Сначала `document_index.search_index` возвращает Top-20 структурных чанков, отсортированных по score. Фильтр сохраняет кандидат, если одновременно `score >= min_similarity` и `score >= best_score - max_score_gap`. Порядок сохранённых чанков остаётся исходным; это фильтрация, а не изменение ранга. После фильтра берутся первые пять. Допустимы 0–5 результатов: добирать отклонённые чанки до пяти нельзя. Для пустой выдачи возвращается фиксированный ответ «В найденных фрагментах книги нет достаточных сведений для ответа.» без вызова модели ответа и без ссылок на источники.

Параметры `top_k_before`, `top_k_after`, `min_similarity` и `max_score_gap` доступны в CLI. Значения по умолчанию: 20, 5, 0,40 и 0,08. Проверяются `top_k_before >= top_k_after > 0`, `-1 <= min_similarity <= 1`, `0 <= max_score_gap <= 2`; `bool`, NaN и бесконечности отклоняются в программном API. Один и тот же индекс и его модель эмбеддингов используются во всех режимах.

Для `rewritten` существующий `providers.ask_model` получает исходный вопрос и короткую инструкцию: вернуть одну поисковую формулировку на русском языке, сохранить предмет, отрицания и конкретные сущности, не добавлять фактов и не отвечать на вопрос. Температура 0, лимит ответа 120 токенов (передаётся как именованный аргумент `max_tokens=120` в `ask_model`). Пустая или многострочная формулировка вызывает понятную ошибку; тихого перехода к исходному запросу нет. Переписанный запрос используется только для поиска. Модели ответа передаётся исходный вопрос и найденные фрагменты. Текст rewrite сохраняется в результате.

Во всех трёх режимах ответ создаётся тем же провайдером, системной инструкцией, нумерацией источников и ограничением текста чанка в 1800 символов, что и в дне 22. Для одного сравниваемого вопроса модель и температура одинаковы; для всего нового прогона модель фиксируется в настройках и не меняется при возобновлении. Изначальный CLI дня 22 остаётся совместимым.

## Интерфейсы и файлы

- `deepseek-api/rag_relevance.py`: чистая функция `select_chunks(candidates, *, min_similarity, max_score_gap, top_k_after)` и функция `rewrite_query(question, *, model, ask)`; в обеих легко подменить внешние зависимости в тестах.
- `deepseek-api/rag_agent.py`: выделить общий формирователь промпта и вызов модели ответа, не меняя формат `answer_question` и команды дня 22.
- `deepseek-api/rag_day23.py`: `answer_question_day23(question, mode, ...)`, `evaluate(...)` и CLI `ask`/`evaluate`. Команды из корня проекта: `python3 deepseek-api/rag_day23.py ask "..." --mode baseline|filtered|rewritten` и `python3 deepseek-api/rag_day23.py evaluate`. Общие `--index` и `--ollama-url` идут до имени команды, остальные настройки — после.
- `docs/day-23/results.json`, `docs/day-23/comparison.md`: отдельный фактический прогон. До прогона эти файлы не создавать.
- `deepseek-api/tests/test_rag_relevance.py`, `deepseek-api/tests/test_rag_day23.py`: проверки фильтра, rewrite, маршрутизации режимов, отказа при пустой выдаче, CLI/оценки и возобновления.
- `deepseek-api/README.md`: команды и методика дня 23.

Возвращаемый результат одного вопроса содержит `question`, `mode`, `search_query`, `candidates_before` и `chunks_after` (ID, источник, раздел, score и текст; без вектора), `answer`, `answer_status`, `model`, настройки и метаданные индекса. Исходный вектор из строки SQLite не записывается в JSON. Для `baseline` поле `chunks_after` означает первые пять кандидатов.

## Сравнение и отчёт

Используются `docs/day-22/control_questions.json` и тот же индекс дня 21. Для каждого вопроса выполняются три режима. Отчёт показывает score и источники до/после отбора, число переданных чанков, попадание ожидаемой главы, переписанный запрос, а также таблицу ручной оценки ответов: полнота 0–2, подтверждение утверждений текстом и замечания о потере полезных сведений. Сводка сравнивает `baseline → filtered` для эффекта фильтра и `filtered → rewritten` для эффекта rewrite. Улучшение не объявляется заранее: возможные равные результаты и ухудшения также фиксируются.

Файлы результата и отчёта не перезаписываются без `--overwrite`. После каждого полного вопроса сохраняется `.partial`; возобновление разрешено только при совпадении хешей вопросов и индекса, модели ответа, `ollama_url`, версии инструкции, порогов и Top-K. В настройках также записывается имя embedding-модели из индекса. Для строгой воспроизводимости на одном Ollama-адресе должна оставаться та же версия модели: индекс не хранит digest весов. Сбой внешнего сервиса сохраняет уже законченные вопросы, не создавая итоговый отчёт. Смена модели ответа требует нового прогона с другими путями или осознанного перезапуска.

После завершения десяти вопросов итоговые `results.json` и **черновой** `comparison.md` записываются атомарно по отдельности; `.partial` удаляется только после проверки наличия обоих файлов. Если процесс остановился между двумя записями, повторный запуск с теми же настройками сверяет вопросы, настройки и отпечатки уже записанного JSON с `.partial` и создаёт только недостающий отчёт. Если оба итоговых файла существуют, но `.partial` ещё остался, совпадающий законченный прогон признаётся завершённым: файл прогресса удаляется, отчёт не меняется. Готовый отчёт автоматически не переписывается. Ручные баллы вносятся в черновой Markdown после прогона, затем ставятся дата проверки и статус «проверено»; только такой отчёт считается завершённым. Обычный повторный `evaluate` не меняет проверенный отчёт; явный `--overwrite` начинает новый прогон и потому требует предварительно сохранить нужные ручные оценки отдельно.

## Проверка и ограничения

Модульные тесты проверяют границу порога (`>=`), связь с лучшим score, сохранение порядка, Top-K, пустую выдачу, отсутствие rewrite в двух первых режимах, исходный вопрос в промпте ответа и отсутствие LLM-вызова при пустом контексте. Отдельно проверяются ошибки Ollama/провайдера и защита существующих результатов.

Живой прогон выполняется на десяти утверждённых вопросах; оценка смысла ответов производится вручную. Проверки вне книги используют вопросы «Какая погода завтра в Москве?» и «Сколько стоит билет на поезд Москва — Казань сегодня?». Для них ожидается отказ, но фиксированный порог его не гарантирует: каждый случай, где фильтр пропустил чанки и дал содержательный ответ, записывается как неудача проверки, а не скрывается подбором порога после прогона. Эти два вопроса не входят в среднюю полноту десяти вопросов. Косинусное сходство не является вероятностью релевантности. Фильтр не исправит неверный порядок высоко оценённых нерелевантных чанков; если это заметно в отчёте, отдельный cross-encoder становится следующим экспериментом.
