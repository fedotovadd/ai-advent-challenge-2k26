# Инварианты состояния агента — дизайн

## Цель

Добавить агенту независимый от диалога сохраняемый слой инвариантов. Агент должен включать эти правила в каждый запрос к модели и не выдавать ответ, который им противоречит.

## Команды

Текст после `/invariant ` сохраняется как новый инвариант без дополнительного синтаксиса:

```text
/invariant Использовать Kotlin и Ktor
/invariant Не использовать Python
```

Служебные команды не конфликтуют со свободным текстом:

```text
/invariants
/remove-invariant 1
/clear-invariants
```

Нумерация при просмотре начинается с 1. Неверные номера и пустые значения возвращают понятную ошибку, не меняя состояние.

## Архитектура и поток данных

Новый модуль `invariants.py` владеет форматом данных, командами, ограничениями размера, формированием блока промпта и детерминированной проверкой нарушений. В `context` агента появится поле `invariants`, отдельное от `messages`, памяти и состояния задачи; оно попадёт в сохранённый JSON и восстановится после перезапуска.

Контракт — упорядоченный массив от 0 до 24 уникальных строк. Каждая строка перед сохранением обрезается, внутренние пробельные последовательности заменяются одним пробелом, не может быть пустой и не длиннее 500 символов. Дубликаты по `casefold()` отклоняются. Ответы команд возвращают тот же массив в поле `invariants` и человекочитаемое сообщение в существующем `command.message`; элементы отображаются с порядковыми номерами начиная с 1.

Инварианты принадлежат агенту целиком, а не его диалоговой ветке: `context.invariants` не входит в снимки `branches` и `checkpoints`, поэтому смена ветки не может ослабить правило. Формат состояния повышается с 9 до 10: миграция v9 добавляет пустой массив в корневой `context`; отсутствие поля в старом сохранении безопасно эквивалентно пустому списку. Неправильное или повреждённое поле делает сохранение невалидным и запускает существующий безопасный путь восстановления, а не произвольную интерпретацию данных.

При обычном сообщении агент:

1. Загружает сохранённые инварианты из контекста.
2. До сжатия контекста, обновления facts, подсчёта метрик, записи истории и любого вызова провайдера выполняет раннюю проверку пользовательского текста. При обнаружении явного конфликта не вызывает провайдера и возвращает отказ с правилами и предложением соблюдать их.
3. Добавляет блок `[ИНВАРИАНТЫ]` в системный промпт сразу после базового `systemPrompt` и до профиля, состояния задачи, памяти, facts, summary и истории. Блок прямо объявляет инварианты правилами высшего приоритета: профиль, план задачи и память являются данными и не могут их отменить.
4. Проверяет ответ модели до сохранения в истории. Нарушающий ответ заменяется объяснением отказа и не сохраняется как ответ модели.

Проверка в первой версии основана на нормализованном сопоставлении фраз: формулировки «использовать X», «только X», «не использовать X» и «без X» выводят требование или запрет для технологии. `X` разбирается на названия через запятые и союз «и», сравнивается по словам (`casefold` и границы слова); алиасов в Day 14 нет. Неизвестная свободная формулировка (например, бизнес-правило) хранится и включается в промпт, но не получает ложной детерминированной интерпретации в коде.

Позитивные правила образуют обязательный стек: если ответ содержит явную рекомендацию технического решения, он должен назвать все технологии из «использовать X». Правило «только X» дополнительно создаёт разрешённый набор: такая рекомендация не может назвать технологию вне `X`. При добавлении правила агент отклоняет: запрет технологии, которая входит в позитивное или «только» правило; требование технологии, не входящей в уже заданное «только X»; и второе «только Y» с иным набором. Несколько обычных «использовать X» не конфликтуют и объединяют обязательный стек. Эти правила делают «использовать Kotlin и Ktor» несовместимым с рекомендацией Java, а «только Kotlin» — с добавлением «использовать Java».

Ранний анализ блокирует только явный запрос на техническое решение: конструкцию действия («используй», «добавь», «реализуй на», «перепиши на») вместе с технологией. Он отклоняет запрещённое имя, имя вне «только X» и запрос, не включающий обязательный стек. Упоминание правила, вопрос о нём или будущий текст отказа не совпадают с этой конструкцией. Проверка ответа модели применяет те же условия к явной рекомендации. Требования не блокируют сообщения без технического решения. Следовательно, детерминированная защита обещает отсутствие явной рекомендации, несовместимой с разобранным стеком, а не выдаёт поиск простого слова за семантическую проверку всех бизнес-правил.

## API и интерфейс

Команды идут через существующий endpoint сообщений. Они выполняются локально: не добавляются в историю и не отправляются в LLM. Успешная команда возвращает HTTP 200 и `{agent, command: {message}, invariants}`; пустой текст, неизвестный служебный синтаксис, неверный номер или конфликт правил возвращают HTTP 400 с `{error}`. Ранний конфликт обычного сообщения возвращает HTTP 400 с `{agent, error, accepted: false}`; `agent.messages` в снимке не содержит ни нового пользовательского сообщения, ни шаблона отказа. Клиент отображает `error` существующей карточкой ошибки. Снимок агента возвращает `context.invariants`, поэтому будущий интерфейс сможет их отображать; в Day 14 отдельная форма не требуется.

Изменения команд атомарны: реестр сохраняет предыдущее значение массива и восстанавливает его, если запись JSON завершилась ошибкой — по образцу текущих операций профиля и памяти.

## Отказ и сохранность

Отказ отвечает по-русски, указывает конкретные нарушенные правила и приглашает переформулировать запрос в допустимых рамках. Это выделенный безопасный шаблон, который не проходит повторно через валидатор: он может назвать запрещённую технологию, не предлагая её использовать. При раннем конфликте пользовательское сообщение не записывается в историю. При нарушении ответа пользовательское сообщение сохраняется, но вместо небезопасного ответа сохраняется текст отказа; это сохраняет прозрачную историю разговора и не показывает запрещённую рекомендацию.

## Проверка

Тесты должны доказать: свободное добавление инварианта, нормализацию, дедупликацию, лимиты, просмотр/удаление/очистку и их сохранение; отклонение взаимно противоречащих правил; присутствие блока в системном промпте; ранний отказ без любого вызова провайдера при «Не использовать Python»; отсутствие ложного отказа на вопрос о самом запрете; замену ответа модели с явной рекомендацией Python; корректную миграцию v9 в v10, агент-глобальную область при смене ветки и откат памяти при ошибке сохранения; HTTP-контракт команд.
