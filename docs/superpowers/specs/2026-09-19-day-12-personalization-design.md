# День 12 — профили пользователей

## Цель

Добавить в локальный чат сохраняемые профили пользователей. Каждый профиль хранит имя, стиль ответа, предпочитаемый формат и ограничения. Один профиль активен для всего приложения и автоматически влияет на каждый пользовательский запрос всех агентов, но не заменяет их системные инструкции или данные памяти.

## Решение

Ввести отдельную коллекцию `UserProfile`, принадлежащую `AgentRegistry`, а не отдельному агенту. Это повторяет разделение Codex: пользовательские предпочтения имеют глобальную область действия, а настройки агента и правила конкретной задачи остаются локальными.

Профиль имеет фиксированную схему:

```json
{
  "id": "profile-1",
  "name": "Пользователь",
  "style": "ясный и дружелюбный",
  "format": "краткие абзацы",
  "constraints": "без Markdown"
}
```

Перед валидацией каждое значение формы очищается методом `strip()`. `name` принимает от 1 до 80 символов, а `style`, `format` и `constraints` — от 1 до 500 символов. Идентификатор назначает сервер в форме `profile-<положительное число>`; клиент его не передаёт при создании и не может менять при редактировании. Имя должно быть уникально после `casefold()`; в состоянии хранится от 1 до 20 профилей. Некорректные данные отклоняются без изменения сохранённого состояния. Сервер всегда отдаёт нормализованные значения.

## Поток данных

1. При создании реестра загружаются профили, активный идентификатор и следующий идентификатор из общего JSON-состояния; для старых сохранений создаётся один профиль по умолчанию `profile-1`.
2. `GET /api/profiles` отвечает `200` и возвращает `{ "profiles": [<profile>], "activeProfileId": "profile-1" }`.
3. `POST /api/profiles` принимает объект ровно с четырьмя редактируемыми полями, создаёт следующий профиль, делает его активным, атомарно сохраняет состояние и отвечает `201` с `{ "profile": <profile>, "activeProfileId": "profile-N" }`.
4. `PUT /api/profiles/<profile-id>` принимает те же четыре поля, изменяет указанный профиль и отвечает `200` с `{ "profile": <profile> }`. `POST /api/profiles/<profile-id>/activate` принимает только пустое тело, меняет активный профиль и отвечает `200` с `{ "activeProfileId": "profile-N" }`. Неверный JSON, лишние или отсутствующие поля, пустые/длинные/повторяющиеся значения и непустое тело активации отвечают `400`; неизвестный id для редактирования или активации — `404`; сбой хранилища — существующим безопасным `500`.
5. Перед каждым пользовательским ответом `AgentRegistry` передаёт текущий активный профиль в `Agent.respond`. Профили не передаются в служебные вызовы обновления facts и summary: они не формируют ответ пользователю. Изолированный эксперимент дня 3 тоже исключён, чтобы его фиксированные стратегии оставались сопоставимы.
6. Агент формирует итоговую системную инструкцию в предсказуемом порядке: собственный `systemPrompt` агента; блок `Профиль пользователя` со строками `Имя`, `Стиль`, `Формат`, `Ограничения`; существующий контекст памяти. Заголовок профиля прямо говорит применять предпочтения только при отсутствии конфликта с предшествующими инструкциями. Настройка JSON остаётся параметром `response_format` для провайдера, но приложение не дописывает в system prompt никакой отдельной текстовой инструкции о валидном JSON или Markdown. Память по-прежнему явно помечена как контекст, а не инструкции.
7. В метаданных последнего пользовательского запроса сохраняются итоговый system prompt и неизменяемая копия активного `userProfile`, поэтому его применение можно проверить без вызова внешней модели.

## Интерфейс

В правой панели появляется раздел «Профиль пользователя» перед настройками ответа. В нём расположены выпадающий список имён и кнопка `+`. Список показывает активный профиль и все доступные имена. Нажатие на имя сначала сохраняет его активацию, а после успешного ответа открывает отдельное окно редактирования выбранного профиля; «Отмена» закрывает окно и отменяет только правки полей, но не уже сохранённую смену активного профиля. При ошибке активации меню остаётся открытым, редактор не появляется, а запрос к модели не отправляется. Нажатие на `+` в панели или «Новый профиль» в списке открывает отдельное окно создания. Формы имеют явные действия «Сохранить» и «Отмена»; новый профиль после сохранения становится активным. Пока смена, создание или редактирование сохраняется, отправка сообщения ждёт результата и при ошибке сохранения не вызывает модель. Профили не меняются при переключении, создании или удалении агента.

## Ошибки и совместимость

- Неверная форма JSON, лишние ключи, пустые после `strip()`, слишком длинные или неуникальные имена, переполненный список и неизвестный id дают определённый контрактом `400` или `404` и не меняют состояние профилей.
- Ошибка записи состояния даёт существующую безопасную ошибку хранилища и откатывает список, активный id и следующий id в памяти.
- Состояние версии 7 мигрируется до версии 8: в его корень добавляются `profiles` с одним профилем по умолчанию, `activeProfileId: "profile-1"` и `nextProfileId: 2`. Агенты, история, метрики и общая долговременная память сохраняются. Все старые `metadata` — включая снимки в ветках и checkpoints — получают `userProfile: null`, поскольку профиль тогда не применялся; новая валидация принимает и это историческое значение.
- В состоянии версии 8 корень имеет точную форму `version`, `nextId`, `sharedLongTerm`, `profiles`, `activeProfileId`, `nextProfileId`, `agents`. Загрузчик принимает его только если `profiles` — список из 1–20 нормализованных профилей с точным набором полей `id`, `name`, `style`, `format`, `constraints`; каждый id имеет вид `profile-N`, все ids уникальны, все имена уникальны после `casefold()`, `activeProfileId` принадлежит списку, а положительный `nextProfileId` больше номера каждого сохранённого id. Некорректное состояние v8 отклоняется целиком и запускает безопасное состояние по умолчанию. Новые метаданные имеют обязательное поле `userProfile` с полным снимком активного профиля, а исторические — `null`.
- Старые клиенты могут продолжать работать с маршрутами агентов: профиль добавляется отдельными маршрутами.

## Проверка

Тесты должны доказать:

1. Создание, редактирование и активация профилей сохраняют верные список, активный id и следующий id; повторяющееся имя или 21-й профиль отклоняются атомарно. Повреждённое состояние v8 с дублирующими id/именами, несуществующим активным id или плохим следующим id загружается как безопасное состояние по умолчанию.
2. Два отличающихся активных профиля формируют разные итоговые system prompts для одного и того же текста; в блоке присутствуют все четыре нормализованных поля.
3. После выбора профиль автоматически применяется к пользовательским запросам двух разных агентов, а снимок в метаданных не меняется при последующем редактировании или выборе другого профиля.
4. Порядок блоков точен при включённом JSON-режиме и непустой памяти: системная инструкция агента, профиль, память; в system prompt отсутствует прежняя дополнительная JSON-инструкция, а `response_format` по-прежнему передаётся провайдеру.
5. Профили переживают перезапуск реестра и миграцию состояния v7; старые основные, branch- и checkpoint-метаданные получают `userProfile: null`.
6. Каждый маршрут возвращает зафиксированные `200`/`201`/`400`/`404`/`500`; некорректный запрос не изменяет профиль, а сбой записи хранилища восстанавливает набор профилей и активный id в памяти.
7. Страница получает список профилей, показывает выпадающее меню имён, при клике на имя сначала активирует его и затем открывает его редактор, открывает отдельную форму создания через `+`, обращается к `POST`/`PUT`/`activate`, и блокирует отправку сообщения при неудачном сохранении.

## Вне объёма

Не добавляются удаление профилей, аккаунты, авторизация, профиль на отдельного агента и автоизвлечение предпочтений из сообщений. Для дня 12 достаточно ограниченного списка явно редактируемых общих профилей и одного активного профиля.
