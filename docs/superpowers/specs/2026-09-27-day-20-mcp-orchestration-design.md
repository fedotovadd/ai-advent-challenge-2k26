# День 20 — оркестрация нескольких MCP-серверов

## Цель

Показать, как агент в обычном чате выбирает инструменты нескольких подключённых
MCP-серверов, маршрутизирует каждый вызов к серверу-владельцу и выполняет
многошаговую задачу с передачей фактических результатов между вызовами.

Реализация продолжает существующий общий MCP-каталог и цикл вызова инструментов.
Фиксированный сценарий `/research` дня 19 остаётся отдельной демонстрацией
заранее заданного конвейера; день 20 проверяет выбор инструментов моделью.

## Рассмотренные варианты

1. **Фиксированный workflow в коде.** Порядок вызовов предсказуем, но выбор
   инструментов делает приложение. Это дублирует подход дня 19 и не проверяет
   маршрутизацию, запрошенную в задании.
2. **Модельная оркестрация через текущий MCP-каталог — выбранный вариант.**
   Модель выбирает очередной инструмент из объединённого списка доступных
   серверов; приложение валидирует вызов и направляет его владельцу. Это
   использует уже существующие `McpRegistry` и `tool_runtime`.
3. **Неограниченное число вызовов и произвольный граф.** Это гибче, но создаёт
   ненужный риск длинных циклов и побочных эффектов, а также усложняет проверку
   порядка. Для демонстрации достаточно конечного лимита в шесть вызовов.

## Подключённые серверы и демонстрационный запрос

Для сценария используются уже имеющиеся локальные серверы:

| MCP-сервер | Адрес | Роль в сценарии |
| --- | --- | --- |
| Public GitHub research | `http://127.0.0.1:8003/mcp` | Поиск репозиториев, создание обзора и сохранение файла |
| GitHub repositories | `http://127.0.0.1:8001/mcp` | Получение актуальных сведений о выбранном репозитории |
| GitHub scheduler | `http://127.0.0.1:8002/mcp` | Создание и проверка отложенного наблюдения |

В демонстрации пользователь отправляет в обычный чат запрос такого смысла:

> Найди Python MCP-серверы, выбери один репозиторий, получи его актуальные
> сведения, сохрани обзор и запланируй однократную проверку через неделю.

Однократное расписание создаётся только потому, что пользователь прямо попросил
его создать. Примерная задержка — 604800 секунд, `interval_seconds` — `null`.

## Ожидаемый маршрут

Агент самостоятельно выбирает инструменты и вызывает их последовательно:

1. `search(query, limit)` на Pipeline MCP находит не более трёх репозиториев.
2. `get_repository(owner, repo)` на GitHub MCP получает актуальные метаданные
   выбранного результата. `owner` и `repo` берутся из `full_name` результата
   поиска.
3. `summarize(search_result)` на Pipeline MCP формирует обзор по исходному
   `structuredContent` поиска.
4. `saveToFile(report)` на Pipeline MCP сохраняет ровно возвращённый
   `structuredContent` обзора.
5. `schedule_repository(owner, repo, delay_seconds=604800,
   interval_seconds=null)` на Scheduler MCP создаёт отложенную однократную
   проверку выбранного репозитория.
6. `get_schedule_summary(job_id)` на Scheduler MCP подтверждает сохранённое
   расписание по `job_id`, возвращённому предыдущим шагом. Пустая история проверок
   до фактического срока запуска является ожидаемым результатом.

Этот список описывает зависимость данных для теста и демонстрации, но не
исполняется отдельным pipeline runner. Решение о следующем вызове принимает
модель по результатам предыдущих вызовов. Сквозная проверка фиксирует ожидаемый
порядок и значения зависимых аргументов.

## Архитектура и границы изменений

- `McpRegistry` остаётся общим владельцем подключений. Подключённые серверы
  публикуют инструменты одним объединённым списком; имена инструментов
  уникализируются по существующей схеме реестра.
- `tool_runtime` продолжает отправлять модели список инструментов, разбирать
  выбранные вызовы, проверять аргументы по схеме из снимка каталога и вызывать
  `registry.call`. Реестр определяет URL MCP-сервера и исходное имя инструмента.
- Максимум за один пользовательский ход: **6 принятых модельных `tool_call`
  записей** и не более **6 раундов, в которых модель может выбрать инструменты**
  до обязательного финального ответа без инструментов. Запись расходует бюджет
  до разбора имени и аргументов, поэтому невалидные аргументы и неизвестный или
  отключённый инструмент также расходуют его. Если ответ модели содержит больше
  записей, чем осталось в бюджете, превышающие записи получают локальный отказ
  без вызова MCP-сервера. Лимиты задаются константами; автоматические повторы на
  уровне приложения не добавляются.
- Существующий `metadata.toolCalls` используется для трассы. Каждая запись
  должна сохранять имя модели-инструмента, исходное имя MCP-инструмента,
  URL сервера, аргументы, полный ограниченный ответ MCP, статус и длительность.
  Порядок списка совпадает с порядком реальных вызовов.
- Существующие пользовательские настройки MCP и вкладка подключения серверов
  используются без нового экрана. В README добавляются адреса и команды запуска
  трёх локальных серверов, порядок подключения и демонстрационный запрос.
- `/research` дня 19, схемы инструментов серверов и формат MCP не меняются.

## Передача данных и проверка вызовов

Для каждого выбранного моделью вызова приложение проверяет, что:

- имя инструмента присутствовало в снимке доступных инструментов для этого хода;
- аргументы являются JSON-объектом и соответствуют опубликованной JSON Schema;
- инструмент всё ещё разрешается в подключённый сервер при отправке;
- результат ограничен действующим размером ответа MCP; ошибки сохраняются как
  `isError` и возвращаются модели как результат инструмента.

Результаты предыдущих вызовов добавляются в контекст модели фактическими
ответами MCP. Код не подменяет данные текстовым пересказом и не конструирует
аргументы за модель. Финальный ответ может утверждать, что файл сохранён или
расписание создано, только если соответствующие вызовы вернули успешные
результаты с валидными структурированными данными. Для этого MCP-клиент сохраняет
опубликованный `outputSchema`, если сервер его предоставляет, а runtime проверяет
успешный `structuredContent` по этой схеме. Для целевых инструментов демонстрации
дополнительно проверяются следующие минимальные контракты, даже если сервер не
публикует `outputSchema`:

- `saveToFile`: `structuredContent` — объект с непустым строковым `path`,
  положительным целым `bytes_written` и `sha256` из 64 строчных hex-символов.
- `schedule_repository`: `structuredContent.job` содержит непустой `id`,
  совпадающие с выбранным репозиторием `owner` и `repo`, `status=active`,
  `interval_seconds=null` и корректный `next_run_at`.
- `get_schedule_summary`: `structuredContent.job.id` совпадает с ID из
  `schedule_repository`; owner/repo совпадают с выбранным репозиторием,
  `interval_seconds=null`, а до срока запуска `success_count` и `error_count`
  равны нулю.

Если `isError=true`, отсутствует обязательный `structuredContent` или нарушена
доступная схема/контракт, вызов считается ошибочным. Ошибка передаётся модели и
в трассу; она не может служить основанием для утверждения об успешном сохранении
или расписании.

## Ошибки и побочные эффекты

- Ошибка схемы, неизвестный инструмент, отключённый сервер или транспортная
  ошибка записываются как неуспешный вызов. Несуществующий инструмент не
  отправляется на сервер.
- После ошибки модель получает MCP-ошибку как результат вызова и решает,
  продолжить ли с доступной информацией или сообщить о проблеме. Приложение не
  повторяет запрос автоматически.
- Исчерпание лимита записей или раундов останавливает дальнейшие вызовы MCP и
  требует итогового ответа без инструментов. Записи сверх лимита в пачке
  получают локальный отказ без маршрутизации. Трасса принятых, отклонённых и
  выполненных записей сохраняется, поэтому она может содержать локальные отказы,
  но на сервер отправляется не более шести вызовов за ход.
- Если `schedule_repository` завершился ошибкой, не вызываются последующие
  инструменты расписания и нельзя сообщать об успешном создании задачи.
- Если ответ `schedule_repository` потерян из-за тайм-аута, итог побочного
  эффекта может быть неизвестен. Автоматически не повторять этот
  неидемпотентный вызов; предложить проверить расписание через `list_schedules`.
- Обычный текстовый запрос без необходимости MCP продолжает обрабатываться без
  вызовов инструментов.

## Проверки

Автоматические проверки должны использовать настоящий MCP-клиентский протокол
и локальные MCP-серверы с контролируемыми ответами; ответы модели и внешнего
GitHub API могут быть подставными. Они проверяют:

1. Подключение двух или более серверов и появление их инструментов в одном
   снимке каталога с однозначным разрешением имени в сервер и исходный tool.
2. Успешный многошаговый прогон по всем трём серверам; фактические вызовы имеют
   ожидаемый порядок и сервер-владелец.
3. `owner/repo` для GitHub и Scheduler происходят из выбранного `full_name`;
   `search_result` и `report` в последующих вызовах соответствуют валидированным
   `structuredContent` предыдущих шагов; `job_id` для проверки получен из
   `schedule_repository`.
4. Трасса `metadata.toolCalls` сохраняет порядок, аргументы, ответы, статусы и
   длительность. Финальное сообщение и обычный путь без MCP остаются совместимы.
5. Невалидные аргументы, неизвестный инструмент, отключение сервера между
   discovery и call, `isError`, тайм-аут и исчерпание лимита не дают ложного
   успеха и не запускают последующие зависимые вызовы автоматически. Каждая
   модельная `tool_call` запись расходует бюджет и при локальной ошибке; запись
   сверх остатка не вызывает MCP.
6. После частичного успеха повтор запроса не создаётся приложением самопроизвольно;
   тесты явно подтверждают, что неидемпотентный `schedule_repository` не повторён.

Отдельно выполняется живая демонстрация в чате с запущенными серверами 8001,
8002 и 8003. Сохраняются фактическая трасса вызовов, итоговый текст, имена
серверов и время выполнения в `docs/day-20/live-results.json`, а инструкция и
анализ результата — в `docs/day-20/orchestration-results.md`. В живом отчёте
нельзя подменять результаты реальных вызовов фиктивными.

## Критерии приёмки

- Одновременно зарегистрированы и подключены не менее двух MCP-серверов; для
  основной демонстрации используются все три локальных сервера.
- Запрос в обычном чате вызывает инструменты из разных серверов, а не фиксированный
  исполнитель дня 19.
- Каждый реальный вызов маршрутизируется к серверу-владельцу, а зависимые данные
  получаются из результатов предыдущих MCP-вызовов.
- Трасса показывает выбор, порядок, аргументы, фактические результаты и ошибки.
- Многошаговый сценарий укладывается в конечный лимит; превышение лимита не
  создаёт ложный успешный результат.
- Существующий `/research`, обычный чат и настройки MCP проходят регрессионную
  проверку.
- В документации есть команды запуска и подключения серверов и сохранён итог
  фактической живой демонстрации.

## Не входит в объём

- Новый визуальный конструктор workflow или отдельный экран оркестрации.
- Выполнение произвольных графов, параллельных веток или неограниченных циклов.
- Автоматические повторы, универсальные политики компенсации и подтверждение
  каждого инструмента пользователем.
- Изменение инструментов GitHub, Pipeline и Scheduler либо перенос `/research`
  на модельный оркестратор.
- Обязательное подключение DeepWiki или внешнего MCP-сервера: три локальных
  сервера достаточны для повторяемого сценария.
