# День 30 — приватный LLM-сервис на VPS

Статус: выполнен пробный запуск SmolLM2 135M на Hostkey vm.v2-pico: 1 vCore, 1 ГБ RAM, 40 ГБ NVMe, Debian 13.4 x86_64. Десять последовательных и три одновременных запроса получили HTTP 200; после последней серии доступно 275 МиБ RAM. Проверен доступ с Mac через SSH-туннель; пользователь подтвердил ответ Alice в диалоге с историей. [Фактические результаты и ограничения проверки](../../day-30/preflight.md). API-обёртка, веб-чат и rate limit не реализованы; превышение контекста не проверено. Ниже описана целевая архитектура дальнейшей реализации, а не уже развёрнутый стек. Пользователь получил инструкции остановки; текущее состояние VPS не подтверждено.

## 1. Что требуется в задании

Нужно превратить локальную модель в доступный по сети сервис: независимый процесс на сервере, HTTP API, чат, ограничение нагрузки и воспроизводимая проверка работы. Обучать новую модель, переносить RAG или создавать аналог ChatGPT не требуется.

«Локальная LLM» означает, что вычисления выполняются на управляемой нами машине. На VPS это удалённый сервер, а не ноутбук пользователя. «Приватный» означает доступ только владельцу и отсутствие отправки переписки провайдеру LLM. При этом инфраструктуре владельца VPS приходится доверять: это не физически собственный компьютер.

## 2. VPS простыми словами

VPS — виртуальный компьютер в дата-центре. Провайдер выделяет ему процессорные ресурсы, RAM и диск. Мы выбираем Linux, получаем IP-адрес и подключаемся по SSH — защищённому удалённому терминалу. Установка программ происходит на сервере. Ноутбук служит пультом управления и клиентом чата.

- **vCPU** выполняют вычисления; на недорогом тарифе физические ядра могут делиться с соседями.
- **RAM** нужна для модели, её контекста и приложения. Размер файла модели не равен полной памяти процесса.
- **Диск** хранит ОС, зависимости и веса модели.
- **IP-адрес** указывает на сервер, **порт** — на конкретную программу на нём.
- **127.0.0.1 / localhost** всегда обозначает ту машину, на которой используется адрес.
- **systemd** запускает сервисы при загрузке Linux и перезапускает завершившийся процесс.
- **SSH-туннель** переносит HTTP-запросы с локального порта ноутбука на закрытый порт сервера через зашифрованное соединение.

Закрытие SSH-терминала не остановит правильно установленный серверный сервис. Закрытие туннеля прервёт доступ с ноутбука; его можно открыть заново. Остановка VPS не обязательно прекращает начисление платы: правила тарифа и удаления дисков нужно проверить до аренды.

## 3. Варианты и выбранная архитектура

| Вариант | Когда подходит | Дополнительная работа |
|---|---|---|
| **VPS + SSH-туннель — рекомендован для дня 30** | Один владелец, браузер и API на ноутбуке | Запускать туннель перед использованием |
| VPS + Tailscale | Нужен удобный доступ с нескольких устройств | Учётная запись, установка клиентов, правила частной сети |
| VPS + публичный HTTPS | Нужна обычная ссылка без туннеля | Домен, TLS, reverse proxy и защита публичной точки входа |

Первый вариант выполняет требование сетевого HTTP API: запрос физически идёт с ноутбука на VPS; SSH защищает транспорт. Если организатор требует именно публичный URL, выбрать третий вариант и отдельно уточнить сетевую часть плана. Из приведённого задания публичность не следует.

```text
Ноутбук: браузер или curl → 127.0.0.1:8080
                          ↓ SSH через интернет
VPS: SSH :22 → API 127.0.0.1:8000 → Ollama 127.0.0.1:11434 → SmolLM2 135M
```

Целевая машина — существующий Hostkey vm.v2-pico, 1 vCore / 1 ГБ RAM / 40 ГБ NVMe. Установлена Debian 13.4 x86_64; переустановка ОС не требуется. На ноутбуке результаты дня 29 не доказывают пригодность VPS.

### Первый этап: проверка на 1 ГБ

Точный тег `smollm2:135m` в каталоге Ollama сейчас содержит F16-веса размером около 271 МБ. Это размер файла, не полной RAM при работе. Зафиксировать фактический digest/формат после загрузки. Модель преимущественно англоязычная; технические сценарии выполнять на простых английских запросах, русский проверить отдельно без обещания качества Qwen.

1. Через консоль Hostkey определить ОС, архитектуру, RAM, доступную память, swap и место на диске. Настроить SSH по ключу на Mac после первого входа.
2. Установить только Ollama нативно, без Docker, Open WebUI, PyTorch и RAG. Слушать только loopback; установить local-only mode, одну модель, одну генерацию и один CPU-поток.
3. Скачать `smollm2:135m`; сначала через локальный `/api/chat` проверить короткий ответ с `num_ctx=1024`, `num_predict=128`, `num_thread=1`, `temperature=0`, `stream=false`. Этот прямой API нужен только для проверки, наружу его не открывать.
4. Провести 10 последовательных запросов и простой диалог; измерить пиковую RAM всех процессов Ollama и минимальную MemAvailable системы, проверить kernel OOM и swap-in/out. Продолжать, если все запросы завершаются за 120 секунд, нет OOM/перезапусков/устойчивого активного swapping и остаётся хотя бы 150 МиБ MemAvailable для будущего API. Это стартовый критерий с последующей проверкой всего стека, а не гарантия достаточности.
5. Если критерий не выполнен, остановить эксперимент и сохранить причину; обсудить меньший контекст/квантованный вариант или увеличение RAM. Не маскировать нехватку RAM автоматическим созданием swap и не менять тариф без решения пользователя.

Полный API и чат разворачивать только после этой проверки. После добавления API повторить измерение под нагрузкой; итоговая приёмка также требует отсутствия OOM и устойчивого активного swapping.

## 5. Функциональный контракт

Один владелец, один настроенный API-ключ, одна фиксированная модель. Python, FastAPI, Uvicorn с **одним worker**, httpx и локальный токенизатор SmolLM2. Redis, база данных и контейнеризация для MVP не нужны.

| Маршрут | Поведение |
|---|---|
| `GET /` | Страница чата, не содержит ключ или переписку |
| `GET /health/live` | Процесс HTTP работает; без подробностей и авторизации |
| `GET /health/ready` | С ключом: доступна Ollama, присутствует модель, конфигурация и токенизатор проверены; иначе 503 |
| `POST /api/chat` | С ключом: сообщения → ответ модели; JSON без streaming |

Авторизация: `Authorization: Bearer <ключ>`. Ключ создаётся на сервере, не коммитится, не передаётся в URL и не записывается в логи. Приложение отказывается стартовать без ключа. Ключ хранится в закрытом файле окружения; пользователь вводит его на странице, где он остаётся только в памяти вкладки. Переписка также живёт только в памяти вкладки и очищается после перезагрузки. Сервер не хранит сессии; клиент передаёт историю в каждом запросе.

Запрос:

```json
{"messages":[{"role":"user","content":"Объясни, что такое VPS"}],"max_tokens":128}
```

История содержит только чередующиеся `user`/`assistant`, начинается и заканчивается `user`; максимум 20 сообщений, непустой текст. Системную инструкцию добавляет сервер. Неизвестные поля запрещены, включая `model`, `base_url`, инструменты и параметры контекста. Клиент не может сменить модель или провайдера. `max_tokens` — целое от 1 до 128, по умолчанию 128.

Успешный ответ содержит `request_id`, `message` с ролью assistant, `model`, фактические `prompt_tokens`, `completion_tokens`, `finish_reason`, `duration_ms`. Незаполненные счётчики не заменять нулём. Если Ollama не дала обязательные данные протокола, это ошибка upstream. При достижении лимита ответа вернуть `finish_reason=length` и показать в UI, что ответ обрезан. Автоматических повторов нет.

UI: поле ключа, история, ввод сообщения, отправка и «Новый чат», индикатор ожидания, понятные ошибки. Неудачный ход не добавляется в подтверждённую историю. Пока запрос выполняется, повторная отправка и сброс чата заблокированы. Ответы отображаются как текст, без исполнения HTML. Никаких внешних CDN или аналитики.

## 6. Лимиты и устойчивость

Предлагаемые стартовые значения подлежат проверке на выбранном VPS:

| Ограничение | Значение / действие |
|---|---|
| Частота | 10 валидных попыток генерации за скользящие 60 секунд на API-ключ; 11-я — 429 `rate_limited`, `Retry-After` |
| Выполнение | Одна генерация одновременно |
| Очередь | Максимум два ожидающих запроса; следующий — 503 `busy`, `Retry-After: 5` |
| Ожидание очереди | Не более 120 секунд, затем 503 `queue_timeout` |
| Генерация | Общий deadline 120 секунд после начала, затем 504 `generation_timeout` |
| Тело запроса | 32 КиБ до полного чтения/разбора, включая chunked-запросы; иначе 413 |
| Окно модели | 1024 токенов, явно настроено и проверено |
| Ответ | До 128 токенов |
| Вход | `input_tokens + max_tokens + 32 <= 1024`; превышение — 422 `context_limit` без вызова модели |

Порядок обработки: ограничение тела и авторизация → JSON/schema → проверка контекста → атомарный rate limit → атомарный admission в очередь. Попытки, дошедшие до rate limit, учитываются и при заполненной очереди. Проверки частоты и параллельности независимы: редкие длинные запросы тоже способны перегрузить модель. Все лимиты находятся в одном процессе; увеличение числа workers без общего хранилища запрещено. После рестарта история rate limit теряется — допустимое ограничение учебного MVP.

Для точного подсчёта: скачать и зафиксировать ревизию и SHA256 `tokenizer.json` официальной HuggingFaceTB/SmolLM2-135M-Instruct, хранить локально. Отрисовывать текстовый ChatML prompt с фиксированной системной инструкцией и маркерами SmolLM2 в одном модуле; посчитать его токены и отправить **тот же текст** в Ollama `/api/generate` с `raw=true`, `stream=false`, `num_ctx=1024`, `num_predict=max_tokens`, температурой 0, `num_thread=1` и stop-маркерами модели. Нативный generate здесь обслуживает чат, потому что в prompt включена вся история. Это исключает расхождение между шаблоном подсчёта и скрытым шаблоном `/api/chat`.

Отключить добавление лишних special tokens в токенизаторе, запретить служебные маркеры SmolLM2 во входном тексте. Перед доступом проверить совместимость токенизации и фактического `prompt_eval_count` на русском, английском, emoji и многоходовой истории. Не списывать расхождение на резерв 32: при несовместимости настройка не принимается. Резерв оставлен для пограничных особенностей runtime. Длинная история явно отклоняется, а не незаметно обрезается.

Разрыв связи с браузером не освобождает слот уже запущенной генерации: её фоновой задачей владеет сервер до завершения. Ожидающий отменённый запрос удаляется из очереди. При неопределённом завершении upstream после deadline сервис переходит в degraded: новые генерации получают 503; runbook предусматривает перезапуск Ollama и API и повторный readiness-check. Нельзя накапливать скрытые фоновые генерации за счёт освобождения семафора при отмене HTTP-запроса. При рестарте приложения во время активной генерации также использовать совместный перезапуск двух сервисов.

Ошибки имеют единый JSON `error.code`, `error.message`, `request_id`: 401 неверный ключ; 400 некорректный JSON; 422 схема/контекст; 413 тело; 429 частота; 503 недоступность/очередь; 504 deadline; 502 некорректный/пустой ответ Ollama. Пользователю не выдаются traceback и секреты.

## 7. Развёртывание и приватность

- API слушает только `127.0.0.1:8000`, Ollama — `127.0.0.1:11434`; с интернета доступен только SSH. Учесть IPv4 и IPv6 в firewall. К модели нет прямого туннеля.
- SSH по ключу, отдельный пользователь для входа, отдельная учётная запись процесса API без административных прав. Перед отключением старого способа входа проверить новый во второй сессии и доступ к консоли провайдера.
- Копировать только необходимые исходники/статику; не переносить `.env`, старые переписки, RAG-индекс и ключи облачных провайдеров.
- Ollama запускается с `OLLAMA_NO_CLOUD=1`, `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_MAX_LOADED_MODELS=1`, малой защитной очередью `OLLAMA_MAX_QUEUE=2`. Очередью пользователей управляет API.
- Для дня 30 создать отдельный alias `smollm2-day30-ctx1024` на `smollm2:135m`. Фиксировать версию Ollama, digest весов, версию Python и зависимости.
- API и Ollama управляются systemd; API имеет `Restart=on-failure`, настройки окружения вне репозитория и ограничение времени остановки. Ollama выделена только этому сервису. Перед каждым запуском процесса API (включая автоматический restart после аварии) systemd выполняет привилегированный `ExecStartPre=+/usr/bin/systemctl restart ollama.service` и ждёт его завершения; после этого API проводит readiness/warmup. При ошибке подготовительного шага API не запускается. Путь systemctl проверить на VPS. Сам процесс API остаётся непривилегированным; права перезапуска ему не выдаются. У Ollama не должно быть обратной зависимости от API. После перезагрузки VPS сервисы стартуют автоматически.
- Логи содержат только request ID, статус, длительность, размер очереди, счётчики токенов и вид ошибки. Тексты сообщений и Authorization не логируются.
- Модель и токенизатор скачиваются во время подготовки. Инференс не требует внешнего AI API. Отдельный тест блокирует исходящий интернет на VPS при сохранении существующего SSH и проверяет генерацию; правила снимаются после проверки.

Пример будущего подключения с ноутбука (`USER` и `VPS_IP` заменяются реальными значениями):

```bash
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 \
  -L 127.0.0.1:8080:127.0.0.1:8000 USER@VPS_IP
```

После этого открыть `http://127.0.0.1:8080`. Локальный адрес здесь — вход в туннель; вычисления выполняются на VPS. Соединение по интернету шифруется SSH, хотя адрес браузера начинается с HTTP.

## 8. Приёмка и доказательства

1. С ноутбука через туннель получить HTTP-ответ и провести двухходовой диалог; зафиксировать запрос и соответствующий request ID в журнале VPS. Закрыть туннель: адрес становится недоступен. Публичные порты 8000/11434 закрыты.
2. Без ключа и с неверным ключом получить 401; не должно быть вызова Ollama. Проверить запрет внешней модели, смены URL, лишних полей и межсайтовых запросов.
3. Прогреть модель. Выполнить 20 коротких последовательных запросов с интервалом 7 секунд: 20 корректных ответов, без перезапусков и OOM. Записать latency p50/p95/max и пиковую RAM; целевой скорости до замера не обещать.
4. Выполнить 3 одновременных коротких запроса: все приняты, одна генерация и до двух ожиданий, все успешны в пределах deadline. Выполнить 5 одновременных: при удерживаемом активном слоте три приняты, два получают 503 busy. Детерминированно проверить это с задержанным fake upstream; на реальной модели фиксировать фактическое распределение, поскольку она может успеть освободить слот.
5. Отдельно проверить 11 валидных запросов в 60 секунд: один 429 с Retry-After; очередь не должна маскировать проверку. В unit-тесте использовать управляемые часы и быстрый upstream; в live-тесте записывать также 503 и учтённые попытки. После выхода из окна запрос принимается.
6. Проверить контекст ровно на допустимой границе и на один токен выше; на превышении нет вызова Ollama. Проверить 32 КиБ и превышение, Unicode и лимит ответа с `finish_reason=length`.
7. Проверить недоступную Ollama, пустой upstream, timeout, отмену клиента и отсутствие утечки слотов. Аварийно завершить API при активной генерации: перед автоматическим запуском нового API Ollama перезапускается, старая генерация завершается, новая не накладывается на неё. После восстановления сервис отвечает. Перезапустить VPS и повторить чат через новый туннель.
8. Проверить локальный инференс при закрытом исходящем интернете и отсутствие переписки/ключа в логах. Ограничение egress не должно блокировать ответы действующей SSH-сессии; иметь консоль провайдера и автоматический откат временного правила.

Результаты сохранить в `docs/day-30/results.json` и `docs/day-30/results.md`: конфигурация VPS, версии, модель/digest, дата, команды, ожидаемое/фактическое, статусы, задержки, память, рестарты, ограничения. Использовать синтетические сообщения. Пустые шаблоны и fake-тесты не выдавать за результат развёртывания.

## 9. За пределами MVP

RAG, MCP, облачные модели, обучение, несколько пользователей, постоянная история, streaming, публичный домен, GPU и горизонтальное масштабирование. Добавлять их только по отдельной потребности. Проверка устойчивости нескольких клиентов не означает обязательную параллельную генерацию: ограниченная очередь — допустимое решение для небольшого CPU-сервера.
