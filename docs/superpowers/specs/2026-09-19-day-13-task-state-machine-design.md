# День 13 — конечный автомат состояния задачи: дизайн

## Цель

Добавить в локальный чат формализованное и сохраняемое состояние одной задачи
на агента. Агент должен собирать требования в диалоге, создавать и показывать
пользователю Markdown-план, выполнять утверждённый план, самостоятельно
переходить к проверке и завершению, а после паузы продолжать с того же места.

## Границы

Работа расширяет `deepseek-api`: Python-сервер, JSON-снимок агента, хранилище
Markdown-планов и существующее поле ввода сообщений. Управление выполняется
только slash-командами; новая панель или кнопки не добавляются. Существующие
команды памяти и профили сохраняют прежнее поведение.

Включены состояния `PLANNING`, `EXECUTION`, `VALIDATION`, `DONE`, пауза,
сохранение плана и инъекция состояния в промпт. Не включены несколько
параллельных задач на одного агента, внешняя БД, автоматическое назначение
задач или изменение интерфейса управления.

## Модель данных и инварианты

В `context` агента добавляется `taskState`. Он равен `null`, пока задача не
создана, либо имеет вид:

```json
{
  "id": "task-1",
  "title": "Подготовить лендинг",
  "stage": "PLANNING",
  "paused": false,
  "step": 0,
  "total": 0,
  "plan": [],
  "done": [],
  "current": "Собрать требования",
  "expectedAction": "Продолжайте отвечать на вопросы агента.",
  "planPath": null
}
```

После создания плана `plan` содержит его упорядоченные шаги, `total` равен
длине списка, `step` — порядковый номер текущего шага (с единицы), `current`
— текст этого шага, а `planPath` указывает на Markdown-файл. `done` содержит
только уже завершённые шаги. Обновление `plan` в `PLANNING` не стирает `done`.

Разрешённые переходы строго ограничены:

| Откуда | Событие | Куда |
|---|---|---|
| нет задачи или `DONE` | `/task Название` | `PLANNING` |
| `PLANNING` с готовым планом | `/execute` | `EXECUTION` |
| `EXECUTION` | `/planning` | `PLANNING` |
| `EXECUTION` | служебная метка модели | `VALIDATION` |
| `VALIDATION` | служебная метка модели | `DONE` |

`/pause` разрешена в трёх незавершённых состояниях и изменяет только
`paused`. `/resume` снимает её без смены этапа, шага или ожидаемого действия.
Пока `paused` равно `true`, обычные сообщения и все переходы отклоняются;
исключение — `/status` и `/resume`. Из `DONE` переходов нет, кроме создания
новой задачи командой `/task`.

## Команды и разговорный сценарий

| Команда | Результат |
|---|---|
| `/task Название` | Создаёт новую задачу в `PLANNING`; команда не уходит модели и не попадает в историю. |
| `/execute` | Переводит план с сохранённым Markdown-файлом из `PLANNING` в `EXECUTION`. Без плана возвращает ошибку. |
| `/planning` | Возвращает задачу из `EXECUTION` в `PLANNING` для уточнений, не теряя завершённые шаги. |
| `/pause` | Ставит активную задачу на паузу. |
| `/resume` | Возобновляет ровно сохранённый этап и шаг. |
| `/status` | Показывает этап, прогресс, текущий шаг, завершённые шаги и ожидаемое действие. |

Обычные сообщения в `PLANNING` используются для опроса и уточнения
требований. Когда информации достаточно, модель возвращает видимый
Markdown-план в выделенном служебном контейнере. Сервер извлекает Markdown,
валидационно получает упорядоченные шаги, сохраняет план в
`deepseek-api/data/task-plans/{agent-id}-{task-id}.md`, выводит сам план
пользователю и обновляет `taskState`, не переходя из `PLANNING`. Только после
того как пользователь прочитал план, он может выполнить `/execute`.

В `EXECUTION` и `VALIDATION` модель получает инструкцию добавлять служебную
метку только после завершения этапа. Сервер допускает лишь таблицу переходов,
удаляет метку из видимого текста и добавляет сообщение вида «Завершён этап
EXECUTION. Начат этап VALIDATION». Любая неизвестная или преждевременная метка
игнорируется; модель не может перепрыгнуть этапы.

## Промпт и файловое хранение

Обычный вызов модели получает системный блок состояния после базовой
инструкции и профиля, но перед памятью и историей. Он содержит:

```text
[TASK_STATE]
Задача: ...
Этап: PLANNING
Прогресс: step/total
Текущий шаг: ...
Выполнено: ...
Ожидаемое действие: ...
План: ...
```

Инструкции блока запрещают модели пропускать этапы, требуют в `PLANNING`
вести опрос и подготовить Markdown-план, а в рабочих этапах работать только
над `current`. Пауза не вызывает модель.

Весь `taskState` сохраняется в существующем `agents.json` через прежнее
атомарное сохранение registry. Markdown-файл хранит читаемую версию плана;
состояние содержит относительный путь и шаги, достаточные для продолжения
даже без повторных объяснений. При загрузке старого JSON миграция добавляет
`taskState: null`; испорченные новые данные не должны делать реестр
невалидным.

## Ошибки и защита границ

Парсер новых slash-команд расширяет существующий локальный парсер команд и
возвращает ясные русские ошибки для пустого названия, неизвестного состояния,
отсутствующего плана, недопустимого перехода и повторной паузы/возобновления.
Команды не вызывают провайдера. Запись Markdown-плана выполняется до фиксации
состояния; при ошибке записи задача остаётся в прежнем согласованном
состоянии. Плановые служебные контейнеры и метки перехода не должны попадать
в сохраняемую переписку в сыром виде.

## Проверка

Автотесты покроют:

- парсинг всех команд и точные запрещённые переходы;
- создание задачи, генерацию Markdown-плана, обновление плановых шагов и
  переход `/execute`;
- возврат `/planning` с сохранением завершённых шагов;
- автоматические `EXECUTION → VALIDATION → DONE` без пропуска стадий и с
  видимыми сообщениями о переходе;
- `/pause` на `PLANNING`, `EXECUTION` и `VALIDATION`, а также `/resume` без
  сброса текущего шага;
- `/status`, сохранение/загрузку registry и миграцию старого state;
- порядок инъекции состояния в промпт и продолжение после перезапуска без
  повторной постановки задачи.

## Критерии готовности

- Пользователь видит и подтверждает Markdown-план до запуска выполнения.
- Состояние задачи, шаг, ожидаемое действие и пауза — явные сохраняемые
  данные, а не вывод из истории чата.
- Агент не выполняет недопустимые переходы и не возобновляет задачу с начала.
- При автоматическом переходе пользователь видит завершённый и новый этап.
- Все перечисленные сценарии имеют проверяемые автоматические тесты.
