# День 17 — свой GitHub MCP-сервер: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Агент из нашего чата самостоятельно вызывает `get_repository` на собственном MCP-сервере и использует полученные сведения GitHub в ответе пользователю.

**Architecture:** Отдельный Python-процесс публикует один инструмент через Streamable HTTP на `http://127.0.0.1:8001/mcp`. На вкладке MCP пользователь подключает его по URL через общий механизм подключения серверов. Backend хранит общий для всех агентов каталог подключённых MCP, передаёт их инструменты модели, исполняет возвращённый `tool_call` через нужный сервер и передаёт результат модели для итогового ответа.

**Tech Stack:** Существующие Python-приложение и OpenAI-совместимый клиент DeepSeek, MCP Python SDK `>=1.30,<2` / FastMCP, httpx, unittest, существующий HTML/JS-интерфейс.

**Статус:** Реализовано и проверено 26 сентября 2026; результаты — `docs/day-17/github-mcp-results.md`. Рабочая ветка на момент исследования — `day-17`. Все пути ниже относительно корня репозитория.

## 1. Что именно делаем

Демонстрационный запрос:

> «Через GitHub узнай, что за проект modelcontextprotocol/python-sdk: дай описание, основной язык, число звёзд и ссылку».

Пользователь пишет обычное сообщение. Модель выбирает инструмент и параметры; приложение выполняет сетевой вызов. В ответе пользователь получает краткую справку, основанную на результате GitHub. В метаданных можно проверить инструмент, аргументы, JSON результата и последующий запрос модели.

Для первого дня достаточно одного инструмента чтения. Создание issues/PR, поиск по GitHub, OAuth, приватные репозитории и публикация MCP-сервера в интернете не входят в первую версию. Для публичного репозитория GitHub допускает запрос без токена; необязательный `GITHUB_TOKEN` хранится только в окружении MCP-процесса.

### Варианты и выбор

1. **Свой FastMCP-сервер + Streamable HTTP — выбран.** Продолжает транспорт Дня 16, позволяет отдельно показать регистрацию и настоящий вызов MCP. Запускаются два локальных процесса.
2. Свой сервер через stdio. Тоже выполняет задание, но потребует нового транспорта и управления дочерним процессом; это лишняя работа для текущего приложения.
3. Готовый GitHub MCP-сервер. Подойдёт для дальнейших экспериментов, но не демонстрирует реализацию собственного сервера вокруг API, требуемую заданием.

### Что уже есть в коде

- `deepseek-api/mcp_client.py`: `initialize()` и `list_tools()` для фиксированного DeepWiki; из ответа сохраняются только имя и описание.
- `deepseek-api/web.py`: `POST /api/mcp/tools` принимает пустой запрос и получает список DeepWiki.
- `deepseek-api/providers.py`: `ask_model()` возвращает только `content` и `usage`; отсутствие текста считается ошибкой.
- `deepseek-api/agent.py`: `Agent.respond()` выполняет один основной вызов модели; история хранит текстовые сообщения. Метрики и проверки сохранённых данных требуют явного расширения.
- `deepseek-api/static/mcp-controls.js`: карточки инструментов, подключение по кнопке.
- README описывает произвольный публичный URL, но текущий код и тесты его не реализуют. Документ `2026-09-22-public-mcp-url-design.md` — отдельный проект изменения, а не выполненная зависимость этого плана.

## 2. Контракт инструмента

Имя: `get_repository`.

Описание: «Получить текущие сведения о публичном GitHub-репозитории по владельцу и имени: описание, основной язык, звёзды, форки, основную ветку и ссылку. Используй для вопросов о конкретном репозитории».

```json
{
  "type": "object",
  "properties": {
    "owner": {"type": "string", "description": "Владелец или организация, например modelcontextprotocol"},
    "repo": {"type": "string", "description": "Имя репозитория без владельца, например python-sdk"}
  },
  "required": ["owner", "repo"],
  "additionalProperties": false
}
```

Сервер валидирует строки: непустые, без `/`, `\\`, управляющих символов, сегментов `.`/`..`; URL строит только на `https://api.github.com`. Запрос: `GET /repos/{owner}/{repo}`. Регистрация через `@mcp.tool()`, описания аргументов через типизированные поля; схема из `list_tools()` является источником схемы для модели, не копируется вручную в frontend.

Успешный структурированный результат содержит `full_name`, `description`, `language`, `stargazers_count`, `forks_count`, `default_branch`, `html_url`, `archived`, `pushed_at`, `fetched_at`. Допускаются `null` для необязательных полей GitHub. `fetched_at` — время получения в UTC. Поле `open_issues_count` пока не выводим, чтобы не смешивать issues и pull requests.

MCP-ошибки инструмента возвращаются с `isError=true` и безопасным текстом: неверные параметры, репозиторий не найден/недоступен, неверный токен, исчерпан лимит, тайм-аут, недоступность GitHub. Ошибки транспорта обрабатывает клиент. Модель получает ошибку как результат инструмента и объясняет её без выдуманных данных.

## 3. Поток выполнения и границы

```text
Сообщение пользователя
  → Agent.respond()
  → общий каталог подключённых MCP → схема get_repository
  → DeepSeek: сообщения + tools
  ← assistant.tool_calls: get_repository(owner, repo)
  → MCP initialize + tools/call
  → наш сервер → GitHub REST API
  ← структурированный результат
  → DeepSeek: исходные сообщения + assistant.tool_calls + role=tool
  ← итоговый текст → чат
```

- В собственном сервере MVP реализуем только `get_repository`. Подключение и маршрутизация инструментов общие: собственный сервер и DeepWiki подключаются одинаково, их объявленные инструменты становятся доступны всем существующим и новым агентам. Отдельного включения MCP в настройках агента нет.
- На вкладке MCP вводится URL сервера; для удобства есть примеры DeepWiki и нашего `http://127.0.0.1:8001/mcp`. Разрешены публичные HTTPS endpoints и точный локальный адрес нашего сервера. Последний — явное исключение из прежнего дизайна публичных URL. Другие HTTP/локальные адреса, URL с учётными данными и автоматические редиректы не поддерживаются в MVP.
- «Подключить» выполняет initialize/list_tools и после успеха атомарно добавляет сервер и схемы инструментов в общий каталог backend. Повторное подключение обновляет запись без дубликатов. «Отключить» удаляет его инструменты из доступных всем агентам. Состояние не зависит от активного агента или открытой вкладки браузера.
- Настройки серверов (`id`, название, URL) сохраняются отдельно от агентов в `data/mcp_servers.json`. После перезапуска показываем сохранённые серверы как отключённые; пользователь подключает их заново, чтобы получить актуальные схемы. Сетевые MCP-сессии открываются на время операции и закрываются; статус «подключён» означает включение в общий каталог, а не постоянный открытый сокет.
- У одинаковых имён инструментов разных серверов должны быть уникальные короткие имена для модели и явная таблица соответствия `model_tool_name → server_id + original_tool_name`. Перед каждым ходом агент получает снимок общего каталога; перед каждым фактическим вызовом runtime повторно проверяет, что сервер подключён. Отключение запрещает новые вызовы, уже выполняющийся может закончиться.
- Первая поддерживаемая конфигурация вызова инструментов: DeepSeek из существующего списка моделей, текстовый ответ; при непустом общем каталоге задаём `thinking: disabled` во всех основных запросах этого хода. Для GLM и JSON-режима явно показываем, что выбранная конфигурация пока не использует MCP; обычный чат продолжает работать без tools. Подключение остаётся глобальным, модель/формат агента молча не меняются. Это ограничение адаптера модели, а не индивидуальная настройка доступа к серверам.
- До двух раундов вызова инструментов и до трёх фактических MCP-вызовов на ход. Если ответ содержит несколько вызовов, каждому `tool_call_id` соответствует ровно один результат, в том числе ошибка лимита. После исчерпания бюджета финальный запрос с `tool_choice=none`; повторные tool calls после него считаются ошибкой протокола.
- Общий тайм-аут каждой MCP-операции — 15 секунд, HTTP-запроса GitHub — 10 секунд. Ограничить результат инструмента 16 KiB; превышение — явная ошибка, без повреждённого обрезанного JSON. Проверять бюджет контекста до каждого обращения к модели.
- В постоянной истории остаются сообщение пользователя и финальный ответ. Полная служебная последовательность хранится в метаданных последнего хода; контекстные стратегии не разрывают пары tool call/result. Отсутствие сырых результатов в следующем ходе — осознанная граница MVP.
- Содержимое и описания MCP — внешние данные: не использовать как системные инструкции. Не передавать инструменты вспомогательным вызовам сводки/извлечения памяти. Инварианты и переходы задачи применять к итоговому ответу, не к промежуточным tool calls.
