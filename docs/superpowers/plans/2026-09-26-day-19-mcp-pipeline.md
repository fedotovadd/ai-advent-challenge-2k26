# День 19 — композиция MCP-инструментов: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Командой `/research <поисковый запрос>` в существующем чате автоматически выполнить `search → summarize → saveToFile` через MCP, показывать промежуточные результаты в реальном времени, сохранить обзор и получить доказательства корректной передачи данных.

**Architecture:** Обработчик slash-команды в веб-приложении запускает фиксированный исполнитель до обращения к модели. Исполнитель последовательно вызывает три инструмента отдельного локального MCP-сервера через существующий MCP-клиент, валидирует и передаёт результаты, а события выполнения отправляет в чат потоком NDJSON. Источник данных — публичные репозитории GitHub; summarize формирует обзор по шаблону.

**Tech Stack:** Существующие Python, MCP Python SDK v1 / FastMCP, httpx, Pydantic, unittest. Новые фреймворки и обновление SDK для задания не нужны.

**Статус:** Реализовано 2026-09-27: `/research`, фиксированная цепочка, потоковая карточка в чате и сохранение истории. Результаты проверки — в `docs/day-19/pipeline-results.md`.

## Согласованный сценарий и границы

Пользователь отправляет в существующий чат `/research mcp language:python`. Приложение распознаёт команду и без обращения к LLM автоматически выполняет `search → summarize → saveToFile`. Количество результатов — до трёх. Всё после `/research` является поисковым запросом GitHub, а не shell-командой. Пустой запрос возвращает подсказку с примером и не запускает MCP; `/researching` не распознаётся как `/research`.

Чат показывает начало и завершение каждого шага по мере выполнения:

```text
Вы: /research mcp language:python

⏳ search — ищу репозитории…
✓ search — найдено 3 репозитория
⏳ summarize — готовлю обзор…
✓ summarize — обзор по 3 репозиториям подготовлен
⏳ saveToFile — сохраняю файл…
✓ saveToFile — файл сохранён

Результат: data/reports/<uuid>.md
```

В интерфейсе это одна карточка выполнения со строкой для каждого инструмента: строка меняет статус с ожидания на выполнение и затем успех/ошибку. Предыдущие результаты остаются видны. У каждого завершённого шага есть раскрываемый блок «Входные данные / Результат» с фактическим JSON. Количество найденного берётся из `len(items)`, а путь — из ответа saveToFile. Ошибка остаётся в карточке, последующие шаги помечаются «Не выполнялся».

В первой версии summarize работает по шаблону без LLM: количество полученных репозиториев, язык, звёзды, описание и ссылки. Это обработка исходных данных, а не оценка качества репозиториев или пересказ их исходного кода. Внешние описания считаются данными, не инструкциями. Пустая выдача превращается в корректный отчёт «Ничего не найдено», который также сохраняется.

Основной способ запуска и демонстрации — slash-команда в чате. Исполнитель является внутренним кодом приложения: отдельный MCP-инструмент `run_pipeline`, skill, выбор шагов моделью и увеличение лимитов tool_runtime не нужны. Обязательный CLI-запуск убран из объёма работ. Все три рабочих шага проходят через реальные MCP tools/call. Новый экран, фоновый планировщик и конструктор цепочек не требуются.

## Контракты и поток данных

Новый сервер: `http://127.0.0.1:8003/mcp`, bind только на loopback.

| Инструмент | Вход | Успешный structuredContent |
| --- | --- | --- |
| `search` | `query: str`, `limit: int = 3` | `SearchResult`: query, fetched_at, total_count, incomplete_results, items |
| `summarize` | `search_result: SearchResult` | `SummaryResult`: query, source_count, markdown |
| `saveToFile` | `report: SummaryResult` | `SavedFile`: path, bytes_written, sha256 |

`items` содержит только `full_name`, `description`, `language`, `stars`, `url`; описание и язык допускают null. `source_count` равен длине items, а не total_count. При incomplete_results в Markdown явно указать неполноту выдачи. Описание ограничить 300 символами, отметив усечение многоточием; не загружать README и содержимое репозитория.

Входные и выходные Pydantic-модели строгие, без лишних полей. Query после strip — от 1 до 200 символов; limit — целое от 1 до 3 (bool не принимается). Markdown — непустой, максимум 6000 байт UTF-8. Ограничивать остальные строки, проверять полный сериализованный MCP-ответ против действующего лимита 16 KiB, включая content и structuredContent; при превышении возвращать ошибку без обрезания JSON. Отдельно проверить Unicode и экранируемые символы.

Передача данных задаётся однозначно:

```text
search(query, limit)
  → S = validate(SearchResult, result.structuredContent)
summarize(search_result=S)
  → R = validate(SummaryResult, result.structuredContent)
saveToFile(report=R)
  → F = validate(SavedFile, result.structuredContent)
```

Валидатор проверяет данные без преобразования типов. Следующему шагу передаётся исходный валидированный объект: без ручного копирования, повторной генерации моделью и извлечения данных из свободного текста. При isError, отсутствующем structuredContent или несовпадении схемы цепочка останавливается.

Файл создаётся в `deepseek-api/data/reports/<uuid>.md` относительно расположения серверного модуля, не cwd процесса. Имя генерирует сервер; инструмент не принимает произвольный путь. Записываются байты `report.markdown.encode('utf-8')` без добавлений. SHA-256 и bytes_written вычисляются по этим же байтам. Каждый новый запуск создаёт новый файл; существующие файлы не перезаписываются. Неполный файл при ошибке записи удаляется. Повторные вызовы сохранения автоматически не выполняются: тайм-аут после записи означает неопределённый результат, а не доказанное отсутствие файла.

## События, журнал и поведение чата

Для `/research` существующий POST `/api/agents/{agent_id}/messages` после валидации запроса возвращает `application/x-ndjson`. Остальные сообщения сохраняют прежний JSON-контракт. UI выбирает способ чтения по Content-Type. До начала потока ошибки ввода/отсутствующего агента/занятости возвращаются обычным JSON с соответствующим HTTP-статусом; после отправки заголовков ошибки передаются событиями.

Каждое событие содержит `run_id`, `agent_id`, `branch_id`, возрастающий `seq`, `type`. Набор событий:

| Событие | Когда отправлять | Данные |
| --- | --- | --- |
| `pipeline_started` | После принятия команды | query, limit=3, список ожидаемых шагов |
| `step_started` | Непосредственно перед MCP-вызовом | step, arguments, server_url |
| `step_completed` | После ответа MCP и проверки схемы | step, result, duration_ms |
| `step_failed` | Ошибка MCP, схемы или тайм-аут | step, безопасное error, duration_ms, фактический ответ при наличии |
| `pipeline_completed` | Все шаги успешны, результат записан в состояние чата | status=success, полный trace, saved_file, обновлённый agent snapshot |
| `pipeline_failed` | Цепочка или сохранение состояния не завершились | failed_step при наличии, status=error, trace, безопасное error |

В success-трассе хранить и MCP-ответ (`isError`, `content`, `structuredContent`), и фактические arguments. Отдельно фиксировать ошибки MCP и ошибки проверки схемы: `isError=false` с неверным structuredContent не означает успешный шаг. До каждого следующего вызова отправлять и flush-ить завершение предыдущего; не собирать все события до конца выполнения. Завершающее событие — ровно одно. EOF без завершающего события означает «Связь прервана; итог неизвестен», не успех.

Карточка и журнал принадлежат исходным agent_id/branch_id/run_id. Переключение агента не переносит их в другой чат. Пока команда выполняется, повторная отправка и изменения той же ветки блокируются и на клиенте, и сервером; разные исследовательские команды не держат глобальную блокировку на время сети. Выявленное существующее ограничение: обычный LLM-запрос держит registry lock и может задержать обновления исследования другого агента; это ограничение документировано, переделка архитектуры обычного чата исключена из дня 19.

Сохранять сообщение пользователя и карточку ответа через существующий механизм истории. Для карточки разрешить опциональное поле `pipeline` у assistant-сообщения: run_id, query, status, steps, saved_file/error. Сохранять состояние до первого MCP-вызова, после каждого законченного шага и при завершении. Поддержать старые role/content-сообщения и ветки без миграции вручную; историю и JSON результатов ограничивают действующие лимиты сообщений и ответов. В запросы LLM передавать только role/content, не служебные поля карточки. Локальная команда не вызывает провайдера/компрессию/извлечение фактов и не начисляет токены или стоимость модели.

При разрыве HTTP-соединения принятый запуск продолжает три шага в текущем серверном обработчике и сохраняет конечное состояние; ошибка записи в сокет отключает доставку событий, а не повторяет инструменты. После обновления страницы UI восстанавливает результат из истории. Автоповтора команды нет. После перезапуска сервера незавершённые карточки отмечаются interrupted с пояснением, что результат последнего шага мог остаться неизвестным; автоматически не возобновлять. Ошибка сохранения состояния явно отображается, уже созданный отчёт не удаляется и saveToFile не вызывается повторно.
