# Day 30 Private LLM Service — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Развернуть на VPS приватный локальный LLM-сервис с HTTP API и браузерным чатом, проверить сетевой доступ, ограничения и устойчивость.

**Architecture:** Отдельный процесс FastAPI с одним worker принимает запросы через SSH-туннель, проверяет ключ, контекст и нагрузку; обращается только к Ollama на loopback. SmolLM2 135M работает последовательно, допускается два ожидающих запроса. systemd обеспечивает запуск API и Ollama.

**Планируемый стек:** Debian 13.4 x86_64, Python 3.11+ (версию на VPS проверить), FastAPI, Uvicorn, httpx, tokenizers, Ollama, HuggingFaceTB/SmolLM2-135M-Instruct, OpenSSH, systemd, unittest.

---

Статус: пользователь установил Ollama и SmolLM2 135M на Hostkey vm.v2-pico с Debian 13.4 x86_64 и 898 МиБ RAM. Выполнены 10 последовательных и 3 одновременных запроса, проверены SSH-туннель с Mac и диалог с историей. [Фактические результаты](../../day-30/preflight.md). Код API-обёртки, веб-чат и rate limit не реализованы; жёсткий предел контекста не проверен. Этот план описывает дальнейшую реализацию. Задача 0 выполнена частично, пригодность полного стека на 1 ГБ ещё требует измерений. Основание: [спецификация](../specs/2026-10-11-day-30-private-llm-service-design.md).

## Задача 3. Ограничить частоту, очередь и время выполнения

- [ ] Создать тесты с управляемыми монотонными часами: 10 допущенных попыток, 11-я получает 429; истечение скользящего окна; корректный округлённый вверх Retry-After. Ключ идентифицировать безопасным внутренним идентификатором, а не писать секрет в события.
- [ ] Создать детерминированные async-тесты с удерживаемым upstream: один активный, два ожидающих, четвёртый отклонён; никакой скрытой неограниченной очереди. Использовать события синхронизации, не задержки по случайному времени.
- [ ] Реализовать `limits.py` с атомарным admission и FIFO-очередью. Предварительно обработанные валидные попытки учитываются rate limiter до проверки заполненности очереди.
- [ ] Добавить тесты удаления отменённого ожидающего запроса, timeout очереди, исключения upstream, disconnect активного клиента. Фоновая задача владеет слотом до реального завершения; не создавать новую генерацию при отмене HTTP-ожидания.
- [ ] Задать общий generation deadline через async-механизм, а не только socket read timeout. При неопределённом завершении после deadline выставить degraded, отклонять дальнейшую генерацию и завершать ожидающие запросы понятной ошибкой.
- [ ] Описать и протестировать восстановление: совместный перезапуск API/Ollama, readiness и новый успешный запрос. Очередь и rate limit после рестарта пусты; это задокументировано.
- [ ] Запустить `test_private_service_limits.py`, затем все тесты сервиса; сохранить коммит.

- [ ] Контекстные проверки используют тот же pinned tokenizer на тестовой машине и синтетические prompt у границы; unit-тесты дополнительно доказывают отсутствие upstream-вызова при отклонении.
- [ ] Для rate limit отправить 11 запросов за окно и явно отделить 429 от busy. Детерминированный критерий 10+1 проверить также на fake upstream без очереди; не менять рабочие лимиты ради красивого live-результата.
- [ ] На VPS параллельно измерять пиковую RAM API и всех процессов Ollama, фиксировать OOM и счётчики рестартов. Для короткой выборки обозначить p95 как описательную статистику, не SLA.
- [ ] Провести отказные сценарии: stop Ollama → 503, start → восстановление; deadline/degraded → совместный restart; отмена браузера → отсутствие утечки слотов. Отдельно аварийно завершить API во время удерживаемой генерации и проверить по журналу/PID, что автоматический restart сначала перезапускает Ollama и только после её восстановления запускает новый API: старый и новый запросы не перекрываются. Искусственную задержку использовать в тестовой среде, без изменения рабочего контракта.
- [ ] Проверить публичные порты, доступ без ключа и исчезновение доступа при закрытом туннеле. Перезагрузить VPS, открыть туннель заново, повторить smoke без ручного запуска процессов.
- [ ] Кратко заблокировать исходящие новые интернет-соединения на VPS, сохраняя established SSH, доступ к консоли и автоматический откат правила; проверить генерацию уже скачанной модели. После проверки снять временное правило. Не применять такое правило вслепую в единственной SSH-сессии.


## Что понадобится от пользователя перед развёртыванием

Первый вход и диагностика выполнены, SSH-туннель проверен. Настройка входа по ключу не подтверждена. При продолжении проверить состояние сервиса, применённые настройки Ollama и оставшиеся измерения задачи 0; затем оценить запас памяти для API-обёртки. Пароли и приватные ключи пользователь не отправляет в чат. Покупка новых ресурсов не требуется для продолжения проверки.
