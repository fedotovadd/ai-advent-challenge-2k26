# День 6: первый агент

## Цель

Преобразовать локальный веб-чат из Дня 5 в однопроцессное приложение с N независимыми агентами. Каждый агент принимает сообщение пользователя, формирует запрос к LLM через API, сохраняет свою историю и возвращает ответ в общем веб-интерфейсе.

Решение должно демонстрировать, что N агентов существуют внутри одного экземпляра приложения: для них не запускаются отдельные HTTP-серверы, процессы или копии интерфейса.

## Пользовательский сценарий

1. Пользователь открывает один локальный веб-интерфейс.
2. В боковой панели он видит список агентов и счётчик их количества.
3. Пользователь может создать одного агента либо указать N и создать N демонстрационных агентов.
4. Каждый демонстрационный агент получает собственную конфигурацию: имя, модель и system prompt. Конфигурации циклически используют доступные модели и разные роли, чтобы различие было видно в интерфейсе.
5. Пользователь выбирает агента в списке и отправляет ему сообщение в общем чате.
6. Выбранный агент сам подготавливает запрос, вызывает LLM и сохраняет ответ в своей истории.
7. При переключении пользователь видит историю, настройки и метаданные именно выбранного агента.

Создание N агентов не вызывает N запросов к провайдерам и поэтому происходит быстро и без расходов API. Массовая отправка одного запроса всем агентам и параллельная оркестрация не входят в День 6.

## Архитектура

```text
Один веб-сервер
    │
    ├── HTTP-обработчик — принимает и возвращает HTTP/JSON
    ├── AgentRegistry — создаёт, хранит и находит N агентов
    │     ├── Agent #1 — config, history, metadata
    │     ├── Agent #2 — config, history, metadata
    │     └── Agent #N — config, history, metadata
    └── LLM-клиент — общий адаптер к DeepSeek и Z.AI API
```

### `Agent`

Агент — отдельная сущность доменной логики. Он инкапсулирует:

- идентификатор и отображаемое имя;
- конфигурацию вызова LLM: модель, system prompt, формат, ограничение токенов и stop-последовательность;
- историю сообщений только этого агента;
- метаданные последнего запроса;
- метод `respond(text, temperature)`, который принимает пользовательский текст, формирует payload, вызывает общий LLM-клиент, проверяет ответ, обновляет историю и метаданные.

Агент не зависит от HTTP. Он получает вызываемую функцию LLM-клиента через конструктор, поэтому его можно проверять подставным клиентом без сети и API-ключа.

### `AgentRegistry`

Реестр хранит агентов в памяти процесса и синхронизирует доступ к ним. Он отвечает за:

- начального агента `agent-1`;
- создание одного агента с новым идентификатором;
- создание N демонстрационных агентов;
- выдачу списка и поиск агента по ID;
- обновление конфигурации выбранного агента.

Для возвращаемых данных используются копии, чтобы вызывающий код не мог изменить внутреннее состояние реестра напрямую.

### LLM-клиент

Существующая функция вызова провайдера остаётся общей инфраструктурой. Она выбирает DeepSeek или Z.AI по модели, берёт соответствующий ключ окружения и выполняет HTTP-вызов. Внутри агента не создаются собственные серверы или процессы; разрешено создавать клиент API на отдельный запрос, как в текущем коде.

## HTTP API

Маршруты отражают термин «агент», а не «сессия».

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/agents` | Вернуть список агентов с конфигурацией, историей и последними метаданными. |
| `POST /api/agents` | Создать одного агента с настройками по умолчанию. |
| `POST /api/agents/bulk` | Создать N демонстрационных агентов. Тело: `{ "count": N }`. |
| `PUT /api/agents/{id}/settings` | Обновить конфигурацию одного агента после валидации. |
| `POST /api/agents/{id}/messages` | Передать сообщение выбранному агенту и вернуть его ответ. |

`count` должен быть положительным целым числом с безопасным верхним пределом, например 100. Это защищает память интерфейса от случайного чрезмерного создания объектов. Значение N в документации означает любое допустимое количество, а не фиксированные 100.

Ошибки неизвестного агента, некорректного JSON, невалидной конфигурации, отсутствующего API-ключа и ошибки провайдера возвращаются в том же стиле, что и в Дне 5.

## Интерфейс

Интерфейс остаётся одним HTML-приложением:

- левая панель: «Агенты», кнопка создания одного агента, поле N и кнопка «Создать N агентов», счётчик и список;
- центральная панель: чат активного агента;
- правая панель: конфигурация и метаданные активного агента.

В списке показываются имя агента, модель и число сообщений. При создании N агентов пользователь сразу видит, что их число увеличилось, а выбор любого из них показывает независимую конфигурацию и пустую историю. Отправка сообщения доступна только активному агенту.

## Инварианты

- Один сервер содержит все N агентов.
- У каждого агента свои `config`, `messages` и `metadata`; изменение или сообщение одного агента не затрагивает другого.
- HTTP-обработчик не формирует LLM payload и не меняет историю напрямую: это делает `Agent.respond`.
- LLM-клиент не знает об агентах и не хранит их состояние.
- Обновление настроек валидирует доступную модель, непустой system prompt, формат, лимит токенов и stop-последовательность.
- Приложение остаётся in-memory: после перезапуска агенты и история пропадают. Постоянное хранилище не входит в задачу.

## Не входит в объём

- отдельный микросервис на агента;
- отдельное окно или приложение для каждого агента;
- инструменты, RAG, планирование шагов, judge, input/output policies;
- массовый параллельный запуск одного запроса всем агентам;
- постоянное хранилище, аутентификация, роли пользователей и лимиты использования API.

Input/output policy и judge можно добавить позже как независимые расширения внутри `Agent.respond`, но они не нужны, чтобы агент соответствовал Дню 6.

## Проверка результата

Автотесты должны подтверждать:

1. `Agent.respond` формирует корректный payload с настройками и только своей историей, вызывает переданный LLM-клиент и сохраняет ответ.
2. Ошибочный или пустой ответ LLM не добавляется в историю как ответ ассистента.
3. Реестр создаёт N агентов с уникальными ID и изолированными конфигурациями.
4. Настройка и переписка одного агента не меняют другие агенты.
5. HTTP API создаёт одного агента, создаёт N агентов, возвращает список, обновляет настройки и передаёт сообщение нужному агенту.
6. При отсутствии ключа или ошибке LLM API возвращается понятная ошибка и метаданные активного агента отражают сбой.
7. Существующий веб-чат продолжает отправлять сообщение и отображать ответ активного агента.

## Критерий готовности

В одном запущенном локальном приложении пользователь может создать N агентов с разными конфигурациями, выбрать любого из них, отправить ему запрос и получить в интерфейсе корректный ответ LLM через API. Код агента существует как отдельная сущность, а не как последовательность действий HTTP-обработчика.
