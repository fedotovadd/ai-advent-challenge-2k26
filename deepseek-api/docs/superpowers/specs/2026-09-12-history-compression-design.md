# Сжатие истории диалога — дизайн

## Цель

Уменьшить размер контекста, который агент отправляет модели в длинном диалоге, сохранив для модели ключевые факты ранней переписки и не меняя видимую пользователю историю.

## Границы

- Агент хранит последние 10 сообщений в исходном виде.
- Более старый контекст представляет отдельное поле `summary`; в payload он заменяет полные старые сообщения.
- Пользовательская лента сообщений остаётся полной: сжатие влияет только на контекст следующего запроса.
- Сводка создаётся отдельным коротким вызовом уже выбранной модели. В ней должны быть факты, решения, ограничения, предпочтения и открытые вопросы, но не дословная переписка.
- Каждый раз, когда новое сообщение вытесняет самое старое из последних десяти, агент обновляет `summary` из предыдущей summary и вытесненного сообщения. Сводка не пересказывается по полной истории повторно.

## Модель данных

В `DEFAULT_SETTINGS` добавляется `contextCompressionEnabled: True`. Снимок агента получает ровно одно новое верхнеуровневое поле `context`:

```json
{
  "summary": null,
  "compressedMessageCount": 0,
  "summaryUsage": {
    "calls": 0,
    "promptTokens": 0,
    "completionTokens": 0,
    "totalTokens": 0,
    "usd": 0,
    "last": null
  }
}
```

`summary` — непустая строка или `null`; `compressedMessageCount` — число первых сообщений `messages`, включённых в summary. `summaryUsage.last` — `null` либо `{promptTokens, completionTokens, totalTokens, source, cost}`; остальные числа — накопленные результаты успешных summary-вызовов. Полная `messages` сохраняется для интерфейса, но в модель не отправляется целиком при включённой компрессии.

`STATE_VERSION` становится `3`. Загрузчик мигрирует v1 в v3, добавляя прежние поля v2 (`trainingContextLimit`, `sendOnOverflow`, `metrics`), затем `contextCompressionEnabled=True` и пустой `context`. Загрузчик v2 в v3 добавляет только новые настройку и `context`. Неверные снимки по-прежнему безопасно игнорируются. После миграции сохраняются все существующие `messages`, `metrics` и метаданные.

## Сборка контекста

`RECENT_MESSAGES_LIMIT = 10` — размер свежего сырого окна, а `SUMMARY_BATCH_MESSAGES = 10` — размер пакета для одного summary-вызова. До вызова модели агент рассчитывает `target_compressed_count = max(0, len(messages) - RECENT_MESSAGES_LIMIT)`. Если между этим target и текущим `compressedMessageCount` накопилось не менее 10 реплик, в summary попадает весь диапазон `[compressedMessageCount:target_compressed_count]` в исходном порядке. До заполнения пакета summary не обновляется и ожидающие реплики временно остаются в основном запросе. Поэтому между обновлениями в модели может быть до 20 исходных сообщений: 10 свежих и до 10 ожидающих сжатия; один вызов summary приходится на пять обычных ходов диалога.

Перед пользовательским запросом агент строит два представления:

1. **Полная история**: system prompt, все сообщения и новое сообщение. Она используется только для расчёта контрфактической метрики «без сжатия».
2. **Сжатая история**: system prompt, при наличии отдельное системное сообщение со summary, несжатый хвост после последнего успешно сжатого сообщения и новое сообщение. Только она передаётся провайдеру. До следующего пакета хвост постепенно растёт, затем снова сокращается до 10 последних сохранённых сообщений.

Сводка готовится до основного вызова только если старые сообщения уже существуют. Она собирается из предыдущей summary и точно определённого диапазона новых сообщений; каждая реплика размечается как `USER:` или `ASSISTANT:`. У summary-вызова фиксированный system prompt с инструкцией сохранять факты, решения, ограничения, предпочтения и открытые вопросы; payload содержит модель агента, `temperature=0` и `max_tokens=512`. Он не наследует `format`, `stop` или пользовательский `maxTokens`. Пустой или нестроковый результат считается ошибкой.

Summary payload предварительно проверяется только по реальному `MODEL_CAPABILITIES[model]["contextLimit"]` с резервом в 512 токенов. Учебный `trainingContextLimit` и `sendOnOverflow` относятся исключительно к основному пользовательскому запросу и не влияют на summary-вызов: это позволяет компрессии уменьшить учебный контекст, а не блокировать её заранее. Если summary не помещается в реальный лимит или провайдер её отклоняет, запрос не отправляется как probe и агент возвращает описанный ниже 502 без изменений состояния.

Новая summary и её usage существуют только как локальный кандидат до успешного основного ответа. При ошибке summary основной запрос не отправляется, а `messages`, `context`, накопленные метрики и metadata не меняются. При ошибке основного вызова summary тоже не сохраняется: сохраняется только прежняя семантика пользовательской реплики и metadata ошибки. Metadata всегда описывает только основной payload, а не служебный summary payload. `ContextSummaryError` обрабатывается в HTTP как 502 с безопасным текстом «Не удалось обновить сводку истории.» и текущим снимком агента.

## Метрики и сравнение

На каждом успешном ходе сохраняются:

- оценка токенов полного payload и фактически переданного сжатого payload;
- экономия токенов этого хода и накопленная экономия;
- число свёрнутых сообщений и размер summary;
- токены и стоимость вызова summary отдельно от основного ответа.

В строке `metrics.calls` добавляются точные поля: `fullPayloadEstimatedTokens`, `compressedPayloadEstimatedTokens`, `compressionGrossSavedTokens`, `summaryCallTokens`, `compressionNetSavedTokens`, `grossInputSavingsUsd`, `summaryCostUsd` и `netSavingsUsd`. Оценки обоих payload включают system сообщения и обычные options. `compressionGrossSavedTokens = fullPayloadEstimatedTokens - compressedPayloadEstimatedTokens`; `compressionNetSavedTokens = compressionGrossSavedTokens - summaryCallTokens`. Контрфактический полный payload не отправляется, поэтому всегда является оценкой; `promptTokens` основного вызова берётся из фактического usage провайдера, если оно полное, иначе из оценки. Для цены используется только разница входных токенов по тарифу модели; `netSavingsUsd = grossInputSavingsUsd - summaryCostUsd`. Для бесплатной модели все USD-поля равны 0. Summary usage использует те же правила actual/estimated, что и основной вызов.

Панель метрик показывает режим контекста, количество сжатых сообщений, токены до/после, сэкономленные токены и стоимость сводок. README описывает повторяемый опыт: провести одинаковый длинный диалог с отключённой и включённой компрессией, затем задать вопрос о факте из ранней истории; качество оценивается по сохранности правильного факта, расход — по сохранённым метрикам. Итоговая экономия считается с учётом стоимости summary.

## Настройка и интерфейс

Компрессия включена для каждого нового агента по умолчанию; в настройках агента её можно выключить, чтобы получить честный контрольный вариант «без сжатия». HTTP принимает прежние наборы из 5 полей (`model`, `systemPrompt`, `format`, `maxTokens`, `stop`) и 7 полей Day 8 (добавлены `trainingContextLimit`, `sendOnOverflow`), а также их варианты с `contextCompressionEnabled`. Если новое поле отсутствует, сервер задаёт `True`; ответ всегда возвращает полный восьмипольный settings-объект. Новое поле обязано быть boolean, иначе сервер возвращает обычный 400 без изменения настроек.

В выключенном режиме summary не вызывается, `context` не используется, а основной payload содержит полную историю. При повторном включении следующий ход начинает копить несжатый старый диапазон до пакета из 10 сообщений. Размер свежего окна и размер пакета равны 10 сообщениям. Подписи панели объясняют, что оценка токенов является приблизительной, если провайдер не вернул `usage`.

## Проверки

Автоматические тесты докажут, что:

- до переполнения окна payload содержит полную историю и summary не создаётся;
- на границах 10, 11 и последующих сообщений summary получает вытесненные реплики строго по порядку, а основной payload содержит summary и несжатый хвост;
- полная история остаётся видимой, а v1→v3 и v2→v3 сохраняют её, summary и метрики переживают перезапуск;
- summary-вызов использует отдельные prompt, options и usage, а metadata остаётся metadata основного payload;
- старые варианты `PUT settings` получают включённую компрессию по умолчанию, а неверный новый флаг возвращает 400 без замены сохранённых настроек;
- trainingContextLimit и sendOnOverflow проверяются только для основного payload; summary использует реальный лимит и при его ошибке атомарно возвращает 502, а не 409/422;
- сжатый payload меньше полного, а метрики показывают gross и net экономию с учётом затрат summary;
- отключённая компрессия передаёт полную историю и не вызывает модель для summary; режимы можно выключить и включить снова;
- ошибка модели при создании summary возвращает 502 и не изменяет сообщения, summary, metadata или накопления.
