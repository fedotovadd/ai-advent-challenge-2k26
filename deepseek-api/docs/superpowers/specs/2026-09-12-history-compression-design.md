# Сжатие истории диалога — дизайн

## Цель

Уменьшить размер контекста, который агент отправляет модели в длинном диалоге, сохранив для модели ключевые факты ранней переписки и не меняя видимую пользователю историю.

## Границы

- Агент хранит последние 10 сообщений в исходном виде.
- Более старый контекст представляет отдельное поле `summary`; в payload он заменяет полные старые сообщения.
- Пользовательская лента сообщений остаётся полной: сжатие влияет только на контекст следующего запроса.
- Сводка создаётся отдельным коротким вызовом уже выбранной модели. В ней должны быть факты, решения, ограничения, предпочтения и открытые вопросы, но не дословная переписка.
- Каждый раз, когда новое сообщение вытесняет самое старое из последних десяти, агент обновляет `summary` из предыдущей summary и вытесненного сообщения. Сводка не пересказывается по полной истории повторно.

## Модель данных

`Agent` получает два новых сохраняемых поля:

- `summary`: строка или `None`, сжатый контекст сообщений, которые больше не входят в окно последних десяти;
- `summaryUsage`: метрики последнего обновления и накопленные токены/стоимость сводок.

Полная `messages` сохраняется для интерфейса и обратной совместимости. Состояние повышает версию, а загрузчик старой версии создаёт пустую summary и нулевые метрики сводок.

## Сборка контекста

Перед пользовательским запросом агент строит два представления:

1. **Полная история**: system prompt, все сообщения и новое сообщение. Она используется только для расчёта контрфактической метрики «без сжатия».
2. **Сжатая история**: system prompt, при наличии отдельное системное сообщение со summary, последние 10 сообщений и новое сообщение. Только она передаётся провайдеру.

Сводка создаётся до основного вызова только если старые сообщения уже существуют. При ошибке обновления summary основной запрос не отправляется, история не меняется, а ошибка и метаданные фиксируются так же безопасно, как при ошибке основного запроса.

## Метрики и сравнение

На каждом успешном ходе сохраняются:

- оценка токенов полного payload и фактически переданного сжатого payload;
- экономия токенов этого хода и накопленная экономия;
- число свёрнутых сообщений и размер summary;
- токены и стоимость вызова summary отдельно от основного ответа.

Панель метрик показывает режим контекста, количество сжатых сообщений, токены до/после, сэкономленные токены и стоимость сводок. README описывает повторяемый опыт: провести одинаковый длинный диалог с отключённой и включённой компрессией, затем задать вопрос о факте из ранней истории; качество оценивается по сохранности правильного факта, расход — по сохранённым метрикам. Итоговая экономия считается с учётом стоимости summary.

## Настройка и интерфейс

Компрессия включена для каждого нового агента по умолчанию; в настройках агента её можно выключить, чтобы получить честный контрольный вариант «без сжатия». Константа окна равна 10 сообщениям. Подписи панели объясняют, что оценка токенов является приблизительной, если провайдер не вернул `usage`.

## Проверки

Автоматические тесты докажут, что:

- до переполнения окна payload содержит полную историю и summary не создаётся;
- после переполнения старое сообщение переносится в summary, а payload содержит summary и только последние 10 сообщений;
- полная история остаётся видимой и summary переживает перезапуск;
- сжатый payload меньше полного, а метрики учитывают затраты summary;
- отключённая компрессия передаёт полную историю и не вызывает модель для summary;
- ошибка модели при создании summary не портит сохранённую историю.
