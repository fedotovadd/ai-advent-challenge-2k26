# Рабочий веб-интерфейс DeepSeek — дизайн

## Цель

Заменить терминальный ввод понятным локальным веб-интерфейсом, сохранив существующую отправку запросов в DeepSeek. Пользователь должен вести несколько чатов, отправлять сообщение и видеть точные данные последнего обращения к API.

## Пользовательский интерфейс

Страница выполнена в светлой тёплой теме с кирпичным акцентом:

- слева — список сессий и кнопка создания нового чата;
- в центре — заголовок активной сессии, сообщения и поле ввода;
- справа — user prompt, system prompt, JSON-представление отправленного запроса и состояние последнего ответа;
- на узком экране боковые панели должны превращаться в верхнюю область сессий и нижнюю область метаданных.

Красота не является функциональным приоритетом: интерфейс должен быть чистым, читаемым и работать без сборки JavaScript.

## Архитектура

`main.py` будет одновременно запускать локальный HTTP-сервер и обращаться к DeepSeek. Запуск `python main.py` открывает сервер на `127.0.0.1:8000`; прежний интерактивный CLI заменяется веб-интерфейсом. Сервер отдаёт единственную HTML-страницу со встроенными CSS и JavaScript и предоставляет JSON API:

- `GET /api/sessions` — список сессий и их сообщения;
- `POST /api/sessions` — создание сессии;
- `POST /api/sessions/<id>/messages` — приём текста, формирование списка сообщений, вызов DeepSeek и сохранение ответа.

Сессии хранятся только в памяти процесса. Это намеренно: приложение остаётся минимальным, а перезапуск даёт чистое состояние. Позже хранилище можно заменить, не меняя браузерный контракт.

Вызов DeepSeek вынесен в небольшую функцию, принимающую список сообщений. Она создаёт клиента с теми же `DEEPSEEK_API_KEY`, `base_url` и `deepseek-v4-flash`, что использует текущий CLI. Каждый вызов получает фиксированный `SYSTEM_PROMPT` — «Ты полезный AI-помощник. Отвечай ясно, практично и по-русски.» — первым элементом `messages`, после которого идут все сообщения конкретной сессии. После каждого успешного или неуспешного обращения сервер возвращает метаданные, которые показываются в правой панели.

## HTTP-контракт

`GET /` возвращает HTML-страницу с `Content-Type: text/html; charset=utf-8`. Неизвестный HTML-маршрут возвращает 404. Все ответы `/api/*` имеют `Content-Type: application/json; charset=utf-8`.

- `GET /api/sessions` возвращает `200` и `{"sessions": [session, ...]}`. После запуска список содержит одну сессию с id `session-1`, названием «Новый чат» и пустым списком `messages`.
- `POST /api/sessions` не принимает тело и возвращает `201` с `{"session": session}`. Новый id формируется последовательно (`session-2`, `session-3`, ...), а название до первого сообщения — «Новый чат».
- `POST /api/sessions/<id>/messages` принимает `{"text": "..."}`. Непустая строка без внешних пробелов добавляется в сессию; первое сообщение автоматически становится названием, обрезанным до 40 символов. Успешный ответ — `200` и `{"session": session, "metadata": metadata}`.

`session` имеет форму `{"id": string, "title": string, "messages": [{"role": "user"|"assistant", "content": string}]}`. `metadata` имеет форму:

```json
{
  "userPrompt": "текст последнего сообщения пользователя",
  "systemPrompt": "фиксированный SYSTEM_PROMPT",
  "payload": {"model": "deepseek-v4-flash", "messages": [{"role": "system", "content": "..."}]},
  "status": {"kind": "success", "label": "200 OK"}
}
```

`payload` — снимок именно того словаря, который передан клиенту DeepSeek, без ключа API. При ошибке обращения API сервер возвращает `502` с `{"session": session, "error": "Не удалось получить ответ DeepSeek.", "metadata": metadata}`, где `status` имеет вид `{"kind": "error", "label": "Ошибка API"}`; пользовательское сообщение остаётся в сессии. Пустой ответ DeepSeek является такой же ошибкой `502`.

При отсутствии ключа сервер сначала добавляет user-сообщение и формирует `payload`, затем возвращает `503` с `{"session": session, "error": "Не задан DEEPSEEK_API_KEY.", "metadata": metadata}` и тем же error-статусом. Это делает состояние чата и правую панель одинаково предсказуемыми для ошибок до и во время обращения к провайдеру. Для каждого `502` и `503` `metadata` обязательно содержит `userPrompt`, `systemPrompt`, полный payload и status. Пустой или отсутствующий `text` и неверный JSON — `400`; неизвестная сессия — `404`; неизвестный API-маршрут — JSON `404`.

## Поток данных

1. Браузер запрашивает список сессий и рисует активный чат.
2. Пользователь отправляет текст. Пока запрос выполняется, кнопка отправки блокируется и показывается состояние ожидания.
3. Сервер добавляет user-сообщение, соединяет system prompt с историей, формирует payload и вызывает DeepSeek.
4. При успехе ответ ассистента добавляется в сессию. Браузер получает обновлённую сессию и метаданные.
5. При ошибке пользовательское сообщение остаётся в истории, а интерфейс показывает понятный текст ошибки и payload последнего запроса.

## Ошибки и безопасность

- Без ключа API запрос возвращает понятную ошибку; сервер не падает.
- Пустое сообщение отклоняется до вызова DeepSeek.
- Ошибки клиента и пустой ответ API возвращаются как JSON с кодом ошибки и не показывают трассировку.
- Ключ API остаётся только в переменной окружения и никогда не передаётся браузеру.
- Все динамические значения — сообщения, названия сессий, ошибки и значения метаданных — отображаются через DOM-свойство `textContent`, а не вставкой HTML: содержимое пользовательских и модельных ответов не может выполнить код в браузере.
- Каждый изменяющий API-запрос проверяет заголовок `Origin`: если он указан и не равен локальному origin сервера, сервер отвечает JSON `403`. Это не даёт внешней странице незаметно отправлять запросы в DeepSeek от имени пользователя.

## Проверка

`tests/test_main.py` заменяется HTTP-тестами для фабрики сервера: она создаёт сервер на временном порту, а DeepSeek замокан в точке отдельной функции вызова. Тесты должны подтверждать создание сессии, начальное состояние, отказ пустого и неверного JSON, 404 неизвестной сессии, корректный payload (включая system prompt и историю), сохранение ответа, отсутствие ключа и обработку ошибки API с возвращённой сессией, а также отказ POST с чужим `Origin`. Отдельно проверяется, что HTML отдан корректно. `README.md` обновляется: вместо терминального ввода в нём указаны запуск сервера и URL интерфейса. Затем запускается весь набор тестов и выполняется ручная проверка в браузере с локальным сервером.
