# Локальный веб-чат DeepSeek

Приложение запускает локальный интерфейс для общения с DeepSeek. Внутри одного сервера работают независимые агенты со своей перепиской, настройками и данными последнего запроса к API.

## Настройки и запуск

### 1. Получите API-ключ

Создайте ключ в [DeepSeek Platform](https://platform.deepseek.com/api_keys). Никому не отправляйте ключ и не записывайте его в исходный код.

### 2. Подготовьте окружение

Требуется Python 3.9 или новее.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 3. Добавьте ключ

В macOS или Linux:

```bash
export DEEPSEEK_API_KEY="ваш_ключ"
```

Для `glm-4.7-flash` добавьте также ключ Z.AI:

```bash
export ZAI_API_KEY="ваш_ключ_z_ai"
```

### 4. Запустите приложение

```bash
python3 main.py
```

Откройте в браузере [http://127.0.0.1:8000](http://127.0.0.1:8000).

Введите сообщение и нажмите «Отправить». Слева можно создавать и переключать агентов. Справа отображаются user prompt, system prompt и JSON запроса, отправленного в DeepSeek. История и настройки агентов сохраняются между запусками приложения.

## День 2 — Настройки ответа

В правой панели над метаданными находятся настройки активной сессии:

- **System prompt** — базовая инструкция для модели.
- **Формат ответа** — обычный текст или JSON. В режиме JSON приложение передаёт в DeepSeek `response_format={"type":"json_object"}` и дополняет system prompt инструкцией вернуть валидный JSON.
- **Максимум токенов** — необязательный лимит, который передаётся как `max_tokens`.
- **Стоп-последовательность** — необязательная строка, которая передаётся как `stop`.

Все настройки сохраняются автоматически в текущей сессии: формат — сразу, а текстовые поля — через короткую паузу после ввода. Если сразу отправить сообщение, приложение сначала сохранит текущие настройки, затем отправит запрос. Поле сообщения закреплено внизу центральной панели, а прокручивается только история диалога.

Чтобы выполнить задание второго дня, отправьте запрос с пустыми настройками, затем задайте формат, лимит или стоп-последовательность и повторите тот же запрос. В разделе «Метаданные» можно сравнить фактически отправленные JSON-запросы и полученные ответы.

## День 3 — Сравнение способов рассуждения

В режиме «День 3» доступны 2 встроенные задачи: «Три сервера» – логическая и «Выбор канала» –аналитическая. Выберите задачу из списка и нажмите «Запустить 4 стратегии». Для каждой из них DeepSeek отвечает напрямую, пошагово, через созданный им промпт и как группа экспертов; затем отдельный вызов модели качественно сравнивает ответы с эталоном и критериями именно этой задачи.

### Способы рассуждения

В эксперименте одна и та же задача передаётся четырьмя способами. Результаты не используют историю и настройки обычного чата, поэтому их удобно сравнивать между собой.

- **Напрямую.** Модель получает только условие задачи и инструкцию дать краткий, проверяемый ответ. Этот способ показывает базовый результат без дополнительных подсказок о ходе решения.
- **Пошагово.** Модель сначала фиксирует исходные данные и цель, затем оформляет решение в пронумерованных шагах с промежуточными результатами и выполняет самопроверку. Подходит для задач, где важно увидеть и проверить логику или вычисления.
- **Свой промпт.** Это два последовательных вызова. Сначала модель в роли инженера промптов создаёт инструкцию для решения конкретной задачи: выбирает роль, метод, порядок шагов, типичные ошибки и способ проверки. Затем другая инструкция просит модель решить задачу по созданному промпту. Так можно увидеть, как качество постановки задачи влияет на ответ.
- **Группа экспертов.** Три роли решают задачу независимо: аналитик разбирает условия и допущения, инженер предлагает процедуру или расчёт, критик ищет ловушки и проверяет граничные случаи. Такой подход полезен, когда нужно сверить решение с разных точек зрения.

После четырёх стратегий модель-модератор сопоставляет их ответы с эталонным решением и критериями выбранной задачи. В карточках результатов можно раскрыть фактические системные и пользовательские промпты, а для «Своего промпта» — также созданную инструкцию. Результаты каждой запущенной задачи сохраняются до перезагрузки страницы и снова показываются при возврате к ней.

### Выводы

Ответы по существу не отличаются: все четыре способа пришли к верным итогам.

Наиболее точного «победителя» здесь нет — точность одинакова. Но наиболее полными и проверяемыми выглядят «Пошагово» и «Группа экспертов»: они показывают ход расчёта или проверки, а не только итог. В первом задании они дополнительно указали общее число регистраций после прироста показов; это уточнение, а не другое решение.

- Прямой/краткий способ полезен для простых задач, когда нужен быстрый итог.
- Пошаговый способ — для вычислений и логики, где человеку важно проверить каждый переход и избежать ошибок.
- Группа экспертов — для неоднозначных задач: разные роли могут независимо проверить решение, найти слабые места и предложить более ясное обоснование.
- Свой промпт — полезен, когда вводных данных недостаточно или неочевиден способ решения. На практике часто пригождается.

## День 4 — Температура

В разделе «Настройки ответа» добавлен ползунок для выбора температуры.

### Тестирование

Запросы отправлялись с тремя значениями температуры:

- `temperature = 0`
- `temperature = 0.7`
- `temperature = 1.2`

Влияние температуры проверили на нескольких задачах, включая:

- математическую — составить команды из нескольких учеников по заданным правилам;
- креативную — придумать пять необычных названий напитка для кофейни.

### Выводы

В математической задаче влияние температуры заметить сложнее. Однако при повторных запусках с `temperature = 1.2` ходы решения различались сильнее, чем при других значениях.

В креативной задаче разница заметнее:

- при `temperature = 0` модель предлагала двухсловные названия, похожие на привычные словосочетания: например, «Северное сияние» и «Утро в Тоскане»; к ним добавлялось описание напитка;
- при `temperature = 1.2` появлялись и более необычные трёхсловные варианты: например, «Бархатный подземный переход» и «Туманный альпинист».


#### `temperature = 0`

Подходит для задач, где важны повторяемость, строгая структура и минимальная вариативность: вычислений, проверки условий, кода, извлечения данных и отчётов по шаблону. В опыте оба ответа были почти одинаково организованы и дали одинаковое корректное решение.

#### `temperature = 0.7`

Хороший универсальный режим для объяснений, обучения, анализа и рабочих текстов. Ответ остаётся точным, но модель может выбрать другой корректный способ рассуждения и объяснить его более естественно.

#### `temperature = 1.2`

Лучше использовать для генерации идей, вариантов, гипотез, сценариев, названий и творческих текстов. В математической задаче ответы тоже остались правильными, но заметнее менялись подача и детализация. Для строгих вычислений высокая температура не даёт преимущества — результат всё равно нужно проверять.

### Итог

- Для точных и повторяемых задач — `0`.
- Для большинства повседневных запросов и понятных объяснений — `0.7`.
- Для поиска нестандартных вариантов и творчества — `1.2`.

## День 5 — сравнение моделей

В настройках каждого чата доступен выбор модели:

- слабая — `deepseek-v4-flash`;
- средняя — `glm-4.7-flash`;
- сильная — `deepseek-v4-pro`.

Выбор, а также метаданные последнего запроса, принадлежат конкретному чату. При переходе между чатами правая панель показывает именно его модель, время ответа, общее число токенов и стоимость. Flash и Pro идут через DeepSeek API с `DEEPSEEK_API_KEY`, а GLM — через Z.AI с `ZAI_API_KEY`.

Для платных моделей стоимость в USD считается по формуле:

`prompt_tokens × цена входа + completion_tokens × цена выхода`.

### Тарифы и расчет стоимости

Цены указаны в USD за 1 млн токенов. Для DeepSeek используются off-peak тарифы для входных токенов без cache hit; приложение не получает от API разбиение входных токенов по кэшу.

| Модель | Провайдер | Входные токены | Выходные токены |
| --- | --- | ---: | ---: |
| `deepseek-v4-flash` | DeepSeek | $0,22 | $0,66 |
| `glm-4.7-flash` | Z.AI | Бесплатно | Бесплатно |
| `deepseek-v4-pro` | DeepSeek | $0,66 | $1,98 |

Для платных моделей приложение считает стоимость так:

`стоимость (USD) = (prompt_tokens × цена входа + completion_tokens × цена выхода) / 1 000 000`.

Для `glm-4.7-flash` стоимость всегда показывается как «Бесплатно». Тарифы DeepSeek приведены по [официальной таблице цен](https://api-docs.deepseek.com/quick_start/pricing/), а бесплатный тариф GLM — по [таблице Z.AI](https://docs.z.ai/guides/overview/pricing).

### Результаты сравнения

Для сравнения все модели получили один и тот же запрос при одинаковом system prompt: «У Маши есть 3 яблока, а у Пети — на 2 яблока больше. Сколько всего яблок у мальчиков?»

| Модель | Время ответа | Всего токенов | Стоимость запроса |
| --- | ---: | ---: | ---: |
| `deepseek-v4-flash` | 4,06 с | 654 | $0,000363 |
| `glm-4.7-flash` | 5,23 с | 490 | Бесплатно |
| `deepseek-v4-pro` | 18,46 с | 1367 | $0,002499 |

### Выводы

- `deepseek-v4-flash` в этом запуске ответила быстрее всех. Это хороший вариант, когда важна минимальная задержка и допустима небольшая стоимость запроса.
- `glm-4.7-flash` отстала от Flash всего на 1,17 с, использовала меньше всего токенов и не требует оплаты. Для учебных, тестовых и повседневных задач это наиболее выгодный выбор.
- `deepseek-v4-pro` сформировала самый длинный ответ, но оказалась примерно в 4,5 раза медленнее Flash и почти в 7 раз дороже. Её стоит выбирать для более сложных запросов, когда ожидаемое качество важнее скорости и цены.

Это сравнение относится к одному короткому арифметическому запросу: результаты для сложных задач, длинных текстов или креативных сценариев могут отличаться.

## День 6 — первый агент

В приложении появился отдельный объект агента. Агент инкапсулирует свою конфигурацию модели, system prompt, историю сообщений и метаданные последнего вызова. Когда пользователь отправляет сообщение, выбранный агент сам собирает запрос к LLM, вызывает DeepSeek или Z.AI API, сохраняет ответ в своей истории и возвращает результат в общий интерфейс.

### Как работает агент

1. Пользователь выбирает агента и отправляет ему запрос в общем интерфейсе.
2. Выбранный `Agent` принимает текст, добавляет его только в свою историю и формирует запрос к LLM с собственной моделью, system prompt и настройками ответа.
3. Агент передаёт готовый запрос общему API-клиенту, который отправляет его в DeepSeek или Z.AI.
4. Агент получает ответ, сохраняет его вместе с метаданными запроса и возвращает обновлённое состояние интерфейсу.

Таким образом, агент — не просто один вызов API. Это отдельная сущность, которая владеет своим состоянием и инкапсулирует полный цикл «запрос пользователя → вызов LLM → ответ → сохранение результата». HTTP-обработчик лишь находит нужного агента и передаёт ему сообщение; он не формирует payload модели и не меняет историю напрямую.

### Почему это соответствует критериям

Приложение запускается одним экземпляром сервера. Внутри него `AgentRegistry` хранит N экземпляров `Agent`; создание нового агента не поднимает отдельный сервер, процесс или интерфейс и не создаёт новый экземпляр приложения. Каждый агент имеет независимые историю, конфигурацию и метаданные, поэтому после создания настройки можно изменить для каждого отдельно: например, назначить разные модели и system prompt. Общий для всего приложения адаптер API передаётся всем агентам как зависимость.

Приложение запускается одним сервером. Внутри него реестр хранит N независимых агентов, поэтому для каждого агента не нужен отдельный процесс, сервер или браузерная вкладка. У агентов не смешиваются сообщения, настройки, модель и метаданные.

В левой панели доступны:

- «Создать агента» — добавляет одного агента с настройками по умолчанию;
- список и счётчик агентов — позволяют выбрать, с кем вести диалог.

Каждый новый агент называется «Агент N» и получает одинаковую конфигурацию по умолчанию, включая default system prompt. Создание агента не отправляет запрос в LLM и не расходует API-лимиты: объект появляется в памяти текущего сервера. Запрос к модели выполняется лишь после отправки сообщения выбранному агенту.

В рамках Дня 6 агенты и их история существовали только до перезапуска. День 7 добавляет постоянное хранение этого состояния.

## День 7 — сохранение контекста

Реестр агентов автоматически сохраняет историю диалога, настройки и метаданные последнего запроса в `data/agents.json`. API-ключи в этот файл не попадают. Запись выполняется атомарно: при остановке приложения файл не должен оказаться частично записанным.

При следующем запуске приложение восстанавливает всех агентов, их настройки и историю. Если файл отсутствует или повреждён, сервер безопасно запускается с новым «Агентом 1».

### Проверка перезапуска

1. Запустите приложение командой `python3 main.py`.
2. Отправьте агенту сообщение, например: «Меня зовут Маша».
3. Остановите приложение сочетанием `Ctrl+C` и снова выполните `python3 main.py`.
4. Отправьте «Как меня зовут?». В новом запросе агенту уже передаётся первая реплика и его предыдущий ответ, поэтому он продолжает этот же диалог.

## День 8 — метрики токенов и контекста

В правой панели каждого агента появился раздел «Токены и стоимость»: размер нового сообщения и истории, токены запроса и ответа, накопленные токены и стоимость, а также таблица расходов по шагам. Фактический `usage` API имеет приоритет; при его отсутствии показана локальная оценка.

«Учебный лимит контекста» позволяет быстро показать предупреждение и отказ без изменения реального лимита модели. По умолчанию переполненный запрос блокируется и история не меняется. Флажок «Отправлять запрос при переполнении — для демонстрации» отправляет временный payload провайдеру: если он отклонит запрос, его текст ошибки будет виден в чате, но не попадёт в будущий контекст.

### Что считает код

Перед каждым запросом агент оценивает размер нового сообщения, истории и полного payload — system prompt, историю и служебные поля запроса. После успешного ответа он сохраняет отдельную строку расходов: входные, выходные и суммарные токены, стоимость шага, накопленные значения, размер истории до и после сообщения и источник чисел.

Для платных моделей стоимость каждого шага рассчитывается по формуле:

`(входные токены × цена входа + выходные токены × цена выхода) / 1 000 000`.

График и таблица расходов позволяют увидеть рост входных токенов от сообщения к сообщению.
Учебный лимит нужен только для опыта. Если он не задан, агент использует реальный лимит выбранной модели: 1 млн токенов для `deepseek-v4-flash` и `deepseek-v4-pro`, 200 тыс. для `glm-4.7-flash`. При проверке учитывается не только текущий payload, но и резерв на ответ: `оценка входа + запрошенный максимум ответа ≤ активный лимит`.

### Сравнение диалогов

| Сценарий | Что происходит с токенами и стоимостью                                                                                                                                                                                                                                            | Поведение агента |
| --- |-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------| --- |
| **Короткий диалог** | Небольшой system prompt и одно-два сообщения дают малый входной payload. Стоимость одного шага складывается из входа и ответа; накопленный итог растёт почти линейно.                                                                                                             | Агент передаёт модели короткую историю, быстро отвечает и сохраняет запись в таблице расходов. |
| **Длинный диалог** | На каждом новом ходе в payload повторно попадает вся сохранённая история. Поэтому входные токены шага растут вместе с историей, а накопленная стоимость увеличивается быстрее, чем число сообщений. Длинные ответы дополнительно увеличивают и историю, и будущие входные токены. | Агент продолжает диалог, пока оценка входа вместе с резервом ответа помещается в активный контекст. |
| **Диалог сверх лимита** | Попытка не добавляется в историю и не создаёт строку успешных расходов. Накопленные токены и стоимость остаются на уровне предыдущего успешного хода.                                                                                                                             | По умолчанию агент останавливает запрос локально. При включённой демонстрации он отправляет временный payload провайдеру, показывает его ошибку и не сохраняет пробную реплику при неуспехе. |

Главный вывод: стоимость диалога зависит не только от длины нового сообщения. В многоходовом чате каждый следующий запрос оплачивает и обрабатывает ранее накопленную историю, поэтому особенно заметен рост входных токенов. Таблица расходов показывает стоимость конкретного хода, а сводка — сумму всех успешных ходов агента.


### Выводы

- Короткий диалог экономичен, потому что история почти не влияет на размер входа.
- Длинный диалог требует контроля не только общего числа сообщений, но payload: именно история делает следующие запросы дороже.

## День 9 — сжатие истории и сравнение

Для длинных диалогов в настройках агента доступен флажок «Сжимать старую историю диалога». Он включён по умолчанию и работает независимо для каждого агента.

### Как устроено сжатие

Агент сохраняет последние 10 сообщений как сырое окно контекста. Более ранняя часть переписки заменяется отдельной краткой сводкой: в ней сохраняются факты, решения, ограничения, предпочтения и открытые вопросы. Новые устаревшие сообщения сначала копятся пакетом из 10, и только затем одним вызовом добавляются в summary. Между обновлениями в запрос временно попадает до 20 исходных сообщений: 10 свежих и до 10 ожидающих сжатия. Это сокращает число дорогих вызовов summary до одного на пять ходов диалога. Сводка, число сжатых сообщений и её накопленное потребление сохраняются вместе с агентом, поэтому после перезапуска сжатый контекст не теряется.

Создание или обновление сводки — это отдельный запрос к модели и отдельная оплата. Поэтому в интерфейсе показаны два результата: «Экономия от сжатия» и «Чистая экономия с учётом summary».

### Как читать показатели

«Полная история» показывает расчётный размер запроса, если бы в него отправили всю переписку. «Сжатая история» показывает размер запроса после замены старых сообщений сводкой. Это расчёт приложения, а не два отдельных запроса к API.

«Экономия от сжатия» — это разница между размером запроса с полной историей и размером запроса со сжатой историей. Она показывает, сколько удалось не отправлять в основном запросе. «Чистая экономия с учётом summary» дополнительно вычитает токены и деньги, потраченные на создание сводки. Поэтому сначала чистая экономия может быть отрицательной: сводка уже создана, а экономия от её использования ещё мала.

### Сравнение качества ответов и расхода токенов на тестовом прогоне от 13 сентября 2026

На тестовом прогоне с 38 сообщениями сжатие уменьшило размер запроса, но на момент замера ещё не окупило создание summary в деньгах.

| Показатель | Значение |
| --- | ---: |
| Оценка полного запроса на последнем ходе | 6 107 токенов |
| Оценка сжатого запроса на последнем ходе | 3 158 токенов |
| Уменьшение оценочного входа | 2 949 токенов, или 48,3% |
| Входные токены последнего вызова, показанные интерфейсом | 4 095 |
| Токены последнего ответа | 707 |
| Сжато сообщений | 20 |
| Размер текущего summary | 628 токенов |
| Экономия от сжатия, накоплено | 18 356 токенов · $0,004038 |
| Стоимость создания и обновления summary, накоплено | 11 453 токена · $0,005152 |
| Чистая экономия, накоплено | 6 903 токена · −$0,001113 по интерфейсу |

**Почему токены сэкономлены, а деньги — ещё нет.** «Экономия от сжатия» считает только то, что не пришлось отправлять в основном запросе. Но чтобы получить сводку, модель отдельно прочитала старую переписку и написала summary. За это тоже списываются токены и деньги. В настройках приложения выходные токены стоят дороже входных, поэтому создание summary могло обойтись дороже, чем экономия на уменьшении основного запроса.

По показанным суммам средняя стоимость миллиона сэкономленных токенов составляет примерно $0,22, а миллиона токенов summary — $0,45. Поэтому меньший расход токенов на summary может стоить больше, чем большее число сэкономленных входных токенов. Точную стоимость вызовов summary следует проверять по раздельным входным и выходным токенам.

Чистая экономия токенов: `18 356 − 11 453 = 6 903`. Денежный результат по округлённым значениям: `$0,004038 − $0,005152 = −$0,001114`. Расхождение с интерфейсом на $0,000001 может объясняться округлением. При экономии последнего хода $0,000649 затраты окупились бы примерно за два следующих хода, если экономия сохранится и новое summary не потребуется.

Качество ответов при этом стало менее точным – в суммаризированной истории не было найдено специально спрятанное кодовое слово.

## День 10 — стратегии контекста

Добавлены три стратегии управления контекстом; Summary из дня 9 сохранён как отдельный режим. Стратегия выбирается для каждого агента, настройки и состояние сохраняются после перезапуска.

| Стратегия | Суть |
| --- | --- |
| Sliding Window | Передаёт последние N сообщений; более ранние удаляются. N считает отдельные сообщения, а не пары. |
| Facts | Дополняет окно сообщений словарём фактов, который обновляется отдельным запросом перед каждым ответом. Факты и расход памяти видны в интерфейсе. |
| Branching | Хранит независимые варианты диалога от общей сохранённой точки — checkpoint. Модель получает полную историю активной ветки. |
| Summary | Заменяет старую переписку краткой сводкой, сохраняя свежие сообщения. |

### Краткий вывод

На сценарии «Соседская полка» проведены три прогона по 15 запросов для Sliding Window, Facts и Branching. Facts и Branching сохранили все 12 полей ТЗ и не смешали варианты A и B; Sliding Window с N = 6 сохранил только 2–3 поля. Facts и Branching сохранили требования, но в плане запуска часто ограничивались общим пунктом «провести тестирование», не указывая проверку запрета двойного бронирования.

Средний расход за сценарий: Sliding Window — 13,1 тыс. токенов, Branching — 16,6 тыс., Facts — 33,4 тыс. с учётом обновления памяти. В этом тесте Branching дал лучшее сочетание сохранности требований и расхода токенов, но потребовал шести дополнительных операций с ветками. Facts удобен для просмотра памяти, однако её обновление после каждого запроса оказалось дороже. Экономия Sliding Window сопровождалась потерей важных деталей.

Развёрнутые выводы по качеству, стабильности, токенам и удобству, таблицы трёх прогонов и описание технических сбоев находятся в [тест-кейсе и отчёте по дню 10](../docs/day-10/universal-context-test-case.md#краткие-выводы-по-критериям). Исходные ответы и метрики сохранены в [docs/day-10/results](../docs/day-10/results/).

## День 11 — модель памяти агента

В приложении используется явная модель памяти с тремя слоями. Слои хранятся отдельно, имеют разное время жизни и добавляются только по явному действию пользователя. Интерфейс в разделе «Память» предназначен для просмотра: изменять рабочую и долговременную память нужно командами в поле сообщения.

### Слои и срок жизни

| Слой | Содержимое | Область действия | Когда очищается |
| --- | --- | --- | --- |
| Краткосрочная память | Текущий диалог: сообщения пользователя и ответы модели | Только выбранный агент и его активная ветка | Зависит от выбранной стратегии контекста: Sliding Window отбрасывает старые сообщения, Summary заменяет их сводкой, Branching хранит их в ветках. При удалении агента его диалог также удаляется. |
| Рабочая память | Обычный массив строк `working` для текущей задачи | Только тот агент, которому отправлена команда | Только явно: `/clear-working` или `/clear-memory` для выбранного агента. Переключение агента, новая задача и перезапуск сервера её не очищают. |
| Долговременная память | Общий массив строк `longTerm`: профиль, предпочтения, важные знания или решения без внутренних категорий | Все агенты приложения, включая новых | Только явно: `/clear-long` или `/clear-memory`. Перезапуск и создание/удаление агента её не очищают. |

Рабочая и долговременная память хранят не словари, а последовательности текстовых элементов. Поэтому в них нет полей `task`, `data`, `profile`, `decisions` и `knowledge`: например, фраза «Срок отпуска — 14–20 октября» сохраняется одной строкой, без ключа.

Для защиты от случайно слишком большого контекста в рабочей памяти допускается до 24 элементов, в долговременной — до 52. Длина одного элемента — до 500 символов. При превышении лимита команда возвращает локальную ошибку и ничего не меняет.

### Команды памяти

Команды вводятся в то же поле, что и обычные сообщения. Сервер сначала распознаёт команду, изменяет память и возвращает служебный статус. В этом случае вызова DeepSeek/Z.AI нет, команда не добавляется в историю диалога и не расходует токены API.

| Команда | Действие | Пример |
| --- | --- | --- |
| `/working текст` | Добавляет `текст` в рабочую память выбранного агента | `/working Делаю дизайн лендинга` |
| `/long текст` | Добавляет `текст` в общую долговременную память и сразу синхронизирует её у всех агентов | `/long Меня зовут Диана` |
| `/clear-working` | Очищает рабочую память выбранного агента | `/clear-working` |
| `/clear-long` | Очищает общую долговременную память у всех агентов | `/clear-long` |
| `/clear-memory` | Очищает рабочую память выбранного агента и общую долговременную память | `/clear-memory` |

После `/working` и `/long` обязателен непустой текст. Команды очистки не принимают дополнительных аргументов. Старые адресные команды (`/profile`, `/decision`, `/knowledge`, `/working-data`) больше не являются командами памяти; используйте вместо них `/working` или `/long`.

Для новой независимой задачи обычно достаточно выполнить `/clear-working`, затем добавить новую задачу через `/working ...`. Если нужно начать полностью «с чистого листа», используйте `/clear-memory`. Новый агент создаётся с пустой рабочей памятью, но получает текущую общую долговременную память.

### Что получает модель

Перед каждым обычным сообщением агент собирает один текстовый контекст. Сначала в нём идут элементы рабочей памяти активного агента, затем элементы общей долговременной памяти, в порядке их добавления. Контекст передаётся одним system-сообщением как обычный текст, а не как JSON. В него не попадают ключи, имена категорий и техническая структура хранилища.

Краткосрочная память добавляется отдельно — как история сообщений в соответствии с выбранной стратегией контекста. Так модель может опираться и на текущую переписку, и на явно сохранённые сведения. Если обе явные памяти пусты, дополнительный контекст не добавляется: модель получает только базовый system prompt и историю диалога.

Например, после команд

```text
/working Делаю дизайн лендинга
/long Предпочитает краткий тон
```

в модели будет контекст, содержащий две строки: «Делаю дизайн лендинга» и «Предпочитает краткий тон». Сама команда и её технические поля в prompt не отправляются.

### Хранение и восстановление

Все слои входят в состояние приложения, которое `AgentRegistry` атомарно сохраняет в `data/agents.json`. В этом файле нет API-ключей. Рабочая память записывается внутри состояния каждого агента; долговременная — также в отдельном общем поле состояния, поэтому после перезапуска она остаётся одинаковой у всех агентов.

При старте сервер восстанавливает состояние из файла. Если файл был создан прежней версией приложения, где рабочая память содержала `task` и `data`, а долговременная была разделена на `profile`, `decisions` и `knowledge`, данные автоматически преобразуются в плоские массивы значений. Ключи и названия категорий в новую память не переносятся, а сами значения сохраняются. Если файл отсутствует или повреждён, сервер создаёт нового агента с пустыми рабочей и долговременной памятью.
