# Локальный веб-чат DeepSeek

Приложение запускает локальный интерфейс для общения с DeepSeek. Внутри одного сервера работают независимые агенты со своей перепиской, настройками и данными последнего запроса к API.

## Настройки и запуск

### 1. Получите API-ключ

Создайте ключ в [DeepSeek Platform](https://platform.deepseek.com/api_keys). Никому не отправляйте ключ и не записывайте его в исходный код.

### 2. Подготовьте окружение

Требуется Python 3.10 или новее.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 3. Добавьте ключ

В macOS или Linux:

```bash
export DEEPSEEK_API_KEY="ваш_ключ"
```

Для `glm-4.7-flash` добавьте также ключ Z.AI:

```bash
export ZAI_API_KEY="ваш_ключ_z_ai"
```

### 4. Запустите приложение

```bash
python3 main.py
```

Откройте в браузере [http://127.0.0.1:8000](http://127.0.0.1:8000).

Введите сообщение и нажмите «Отправить». Слева можно создавать и переключать агентов. Справа отображаются user prompt, system prompt и JSON запроса, отправленного в DeepSeek. История и настройки агентов сохраняются между запусками приложения.

## День 2 — Настройки ответа

В правой панели над метаданными находятся настройки активной сессии:

- **System prompt** — базовая инструкция для модели.
- **Формат ответа** — обычный текст или JSON. В режиме JSON приложение передаёт в DeepSeek `response_format={"type":"json_object"}`; текстовый system prompt при этом не меняется.
- **Максимум токенов** — необязательный лимит, который передаётся как `max_tokens`.
- **Стоп-последовательность** — необязательная строка, которая передаётся как `stop`.

Все настройки сохраняются автоматически в текущей сессии: формат — сразу, а текстовые поля — через короткую паузу после ввода. Если сразу отправить сообщение, приложение сначала сохранит текущие настройки, затем отправит запрос. Поле сообщения закреплено внизу центральной панели, а прокручивается только история диалога.

Чтобы выполнить задание второго дня, отправьте запрос с пустыми настройками, затем задайте формат, лимит или стоп-последовательность и повторите тот же запрос. В разделе «Метаданные» можно сравнить фактически отправленные JSON-запросы и полученные ответы.

## День 3 — Сравнение способов рассуждения

В режиме «День 3» доступны 2 встроенные задачи: «Три сервера» – логическая и «Выбор канала» –аналитическая. Выберите задачу из списка и нажмите «Запустить 4 стратегии». Для каждой из них DeepSeek отвечает напрямую, пошагово, через созданный им промпт и как группа экспертов; затем отдельный вызов модели качественно сравнивает ответы с эталоном и критериями именно этой задачи.

### Способы рассуждения

В эксперименте одна и та же задача передаётся четырьмя способами. Результаты не используют историю и настройки обычного чата, поэтому их удобно сравнивать между собой.

- **Напрямую.** Модель получает только условие задачи и инструкцию дать краткий, проверяемый ответ. Этот способ показывает базовый результат без дополнительных подсказок о ходе решения.
- **Пошагово.** Модель сначала фиксирует исходные данные и цель, затем оформляет решение в пронумерованных шагах с промежуточными результатами и выполняет самопроверку. Подходит для задач, где важно увидеть и проверить логику или вычисления.
- **Свой промпт.** Это два последовательных вызова. Сначала модель в роли инженера промптов создаёт инструкцию для решения конкретной задачи: выбирает роль, метод, порядок шагов, типичные ошибки и способ проверки. Затем другая инструкция просит модель решить задачу по созданному промпту. Так можно увидеть, как качество постановки задачи влияет на ответ.
- **Группа экспертов.** Три роли решают задачу независимо: аналитик разбирает условия и допущения, инженер предлагает процедуру или расчёт, критик ищет ловушки и проверяет граничные случаи. Такой подход полезен, когда нужно сверить решение с разных точек зрения.

После четырёх стратегий модель-модератор сопоставляет их ответы с эталонным решением и критериями выбранной задачи. В карточках результатов можно раскрыть фактические системные и пользовательские промпты, а для «Своего промпта» — также созданную инструкцию. Результаты каждой запущенной задачи сохраняются до перезагрузки страницы и снова показываются при возврате к ней.

### Выводы

Ответы по существу не отличаются: все четыре способа пришли к верным итогам.

Наиболее точного «победителя» здесь нет — точность одинакова. Но наиболее полными и проверяемыми выглядят «Пошагово» и «Группа экспертов»: они показывают ход расчёта или проверки, а не только итог. В первом задании они дополнительно указали общее число регистраций после прироста показов; это уточнение, а не другое решение.

- Прямой/краткий способ полезен для простых задач, когда нужен быстрый итог.
- Пошаговый способ — для вычислений и логики, где человеку важно проверить каждый переход и избежать ошибок.
- Группа экспертов — для неоднозначных задач: разные роли могут независимо проверить решение, найти слабые места и предложить более ясное обоснование.
- Свой промпт — полезен, когда вводных данных недостаточно или неочевиден способ решения. На практике часто пригождается.

## День 4 — Температура

В разделе «Настройки ответа» добавлен ползунок для выбора температуры.

### Тестирование

Запросы отправлялись с тремя значениями температуры:

- `temperature = 0`
- `temperature = 0.7`
- `temperature = 1.2`

Влияние температуры проверили на нескольких задачах, включая:

- математическую — составить команды из нескольких учеников по заданным правилам;
- креативную — придумать пять необычных названий напитка для кофейни.

### Выводы

В математической задаче влияние температуры заметить сложнее. Однако при повторных запусках с `temperature = 1.2` ходы решения различались сильнее, чем при других значениях.

В креативной задаче разница заметнее:

- при `temperature = 0` модель предлагала двухсловные названия, похожие на привычные словосочетания: например, «Северное сияние» и «Утро в Тоскане»; к ним добавлялось описание напитка;
- при `temperature = 1.2` появлялись и более необычные трёхсловные варианты: например, «Бархатный подземный переход» и «Туманный альпинист».


#### `temperature = 0`

Подходит для задач, где важны повторяемость, строгая структура и минимальная вариативность: вычислений, проверки условий, кода, извлечения данных и отчётов по шаблону. В опыте оба ответа были почти одинаково организованы и дали одинаковое корректное решение.

#### `temperature = 0.7`

Хороший универсальный режим для объяснений, обучения, анализа и рабочих текстов. Ответ остаётся точным, но модель может выбрать другой корректный способ рассуждения и объяснить его более естественно.

#### `temperature = 1.2`

Лучше использовать для генерации идей, вариантов, гипотез, сценариев, названий и творческих текстов. В математической задаче ответы тоже остались правильными, но заметнее менялись подача и детализация. Для строгих вычислений высокая температура не даёт преимущества — результат всё равно нужно проверять.

### Итог

- Для точных и повторяемых задач — `0`.
- Для большинства повседневных запросов и понятных объяснений — `0.7`.
- Для поиска нестандартных вариантов и творчества — `1.2`.

## День 5 — сравнение моделей

В настройках каждого чата доступен выбор модели:

- слабая — `deepseek-v4-flash`;
- средняя — `glm-4.7-flash`;
- сильная — `deepseek-v4-pro`.

Выбор, а также метаданные последнего запроса, принадлежат конкретному чату. При переходе между чатами правая панель показывает именно его модель, время ответа, общее число токенов и стоимость. Flash и Pro идут через DeepSeek API с `DEEPSEEK_API_KEY`, а GLM — через Z.AI с `ZAI_API_KEY`.

Для платных моделей стоимость в USD считается по формуле:

`prompt_tokens × цена входа + completion_tokens × цена выхода`.

### Тарифы и расчет стоимости

Цены указаны в USD за 1 млн токенов. Для DeepSeek используются off-peak тарифы для входных токенов без cache hit; приложение не получает от API разбиение входных токенов по кэшу.

| Модель | Провайдер | Входные токены | Выходные токены |
| --- | --- | ---: | ---: |
| `deepseek-v4-flash` | DeepSeek | $0,22 | $0,66 |
| `glm-4.7-flash` | Z.AI | Бесплатно | Бесплатно |
| `deepseek-v4-pro` | DeepSeek | $0,66 | $1,98 |

Для платных моделей приложение считает стоимость так:

`стоимость (USD) = (prompt_tokens × цена входа + completion_tokens × цена выхода) / 1 000 000`.

Для `glm-4.7-flash` стоимость всегда показывается как «Бесплатно». Тарифы DeepSeek приведены по [официальной таблице цен](https://api-docs.deepseek.com/quick_start/pricing/), а бесплатный тариф GLM — по [таблице Z.AI](https://docs.z.ai/guides/overview/pricing).

### Результаты сравнения

Для сравнения все модели получили один и тот же запрос при одинаковом system prompt: «У Маши есть 3 яблока, а у Пети — на 2 яблока больше. Сколько всего яблок у мальчиков?»

| Модель | Время ответа | Всего токенов | Стоимость запроса |
| --- | ---: | ---: | ---: |
| `deepseek-v4-flash` | 4,06 с | 654 | $0,000363 |
| `glm-4.7-flash` | 5,23 с | 490 | Бесплатно |
| `deepseek-v4-pro` | 18,46 с | 1367 | $0,002499 |

### Выводы

- `deepseek-v4-flash` в этом запуске ответила быстрее всех. Это хороший вариант, когда важна минимальная задержка и допустима небольшая стоимость запроса.
- `glm-4.7-flash` отстала от Flash всего на 1,17 с, использовала меньше всего токенов и не требует оплаты. Для учебных, тестовых и повседневных задач это наиболее выгодный выбор.
- `deepseek-v4-pro` сформировала самый длинный ответ, но оказалась примерно в 4,5 раза медленнее Flash и почти в 7 раз дороже. Её стоит выбирать для более сложных запросов, когда ожидаемое качество важнее скорости и цены.

Это сравнение относится к одному короткому арифметическому запросу: результаты для сложных задач, длинных текстов или креативных сценариев могут отличаться.

## День 6 — первый агент

В приложении появился отдельный объект агента. Агент инкапсулирует свою конфигурацию модели, system prompt, историю сообщений и метаданные последнего вызова. Когда пользователь отправляет сообщение, выбранный агент сам собирает запрос к LLM, вызывает DeepSeek или Z.AI API, сохраняет ответ в своей истории и возвращает результат в общий интерфейс.

### Как работает агент

1. Пользователь выбирает агента и отправляет ему запрос в общем интерфейсе.
2. Выбранный `Agent` принимает текст, добавляет его только в свою историю и формирует запрос к LLM с собственной моделью, system prompt и настройками ответа.
3. Агент передаёт готовый запрос общему API-клиенту, который отправляет его в DeepSeek или Z.AI.
4. Агент получает ответ, сохраняет его вместе с метаданными запроса и возвращает обновлённое состояние интерфейсу.

Таким образом, агент — не просто один вызов API. Это отдельная сущность, которая владеет своим состоянием и инкапсулирует полный цикл «запрос пользователя → вызов LLM → ответ → сохранение результата». HTTP-обработчик лишь находит нужного агента и передаёт ему сообщение; он не формирует payload модели и не меняет историю напрямую.

### Почему это соответствует критериям

Приложение запускается одним экземпляром сервера. Внутри него `AgentRegistry` хранит N экземпляров `Agent`; создание нового агента не поднимает отдельный сервер, процесс или интерфейс и не создаёт новый экземпляр приложения. Каждый агент имеет независимые историю, конфигурацию и метаданные, поэтому после создания настройки можно изменить для каждого отдельно: например, назначить разные модели и system prompt. Общий для всего приложения адаптер API передаётся всем агентам как зависимость.

Приложение запускается одним сервером. Внутри него реестр хранит N независимых агентов, поэтому для каждого агента не нужен отдельный процесс, сервер или браузерная вкладка. У агентов не смешиваются сообщения, настройки, модель и метаданные.

В левой панели доступны:

- «Создать агента» — добавляет одного агента с настройками по умолчанию;
- список и счётчик агентов — позволяют выбрать, с кем вести диалог.

Каждый новый агент называется «Агент N» и получает одинаковую конфигурацию по умолчанию, включая default system prompt. Создание агента не отправляет запрос в LLM и не расходует API-лимиты: объект появляется в памяти текущего сервера. Запрос к модели выполняется лишь после отправки сообщения выбранному агенту.

В рамках Дня 6 агенты и их история существовали только до перезапуска. День 7 добавляет постоянное хранение этого состояния.

## День 7 — сохранение контекста

Реестр агентов автоматически сохраняет историю диалога, настройки и метаданные последнего запроса в `data/agents.json`. API-ключи в этот файл не попадают. Запись выполняется атомарно: при остановке приложения файл не должен оказаться частично записанным.

При следующем запуске приложение восстанавливает всех агентов, их настройки и историю. Если файл отсутствует или повреждён, сервер безопасно запускается с новым «Агентом 1».

### Проверка перезапуска

1. Запустите приложение командой `python3 main.py`.
2. Отправьте агенту сообщение, например: «Меня зовут Маша».
3. Остановите приложение сочетанием `Ctrl+C` и снова выполните `python3 main.py`.
4. Отправьте «Как меня зовут?». В новом запросе агенту уже передаётся первая реплика и его предыдущий ответ, поэтому он продолжает этот же диалог.

## День 8 — метрики токенов и контекста

В правой панели каждого агента появился раздел «Токены и стоимость»: размер нового сообщения и истории, токены запроса и ответа, накопленные токены и стоимость, а также таблица расходов по шагам. Фактический `usage` API имеет приоритет; при его отсутствии показана локальная оценка.

«Учебный лимит контекста» позволяет быстро показать предупреждение и отказ без изменения реального лимита модели. По умолчанию переполненный запрос блокируется и история не меняется. Флажок «Отправлять запрос при переполнении — для демонстрации» отправляет временный payload провайдеру: если он отклонит запрос, его текст ошибки будет виден в чате, но не попадёт в будущий контекст.

### Что считает код

Перед каждым запросом агент оценивает размер нового сообщения, истории и полного payload — system prompt, историю и служебные поля запроса. После успешного ответа он сохраняет отдельную строку расходов: входные, выходные и суммарные токены, стоимость шага, накопленные значения, размер истории до и после сообщения и источник чисел.

Для платных моделей стоимость каждого шага рассчитывается по формуле:

`(входные токены × цена входа + выходные токены × цена выхода) / 1 000 000`.

График и таблица расходов позволяют увидеть рост входных токенов от сообщения к сообщению.
Учебный лимит нужен только для опыта. Если он не задан, агент использует реальный лимит выбранной модели: 1 млн токенов для `deepseek-v4-flash` и `deepseek-v4-pro`, 200 тыс. для `glm-4.7-flash`. При проверке учитывается не только текущий payload, но и резерв на ответ: `оценка входа + запрошенный максимум ответа ≤ активный лимит`.

### Сравнение диалогов

| Сценарий | Что происходит с токенами и стоимостью                                                                                                                                                                                                                                            | Поведение агента |
| --- |-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------| --- |
| **Короткий диалог** | Небольшой system prompt и одно-два сообщения дают малый входной payload. Стоимость одного шага складывается из входа и ответа; накопленный итог растёт почти линейно.                                                                                                             | Агент передаёт модели короткую историю, быстро отвечает и сохраняет запись в таблице расходов. |
| **Длинный диалог** | На каждом новом ходе в payload повторно попадает вся сохранённая история. Поэтому входные токены шага растут вместе с историей, а накопленная стоимость увеличивается быстрее, чем число сообщений. Длинные ответы дополнительно увеличивают и историю, и будущие входные токены. | Агент продолжает диалог, пока оценка входа вместе с резервом ответа помещается в активный контекст. |
| **Диалог сверх лимита** | Попытка не добавляется в историю и не создаёт строку успешных расходов. Накопленные токены и стоимость остаются на уровне предыдущего успешного хода.                                                                                                                             | По умолчанию агент останавливает запрос локально. При включённой демонстрации он отправляет временный payload провайдеру, показывает его ошибку и не сохраняет пробную реплику при неуспехе. |

Главный вывод: стоимость диалога зависит не только от длины нового сообщения. В многоходовом чате каждый следующий запрос оплачивает и обрабатывает ранее накопленную историю, поэтому особенно заметен рост входных токенов. Таблица расходов показывает стоимость конкретного хода, а сводка — сумму всех успешных ходов агента.


### Выводы

- Короткий диалог экономичен, потому что история почти не влияет на размер входа.
- Длинный диалог требует контроля не только общего числа сообщений, но payload: именно история делает следующие запросы дороже.

## День 9 — сжатие истории и сравнение

Для длинных диалогов в настройках агента доступен флажок «Сжимать старую историю диалога». Он включён по умолчанию и работает независимо для каждого агента.

### Как устроено сжатие

Агент сохраняет последние 10 сообщений как сырое окно контекста. Более ранняя часть переписки заменяется отдельной краткой сводкой: в ней сохраняются факты, решения, ограничения, предпочтения и открытые вопросы. Новые устаревшие сообщения сначала копятся пакетом из 10, и только затем одним вызовом добавляются в summary. Между обновлениями в запрос временно попадает до 20 исходных сообщений: 10 свежих и до 10 ожидающих сжатия. Это сокращает число дорогих вызовов summary до одного на пять ходов диалога. Сводка, число сжатых сообщений и её накопленное потребление сохраняются вместе с агентом, поэтому после перезапуска сжатый контекст не теряется.

Создание или обновление сводки — это отдельный запрос к модели и отдельная оплата. Поэтому в интерфейсе показаны два результата: «Экономия от сжатия» и «Чистая экономия с учётом summary».

### Как читать показатели

«Полная история» показывает расчётный размер запроса, если бы в него отправили всю переписку. «Сжатая история» показывает размер запроса после замены старых сообщений сводкой. Это расчёт приложения, а не два отдельных запроса к API.

«Экономия от сжатия» — это разница между размером запроса с полной историей и размером запроса со сжатой историей. Она показывает, сколько удалось не отправлять в основном запросе. «Чистая экономия с учётом summary» дополнительно вычитает токены и деньги, потраченные на создание сводки. Поэтому сначала чистая экономия может быть отрицательной: сводка уже создана, а экономия от её использования ещё мала.

### Сравнение качества ответов и расхода токенов на тестовом прогоне от 13 сентября 2026

На тестовом прогоне с 38 сообщениями сжатие уменьшило размер запроса, но на момент замера ещё не окупило создание summary в деньгах.

| Показатель | Значение |
| --- | ---: |
| Оценка полного запроса на последнем ходе | 6 107 токенов |
| Оценка сжатого запроса на последнем ходе | 3 158 токенов |
| Уменьшение оценочного входа | 2 949 токенов, или 48,3% |
| Входные токены последнего вызова, показанные интерфейсом | 4 095 |
| Токены последнего ответа | 707 |
| Сжато сообщений | 20 |
| Размер текущего summary | 628 токенов |
| Экономия от сжатия, накоплено | 18 356 токенов · $0,004038 |
| Стоимость создания и обновления summary, накоплено | 11 453 токена · $0,005152 |
| Чистая экономия, накоплено | 6 903 токена · −$0,001113 по интерфейсу |

**Почему токены сэкономлены, а деньги — ещё нет.** «Экономия от сжатия» считает только то, что не пришлось отправлять в основном запросе. Но чтобы получить сводку, модель отдельно прочитала старую переписку и написала summary. За это тоже списываются токены и деньги. В настройках приложения выходные токены стоят дороже входных, поэтому создание summary могло обойтись дороже, чем экономия на уменьшении основного запроса.

По показанным суммам средняя стоимость миллиона сэкономленных токенов составляет примерно $0,22, а миллиона токенов summary — $0,45. Поэтому меньший расход токенов на summary может стоить больше, чем большее число сэкономленных входных токенов. Точную стоимость вызовов summary следует проверять по раздельным входным и выходным токенам.

Чистая экономия токенов: `18 356 − 11 453 = 6 903`. Денежный результат по округлённым значениям: `$0,004038 − $0,005152 = −$0,001114`. Расхождение с интерфейсом на $0,000001 может объясняться округлением. При экономии последнего хода $0,000649 затраты окупились бы примерно за два следующих хода, если экономия сохранится и новое summary не потребуется.

Качество ответов при этом стало менее точным – в суммаризированной истории не было найдено специально спрятанное кодовое слово.

## День 10 — стратегии контекста

Добавлены три стратегии управления контекстом; Summary из дня 9 сохранён как отдельный режим. Стратегия выбирается для каждого агента, настройки и состояние сохраняются после перезапуска.

| Стратегия | Суть |
| --- | --- |
| Sliding Window | Передаёт последние N сообщений; более ранние удаляются. N считает отдельные сообщения, а не пары. |
| Facts | Дополняет окно сообщений словарём фактов, который обновляется отдельным запросом перед каждым ответом. Факты и расход памяти видны в интерфейсе. |
| Branching | Хранит независимые варианты диалога от общей сохранённой точки — checkpoint. Модель получает полную историю активной ветки. |
| Summary | Заменяет старую переписку краткой сводкой, сохраняя свежие сообщения. |

### Краткий вывод

На сценарии «Соседская полка» проведены три прогона по 15 запросов для Sliding Window, Facts и Branching. Facts и Branching сохранили все 12 полей ТЗ и не смешали варианты A и B; Sliding Window с N = 6 сохранил только 2–3 поля. Facts и Branching сохранили требования, но в плане запуска часто ограничивались общим пунктом «провести тестирование», не указывая проверку запрета двойного бронирования.

Средний расход за сценарий: Sliding Window — 13,1 тыс. токенов, Branching — 16,6 тыс., Facts — 33,4 тыс. с учётом обновления памяти. В этом тесте Branching дал лучшее сочетание сохранности требований и расхода токенов, но потребовал шести дополнительных операций с ветками. Facts удобен для просмотра памяти, однако её обновление после каждого запроса оказалось дороже. Экономия Sliding Window сопровождалась потерей важных деталей.

Развёрнутые выводы по качеству, стабильности, токенам и удобству, таблицы трёх прогонов и описание технических сбоев находятся в [тест-кейсе и отчёте по дню 10](../docs/day-10/universal-context-test-case.md#краткие-выводы-по-критериям). Исходные ответы и метрики сохранены в [docs/day-10/results](../docs/day-10/results/).

## День 11 — модель памяти агента

В приложении используется явная модель памяти с тремя слоями. Слои хранятся отдельно, имеют разное время жизни и добавляются только по явному действию пользователя. Интерфейс в разделе «Память» предназначен для просмотра: изменять рабочую и долговременную память нужно командами в поле сообщения.

### Слои и срок жизни

| Слой | Содержимое | Область действия | Когда очищается |
| --- | --- | --- | --- |
| Краткосрочная память | Текущий диалог: сообщения пользователя и ответы модели | Только выбранный агент и его активная ветка | Зависит от выбранной стратегии контекста: Sliding Window отбрасывает старые сообщения, Summary заменяет их сводкой, Branching хранит их в ветках. При удалении агента его диалог также удаляется. |
| Рабочая память | Обычный массив строк `working` для текущей задачи | Только тот агент, которому отправлена команда | Только явно: `/clear-working` или `/clear-memory` для выбранного агента. Переключение агента, новая задача и перезапуск сервера её не очищают. |
| Долговременная память | Общий массив строк `longTerm`: профиль, предпочтения, важные знания или решения без внутренних категорий | Все агенты приложения, включая новых | Только явно: `/clear-long` или `/clear-memory`. Перезапуск и создание/удаление агента её не очищают. |

Рабочая и долговременная память хранят не словари, а последовательности текстовых элементов. Поэтому в них нет полей `task`, `data`, `profile`, `decisions` и `knowledge`: например, фраза «Срок отпуска — 14–20 октября» сохраняется одной строкой, без ключа.

Для защиты от случайно слишком большого контекста в рабочей памяти допускается до 24 элементов, в долговременной — до 52. Длина одного элемента — до 500 символов. При превышении лимита команда возвращает локальную ошибку и ничего не меняет.

### Команды памяти

Команды вводятся в то же поле, что и обычные сообщения. Сервер сначала распознаёт команду, изменяет память и возвращает служебный статус. В этом случае вызова DeepSeek/Z.AI нет, команда не добавляется в историю диалога и не расходует токены API.

| Команда | Действие | Пример |
| --- | --- | --- |
| `/working текст` | Добавляет `текст` в рабочую память выбранного агента | `/working Делаю дизайн лендинга` |
| `/long текст` | Добавляет `текст` в общую долговременную память и сразу синхронизирует её у всех агентов | `/long Меня зовут Диана` |
| `/clear-working` | Очищает рабочую память выбранного агента | `/clear-working` |
| `/clear-long` | Очищает общую долговременную память у всех агентов | `/clear-long` |
| `/clear-memory` | Очищает рабочую память выбранного агента и общую долговременную память | `/clear-memory` |

После `/working` и `/long` обязателен непустой текст. Команды очистки не принимают дополнительных аргументов. Старые адресные команды (`/profile`, `/decision`, `/knowledge`, `/working-data`) больше не являются командами памяти; используйте вместо них `/working` или `/long`.

Для новой независимой задачи обычно достаточно выполнить `/clear-working`, затем добавить новую задачу через `/working ...`. Если нужно начать полностью «с чистого листа», используйте `/clear-memory`. Новый агент создаётся с пустой рабочей памятью, но получает текущую общую долговременную память.

### Что получает модель

Перед каждым обычным сообщением агент собирает один текстовый контекст. Сначала в нём идут элементы рабочей памяти активного агента, затем элементы общей долговременной памяти, в порядке их добавления. Контекст передаётся одним system-сообщением как обычный текст, а не как JSON. В него не попадают ключи, имена категорий и техническая структура хранилища.

Краткосрочная память добавляется отдельно — как история сообщений в соответствии с выбранной стратегией контекста. Так модель может опираться и на текущую переписку, и на явно сохранённые сведения. Если обе явные памяти пусты, дополнительный контекст не добавляется: модель получает только базовый system prompt и историю диалога.

Например, после команд

```text
/working Делаю дизайн лендинга
/long Предпочитает краткий тон
```

в модели будет контекст, содержащий две строки: «Делаю дизайн лендинга» и «Предпочитает краткий тон». Сама команда и её технические поля в prompt не отправляются.

### Хранение и восстановление

Все слои входят в состояние приложения, которое `AgentRegistry` атомарно сохраняет в `data/agents.json`. В этом файле нет API-ключей. Рабочая память записывается внутри состояния каждого агента; долговременная — также в отдельном общем поле состояния, поэтому после перезапуска она остаётся одинаковой у всех агентов.

При старте сервер восстанавливает состояние из файла. Если файл был создан прежней версией приложения, где рабочая память содержала `task` и `data`, а долговременная была разделена на `profile`, `decisions` и `knowledge`, данные автоматически преобразуются в плоские массивы значений. Ключи и названия категорий в новую память не переносятся, а сами значения сохраняются. Если файл отсутствует или повреждён, сервер создаёт нового агента с пустыми рабочей и долговременной памятью.

## День 12 — персонализация ассистента

В правой панели находится глобальный список профилей пользователя. Он выглядит как компактный выпадающий список: выбранный профиль отмечен галочкой, а строка «+ Новый профиль» открывает создание профиля. Нажатие на имя профиля сначала делает его активным, затем открывает одно диалоговое окно для редактирования всех четырёх полей:

- имя;
- стиль ответа;
- формат ответа;
- ограничения.

Профили общие для всех агентов на этом локальном сервере и сохраняются в `data/agents.json`. Можно создать до 20 профилей; удалить профиль в интерфейсе нельзя. При обновлении проверяются непустые поля, длина и уникальность имени.

Перед каждым обычным запросом приложение автоматически добавляет активный профиль к system prompt: сначала идёт базовая инструкция агента, затем профиль, затем данные памяти и история разговора. Поэтому предпочтения действуют сразу для всех агентов и не требуют вставлять их в каждое сообщение. В режиме JSON профиль тоже применяется, а требование JSON передаётся только параметром API `response_format` — дополнительной текстовой инструкции нет.

Для быстрой проверки создайте, например, профиль «Анна Смирнова» со стилем «деловой и тёплый» и профиль «Илья Орлов» со стилем «кратко и по делу». Отправьте один и тот же запрос, переключив профиль в меню: в блоке «Метаданные» будет видно, какой профиль вошёл в system prompt текущего запроса.

## День 13 — состояние задачи

У каждого агента может быть одна активная задача с формальным конечным
автоматом: `PLANNING → EXECUTION → VALIDATION → DONE`. Состояние не выводится
из текста переписки: этап, шаг, выполненные пункты, ожидаемое действие и
пауза хранятся явно в `context.taskState`.

В чате над полем ввода отображается компактная карточка. Во второй строке
видны этап и прогресс, например `Этап: 1/4 PLANNING · Шаг: 0/0`; ниже —
текущий шаг, ожидаемое действие, статус и Markdown-чек-лист. Выполненные
пункты имеют отметку `[x]`, остальные — `[ ]`.

### Сценарий работы

1. Отправьте `/task Название`.
   Интерфейс сразу показывает «Создана задача: …», а `Название` одновременно
   передаётся модели как первый обычный промпт задачи. Агент задаёт вопросы и
   остаётся на этапе `PLANNING`.
2. Ответьте на вопросы. Когда вводных достаточно, агент возвращает
   Markdown-план. Если в плане есть дополнительные нумерованные списки
   (например, критерии), рабочие пункты указываются в отдельном разделе
   `## Шаги`.
3. Прочитайте план и отправьте `/execute`. Первый незавершённый пункт
   начинается сразу; пользователь не подтверждает каждый следующий шаг.
4. После завершения пункта агент обновляет чек-лист, сообщает о переходе и
   запускает следующий. После последнего пункта он переходит в
   `VALIDATION`, затем в `DONE`.
5. Если во время выполнения понадобились новые вводные, отправьте
   `/planning`: агент вернётся к планированию, но сохранит уже завершённые
   пункты. Новый план обязан оставлять их неизменным префиксом.

### Команды и переходы

| Команда | Когда доступна | Действие |
| --- | --- | --- |
| `/task Название` | Нет активной задачи или предыдущая завершена | Создаёт задачу в `PLANNING` и начинает опрос названием задачи. |
| `/execute` | `PLANNING`, когда Markdown-план сохранён | Подтверждает план и запускает первый незавершённый шаг. |
| `/planning` | `EXECUTION` | Возвращает к уточнению требований и пересмотру плана. |
| `/pause` | `PLANNING`, `EXECUTION`, `VALIDATION` | Сохраняет этап, шаг и ожидаемое действие; следующий автоматический запрос не запускается. Текущий запрос модели не прерывается. |
| `/resume` | Только на паузе | Снимает паузу без повторной постановки задачи и продолжает сохранённый рабочий этап. |
| `/status` | На любом этапе | Выводит этап, прогресс, текущий шаг, выполненные шаги и ожидаемое действие. |

Пока задача на паузе, обычные сообщения и переходы запрещены; доступны только
`/resume` и `/status`. После `DONE` новую задачу можно создать следующей
командой `/task`.

### Сохранение и восстановление

Состояние задачи сохраняется в `data/agents.json`, а читаемый Markdown-план —
в `data/task-plans/{agent-id}-{task-id}.md`. После перезапуска агент получает
состояние и чек-лист в system prompt, поэтому `/resume` продолжает работу с
того же этапа без повторных объяснений.

Служебные контейнеры и метки модели не показываются пользователю: план
извлекается из `[[TASK_PLAN]]…[[/TASK_PLAN]]`, а завершение рабочего шага и
проверки подтверждается служебными отметками в конце ответа. Если старый
ответ уже содержал корректный контейнер плана, но прежняя версия приложения
его не сохранила, `/execute` восстанавливает этот план из истории перед
запуском выполнения.

## День 14 — инварианты состояния

Инварианты — независимые от диалога правила агента: выбранный стек,
архитектурные решения, запреты и бизнес-ограничения. Они хранятся в
`context.invariants`, отдельно от истории сообщений, памяти и состояния
задачи. Поэтому правила сохраняются после перезапуска и не откатываются при
переключении контекстной ветки.

### Команды

| Команда | Действие |
| --- | --- |
| `/invariant Правило` | Добавляет правило в свободной формулировке. Двоеточие не нужно. |
| `/invariants` | Показывает текущие правила с номерами. |
| `/remove-invariant 1` | Удаляет правило с указанным номером. |
| `/clear-invariants` | Очищает список правил. |

Например:

```text
/invariant Использовать Kotlin и Ktor
/invariant Не использовать Python
```

Дубликаты, пустые и слишком длинные правила, а также явные противоречия
между ограничениями стека отклоняются до сохранения.

### Как ограничения применяются

Перед каждым запросом в system prompt добавляется блок `[ИНВАРИАНТЫ]`. Он
расположен раньше профиля пользователя, контекста задачи, памяти и истории,
поэтому эти данные не могут отменить заданные правила.

Явный конфликт, например «Не использовать Python» и «Реализуй на Python»,
возвращает HTTP `400` с объяснением, не вызывает модель и не добавляет
сообщение в историю. Если конфликтное решение сгенерирует сама модель,
приложение заменит его безопасным отказом до показа пользователю.

Детерминированная проверка распознаёт формулировки «использовать X», «только
X», «не использовать X» и «без X». Свободные правила, включая бизнес-правила,
всё равно поступают модели как приоритетный контекст, но не выдаются за полную
машинную семантическую проверку.

## День 15 — контролируемые переходы состояний

Задача проходит только по разрешённому маршруту:

```text
                /planning
  ┌─────────────────────────┐
  ▼                         │
PLANNING ── план + /execute ──> EXECUTION ── все шаги ──> VALIDATION ── проверка ──> DONE
                                  ▲                            │
                                  └── доработка шага N ────────┘
```

- Без сохранённого Markdown-плана `/execute` отклоняется: выполнение нельзя начать раньше утверждения плана.
- Финал разрешает только `[[TASK_VALIDATION_PASSED]]` после `VALIDATION`; неверная или преждевременная метка не меняет задачу и скрывается из чата.
- `/pause` сохраняет этап и текущий шаг в `data/agents.json`; `/resume` продолжает именно их после перезапуска.

## День 17 — свой GitHub MCP-инструмент

Наш отдельный MCP-сервер регистрирует `get_repository(owner, repo)` и получает
сведения о публичном репозитории через GitHub REST API. Возвращает описание,
язык, звёзды, форки, основную ветку, ссылку и время получения данных.

### Запуск

Команды выполняются из папки `deepseek-api`. Установите зависимости в своё
окружение:

```bash
python -m pip install -r requirements.txt
```

В первом терминале запустите собственный MCP-сервер:

```bash
python github_mcp_server.py
```

Он слушает `http://127.0.0.1:8001/mcp`. GitHub-токен для публичных данных не
обязателен; при необходимости задайте `GITHUB_TOKEN` в окружении именно этого
процесса. Токен не передаётся модели или браузеру.

Во втором терминале, с `DEEPSEEK_API_KEY` в окружении, запустите приложение:

```bash
python main.py
```

1. Откройте `http://127.0.0.1:8000` и вкладку **MCP**.
2. Введите `http://127.0.0.1:8001/mcp`, нажмите **Подключить**.
3. У сервера появятся статус **Доступен всем агентам**, инструмент
   `get_repository` и его входные параметры.
4. Перейдите в чат любого агента с DeepSeek и обычным текстовым форматом.
5. Отправьте: «Через GitHub узнай, что за проект modelcontextprotocol/python-sdk:
   дай описание, основной язык, число звёзд и ссылку».
6. В метаданных раскройте **Вызовы инструментов** и **Запросы модели**:
   видны аргументы, результат MCP, запрос с `role=tool` и итоговый ответ.

Сервер подключается один раз для всех существующих и новых агентов.
Истории и результаты вызовов остаются раздельными. Кнопка **Отключить**
запрещает новые вызовы этого сервера у всех агентов; начавшийся вызов может
завершиться. Никаких индивидуальных переключателей MCP у агентов нет.

Через ту же форму можно подключить публичный HTTPS MCP, например DeepWiki.
Локальный HTTP разрешён только для точного адреса нашего сервера
`http://127.0.0.1:8001/mcp`; URL с учётными данными, query, fragment и
HTTP-редиректы не поддерживаются. Подключайте только доверенные серверы:
их объявленные инструменты становятся доступны моделям всех агентов.

Общие адреса серверов сохраняются в `data/mcp_servers.json`. После перезапуска
они показаны как отключённые: нажмите **Подключить** для свежего списка
инструментов. Ошибка подключения не блокирует обычный чат.

### Цикл агента и ограничения

Модель получает схемы tools, сама выбирает вызов, backend исполняет его через
MCP и возвращает результат в следующем запросе модели с правильным
`tool_call_id`. В обычной истории сохраняются пользовательский запрос и
финальный ответ; промежуточная последовательность — в метаданных последнего
хода. Сырой результат не переносится автоматически в следующий ход.

Первая версия поддерживает MCP для DeepSeek в текстовом режиме, с отключённым
thinking. GLM и JSON-режим продолжают работать без инструментов; в интерфейсе
показывается это ограничение. Вспомогательные запросы памяти tools не получают.

На один ход допускаются до шести раундов выбора инструментов, до шести
принятых модельных вызовов инструментов и финальный запрос модели без
инструментальных вызовов. Невалидный или неизвестный вызов тоже расходует
лимит; элементы пачки сверх остатка получают локальную ошибку без вызова MCP.
Тайм-аут MCP-операции — 15 секунд, GitHub — 10 секунд; результат MCP ограничен
16 KiB. Неизвестный
инструмент, неправильные параметры и ошибки API возвращаются модели как
ошибки инструмента. Использование токенов и стоимость суммируются по всем
полученным ответам модели, включая промежуточные и частично неуспешные ходы.

## День 18 — планировщик и фоновые задачи

Смысл задания: агент один раз ставит задачу, а отдельный процесс выполняет её
позже или регулярно, сохраняет наблюдения и строит общий результат. В этой
реализации агент следит за публичным GitHub-репозиторием: собирает число звёзд
и форков, считает их изменение с первого наблюдения и количество успешных
и неуспешных проверок. Это продолжение GitHub-инструмента из дня 17.

### Быстрый запуск

Из каталога `deepseek-api`, в окружении с установленными `requirements.txt`:

```bash
python scheduler_mcp_server.py
```

В другом терминале запустите чат, если он ещё не работает:

```bash
python main.py
```

1. Во вкладке **MCP** подключите `http://127.0.0.1:8002/mcp` — этот адрес есть в подсказках поля URL.
2. Откройте чат агента с DeepSeek и текстовым форматом ответа.
3. Напишите: **«Проверяй репозиторий octocat/Hello-World каждые 60 секунд, начиная сейчас. Создай расписание и сообщи его ID».**
4. Откройте [страницу сводок](http://127.0.0.1:8002/) или ссылку «Открыть сводки по расписанию» в карточке MCP. Она обновляется каждые 5 секунд. Чат можно закрыть.
5. Позже спросите: **«Покажи сводку по заданию ID»**. Для остановки: **«Отмени задание ID»**.

Для отложенной однократной проверки: **«Через 30 секунд один раз проверь
octocat/Hello-World и сохрани результат»**. Первый запуск может быть отложен и
у периодической задачи: **«Начни через 30 секунд, затем проверяй каждый час»**.
Запрос «каждый час» задаёт интервал 3600 секунд; календарные cron-выражения и
«ежедневно в 09:00» в этой версии не поддерживаются.

Фоновому процессу не нужны ключ модели и отдельный `github_mcp_server.py`:
он использует общий модуль `github_api.py`. `DEEPSEEK_API_KEY` нужен чату, чтобы
модель сама выбирала MCP-инструменты. `GITHUB_TOKEN` необязателен для публичных
репозиториев. Длинные интервалы уменьшают расход лимита GitHub; 10 секунд —
минимальный период для короткой демонстрации, а не рекомендуемый постоянный режим.

### Инструменты и агрегированный результат

| Инструмент | Параметры | Результат |
| --- | --- | --- |
| `schedule_repository` | `owner`, `repo`, `delay_seconds=0`, `interval_seconds=null` | Новое задание с ID, временем запуска и начальной сводкой |
| `list_schedules` | `limit=3` (1–3), `offset=0` | Страница заданий со сводками; `total` позволяет запросить следующие |
| `get_schedule_summary` | `job_id`, `history_offset=0` | Сводка за всё время и страница истории по 3 попытки |
| `cancel_schedule` | `job_id` | Отмена будущих запусков без удаления истории |

`interval_seconds=null` означает один запуск, целое значение от 10 — период.
Задержка и период ограничены 365 днями. Допускается до 100 активных заданий.
Каждый `schedule_repository` создаёт новое задание: при сомнении в результате
вызова сначала запросите список, чтобы не создать дубликат.

Пример аргументов:

```json
{"owner":"octocat","repo":"Hello-World","delay_seconds":30,"interval_seconds":3600}
```

Пример сводки при двух наблюдениях с ростом счётчиков:

> octocat/Hello-World: успешных проверок — 2, ошибок — 0. Звёзды: 43 (+2), форки: 9 (+1) с первого наблюдения.

Числа в этом примере условные. `stars_delta` и `forks_delta` — разница между
первым и последним **успешными** наблюдениями, а не число новых событий за
календарные сутки. До первого успеха поля равны `null`; после одного — изменение
равно нулю. Сводка также содержит время первого/последнего успеха, следующего
запуска и последнюю зарегистрированную ошибку. Ошибка остаётся видна и после
восстановления. Коммиты и pull requests эта задача не анализирует.

### Хранение и фоновое выполнение

- Файл `deepseek-api/data/scheduler.sqlite3` содержит таблицы заданий и попыток.
  SQLite WAL и транзакции сохраняют результат вместе с новым временем запуска.
  Путь можно изменить: `python scheduler_mcp_server.py --db /absolute/path/jobs.sqlite3`.
- Первый и последний успешные снимки и счётчики сохраняются за всё время.
  Подробно хранятся последние 100 попыток **каждого** задания. MCP выдаёт их
  страницами по 3, чтобы укладываться в лимит чата 16 KiB. Описания репозитория
  не копируются в историю — хранятся только нужные счётчики и времена.
- Worker стартует при запуске HTTP-приложения. Новый MCP-клиент не запускает
  отдельный worker. Закрытие браузера, остановка чата и отключение MCP от
  общего каталога не останавливают расписания; для этого нужен `cancel_schedule`.
- Проверка готовых задач происходит примерно раз в секунду. Один worker
  выполняет проверки последовательно, поэтому при нагрузке/медленной сети
  фактический запуск может быть позже планового. Отсечка каждой проверки — 20 секунд.
- После простоя просроченное задание выполняется один раз, пропущенные интервалы
  объединяются; следующий запуск остаётся на исходной временной сетке.
- Захват задачи получает lease на 60 секунд. После аварийной остановки попытка
  может быть повторена после истечения lease. Повторный read-only запрос GitHub
  допустим; устаревший исполнитель не может записать второй результат.
- Ошибки API и тайм-ауты сохраняются в истории. Периодическая задача повторит
  попытку в следующий интервал; однократная завершится с записанной ошибкой.
  Отмена не прерывает уже выполняющийся запрос, но исключает следующие.
- Все времена в SQLite/API — UTC; страница отображает их в часовом поясе браузера.
  Каждый завершённый запуск также печатает JSON-сводку с `event=schedule_summary`
  в stdout. Генерация фоновых сводок не вызывает LLM и не расходует её токены.

История отменённых задач сохраняется, поэтому количество самих заданий и общий
размер базы могут расти. Для долгой эксплуатации нужны резервные копии SQLite
и ротация stdout/stderr логов. Самый простой согласованный backup — после остановки
планировщика; для работающего процесса используйте SQLite backup API.

### Постоянный запуск на macOS

Обычный запуск в терминале действует до завершения процесса. Для автоматического
запуска после входа в macOS и перезапуска после сбоя можно использовать `launchd`.
Это **пример установки**, он не выполняется автоматически вместе с приложением.
Остановите экземпляр планировщика в терминале, чтобы освободить порт 8002.

Из `deepseek-api` выполните Python из виртуального окружения; код сформирует
plist с абсолютными путями, в том числе корректно обработает пробелы:

```bash
.venv/bin/python - <<'PY'
import plistlib
import sys
from pathlib import Path

project = Path.cwd().resolve()
assert (project / 'scheduler_mcp_server.py').is_file(), 'Перейдите в deepseek-api'
logs = project / 'data'
logs.mkdir(exist_ok=True)
target = Path.home() / 'Library/LaunchAgents/ru.ai-advent.scheduler.plist'
target.parent.mkdir(parents=True, exist_ok=True)
config = {
    'Label': 'ru.ai-advent.scheduler',
    'ProgramArguments': [sys.executable, str(project / 'scheduler_mcp_server.py')],
    'WorkingDirectory': str(project),
    'RunAtLoad': True,
    'KeepAlive': True,
    'ThrottleInterval': 10,
    'StandardOutPath': str(logs / 'scheduler-summary.jsonl'),
    'StandardErrorPath': str(logs / 'scheduler-error.log'),
}
with target.open('wb') as stream:
    plistlib.dump(config, stream)
print(target)
PY

launchctl bootstrap "gui/$(id -u)" "$HOME/Library/LaunchAgents/ru.ai-advent.scheduler.plist"
launchctl print "gui/$(id -u)/ru.ai-advent.scheduler"
```

Для остановки службы:

```bash
launchctl bootout "gui/$(id -u)" "$HOME/Library/LaunchAgents/ru.ai-advent.scheduler.plist"
```

`bootout` выгружает службу сейчас; чтобы отключить будущий автозапуск, уберите
этот plist из `~/Library/LaunchAgents`. Файл базы при этом остаётся. После
перемещения проекта plist нужно пересоздать. Переменные терминала не наследуются
службой: пример работает без GitHub-токена и без ключа модели.

LaunchAgent работает в пользовательском сеансе. Во сне, при выходе пользователя
или на выключенном компьютере проверки не выполняются. Для фактического 24/7
нужен постоянно включённый сервер с supervisor; на Linux аналогом будет systemd.
Сам HTTP-сервер слушает только loopback. Доступ MCP общий для локальных агентов,
авторизации пользователей здесь нет. Дополнительные сведения — в
[документации Apple о launchd](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html).

### Как проверить выполнение задания

```bash
python -m unittest discover -s tests -p 'test_scheduler*.py' -v
python -m unittest discover -s tests -v
```

Тесты проверяют задержку, повторение, сохранение/перезапуск, сводку, конкуренцию,
ошибки и восстановление, отмену во время выполнения, ограничение истории и
размера MCP-ответа, строгие схемы, настоящий MCP-протокол и lifespan без клиента.
Код MCP использует установленную ветку v1, см.
[MCP Python SDK v1](https://py.sdk.modelcontextprotocol.io/v1/server/).
Результаты сквозной проверки — в `docs/day-18` в корне репозитория.

## День 19 — композиция MCP-инструментов

Команда в обычном чате автоматически выполняет поиск, подготовку обзора и запись файла:

```text
/research Найди три Python-репозитория про MCP, составь краткий обзор и сохрани его
```

После `/research` можно написать задачу обычным языком (одна строка, до 2000 символов):

```text
/research Найди две библиотеки для Telegram-ботов на Python, составь краткий обзор и сохрани его
```

Выбранная в чате модель за один запрос преобразует текст в запрос GitHub и количество
результатов (1–3). Для этого нужен `DEEPSEEK_API_KEY` или `ZAI_API_KEY`, в зависимости
от модели. В чате появятся «Понимаю запрос» и получившийся запрос GitHub; затем
выполнятся три MCP-инструмента. Разбор сохраняется в карточке, запрос модели —
в метаданных, расход токенов и стоимость — в общих счётчиках и метаданных.
Модель получает только текущую инструкцию, без истории чата.

Простые запросы вроде `mcp`, `repo:owner/name` и `mcp language:python` работают
без модели. Для любого готового запроса GitHub используйте явный режим
`/research --query telegram bot language:python` (сам запрос — до 200 символов).
Формат ответа обычного чата не влияет на исследование. Отдельный skill или MCP
`run_pipeline` не используется: цепочкой управляет код приложения.

Поддерживаются поиск публичных репозиториев и обзор их метаданных. Чтение README,
анализ кода, локального репозитория и произвольный путь сохранения не поддерживаются.
Для запроса «Напиши кратко что в репозитории» укажите тему или `owner/repo`;
при неоднозначности модель попросит уточнение, а инструменты не запустятся.
Уточнённую команду нужно отправить заново с `/research`.
Команда `/research` без текста показывает подсказку и не запускает исследование.

### Запуск

Подготовьте `.venv` и зависимости по разделу [«Настройки и запуск»](#настройки-и-запуск).
Для свободного текста добавьте ключ выбранной модели в окружение того терминала,
где будет запущен `main.py`. Готовый запрос с `--query` не требует ключа модели.

Из каталога `deepseek-api` запустите два процесса в разных терминалах.
Первый — MCP-сервер с тремя инструментами:

```bash
.venv/bin/python pipeline_mcp_server.py
```

Второй — веб-приложение:

```bash
.venv/bin/python main.py
```

Откройте [чат](http://127.0.0.1:8000) и отправьте одну из команд выше.
MCP-сервер слушает только `http://127.0.0.1:8003/mcp`. Команда обращается к этому
фиксированному серверу напрямую: добавлять его в каталог инструментов модели
не требуется. Во вкладке MCP адрес доступен как пример для просмотра схем.
Серверы дней 17–18 запускать для этого задания не нужно.
Оба процесса должны работать во время демонстрации; остановка — `Ctrl+C` в каждом
терминале. После изменения Python-кода перезапустите соответствующий сервер.

### Сценарий демонстрации

1. Выберите в чате модель, для которой настроен ключ, и отправьте
   `/research Найди три Python-репозитория про MCP, составь краткий обзор и сохрани его`.
2. Покажите стадию «Понимаю запрос» и получившиеся параметры GitHub, затем
   последовательные статусы `search`, `summarize` и `saveToFile`.
3. Раскройте «Входные данные / Результат» у шагов. Сравните `structuredContent`
   из `search` с аргументом `search_result` у `summarize`, а результат `summarize`
   — с аргументом `report` у `saveToFile`.
4. Откройте файл по показанному пути: его текст должен совпадать с `markdown`
   из результата `summarize`. В результате сохранения также доступны размер и SHA-256.
5. Обновите страницу и покажите, что карточка с результатами восстановилась.

Вариант без обращения к модели: `/research --query mcp language:python`.
В нём сразу начинается `search`, затем выполняются оставшиеся два инструмента.

### Что видно в чате

Карточка показывает состояние каждого шага сразу, по мере выполнения:

```text
✓ search — найдено 3 репозитория
✓ summarize — обзор по 3 репозиториям подготовлен
✓ saveToFile — файл сохранён
```

Пока шаг выполняется, отображается индикатор ожидания. Под каждым шагом можно
раскрыть **«Входные данные / Результат»**: реальные аргументы, ответ MCP, адрес
сервера и длительность. В конце показывается копируемый абсолютный путь к файлу.
При успешном выполнении в метаданных доступны три вызова инструментов.
Для свободной фразы там дополнительно виден один запрос модели, его токены и
стоимость; расход также отражается в метриках последнего хода и графике.
Для готового запроса GitHub список запросов модели пуст.

Карточки сохраняются в истории агента и его ветки, восстанавливаются после
обновления страницы и подчиняются выбранной стратегии хранения истории.
Sliding Window может удалить старую карточку за пределами окна; созданный файл
при этом остаётся. Служебный JSON карточки не отправляется модели при последующем
обычном разговоре, в том числе при извлечении facts.
Журнал выполнения — это карточка в чате и её данные в
`deepseek-api/data/agents.json` при стандартном запуске. Отдельный файл журнала
для каждого исследования не создаётся; Markdown-отчёты хранятся в `data/reports/`.

### Инструменты и данные

| Инструмент | Вход | Результат |
| --- | --- | --- |
| `search` | query, limit (1–3, по умолчанию 3) | SearchResult: запрос, время, количество совпадений, признак неполноты, items |
| `summarize` | search_result целиком | SummaryResult: запрос, source_count, Markdown |
| `saveToFile` | report целиком | SavedFile: path, bytes_written, sha256 |

Исполнитель вызывает каждый шаг через настоящий MCP `tools/call` и передаёт
предыдущий `structuredContent` без преобразования данных. Схемы проверяются на
каждой границе; лимит MCP-ответа — 16 KiB. Поиск использует GitHub Search API,
необязательный `GITHUB_TOKEN` и тайм-аут 10 секунд. Лимит MCP-операции — 15 секунд.

`summarize` формирует обзор **по шаблону без LLM**: названия, описания (до 300
символов), языки, звёзды и ссылки. Он не анализирует исходный код репозиториев.
Пустой поиск тоже проходит три шага и сохраняет отчёт «Ничего не найдено».
Неполная выдача GitHub отмечается в отчёте.

Файлы создаются в `deepseek-api/data/reports/<uuid>.md`, относительно серверного
модуля. Инструмент не принимает произвольный путь и не перезаписывает существующие
отчёты. В файл попадают точные UTF-8-байты Markdown второго шага (до 6000 байт).
Повторный самостоятельный запуск создаёт новый отчёт. Автоматической очистки
отчётов нет.

Поле `SavedFile.path` в результате MCP — абсолютный путь в файловой системе
компьютера, где работает сервер; это не URL. Веб-приложение сейчас не предоставляет
HTTP-маршрут для отчётов, поэтому браузер не может открыть этот путь напрямую.
Откройте файл локально на машине сервера. Ссылка вида `http://localhost:<порт>/Users/...`
не создаётся инструментом и не является адресом отчёта.

### Ошибки и ограничения

- Разбор свободного текста ограничен одним вызовом модели с тайм-аутом 30 секунд,
  без автоматических повторов. Невалидный ответ или ошибка модели останавливает
  исследование до MCP-вызовов. Модель выбирает только запрос и лимит; схемы
  и ограничения инструментов проверяются кодом.
- Ошибка на шаге останавливает цепочку; последующие шаги показываются как
  «Не выполнялся». При недоступном MCP-сервере карточка подсказывает его запуск.
- Повторная команда и изменения того же агента во время исследования получают
  HTTP 409. Новые исследования разных агентов могут выполняться параллельно.
- В существующей архитектуре обычный LLM-запрос удерживает общую блокировку
  реестра: такой запрос другого агента может задержать начало исследования или
  обновление его карточки. Для демо запускайте `/research` без одновременного
  обычного запроса модели. Сам пайплайн не удерживает эту блокировку на время сети.
- Разрыв браузерного соединения не повторяет и не отменяет принятый запуск:
  сервер заканчивает работу и сохраняет историю. До обновления страницы интерфейс
  сообщает, что результат неизвестен. Автоматического повторного POST нет.
- После перезапуска сервера незавершённая карточка отмечается как прерванная.
  Тайм-аут сохранения может означать, что файл уже создан; автоматических повторов
  `saveToFile` нет. Ошибка записи истории сообщается отдельно от результата файла.

### Проверка

```bash
.venv/bin/python -m unittest discover -s tests -p 'test_pipeline*.py' -v
.venv/bin/python -m unittest discover -s tests -p 'test_research_intent.py' -v
.venv/bin/python -m unittest discover -s tests -v
```

Тесты проверяют настоящий HTTP MCP, поток до завершения следующего шага,
передачу JSON, точные байты/хеш файла, пустой поиск, ошибки, восстановление
истории и разрыв соединения. Для готовых запросов проверяется отсутствие LLM-вызовов,
для свободных фраз — один вызов модели, строгий разбор параметров, передача лимита,
отказ от запуска инструментов при ошибке и учёт токенов. Сквозной тест использует
реальный HTTP/MCP-транспорт с подставными ответами модели и GitHub.
На проверке 27 сентября 2026 прошли **284 теста**. Свидетельства живой проверки
и образец отчёта находятся в [docs/day-19](../docs/day-19/pipeline-results.md).

## День 20 — оркестрация нескольких MCP-серверов

В обычном чате модель выбирает очередной инструмент из объединённого каталога
подключённых MCP-серверов. Приложение проверяет аргументы и маршрутизирует вызов
к серверу-владельцу. Результат MCP возвращается модели для следующего решения.
Ограничения — шесть принятых вызовов и шесть раундов выбора; после этого
выполняется финальный запрос без инструментов.

### Промежуточные статусы вызовов в чате

Для обычных сообщений чата при подключённых инструментах, модели DeepSeek и
текстовом формате приложение передаёт события вызовов MCP потоком NDJSON.
Карточка в переписке показывает сервер, инструмент и статус «выполняется»,
«готово» или «ошибка». Обычные запросы без доступных MCP-инструментов сохраняют
прежний JSON-ответ. Карточка временная: она остаётся в текущей вкладке, но не
добавляется в историю диалога на сервере.

### Запуск трёх локальных MCP-серверов

Выполняйте команды из `deepseek-api`, в отдельных терминалах:

```bash
.venv/bin/python pipeline_mcp_server.py
.venv/bin/python github_mcp_server.py
.venv/bin/python scheduler_mcp_server.py
```

В четвёртом терминале запустите чат с `DEEPSEEK_API_KEY`:

```bash
.venv/bin/python main.py
```

Откройте `http://127.0.0.1:8000`, перейдите во вкладку **MCP** и подключите:

- `http://127.0.0.1:8003/mcp` — `search`, `summarize`, `saveToFile`;
- `http://127.0.0.1:8001/mcp` — `get_repository`;
- `http://127.0.0.1:8002/mcp` — `schedule_repository`, `get_schedule_summary` и другие инструменты планировщика.

Выберите чат модели DeepSeek в текстовом режиме и отправьте запрос:

> Найди Python MCP-серверы, выбери один репозиторий, получи его актуальные
> сведения, сохрани обзор и запланируй однократную проверку через неделю.

Для проверки ожидается последовательность:

1. Pipeline `search` находит до трёх репозиториев.
2. GitHub `get_repository` получает сведения об одном из найденных.
3. Pipeline `summarize` получает исходный `structuredContent` поиска.
4. Pipeline `saveToFile` получает исходный `structuredContent` обзора.
5. Scheduler `schedule_repository` создаёт однократное задание с задержкой
   604800 секунд и `interval_seconds=null`.
6. Scheduler `get_schedule_summary` подтверждает то же задание. До срока
   первого запуска сводка должна показывать ноль успешных и неуспешных проверок.

Откройте **Вызовы инструментов** в метаданных ответа и проверьте имя сервера,
порядок, аргументы и результаты. Схема MCP-результата проверяется, если сервер
публикует `outputSchema`; сохранение файла и создание расписания дополнительно
проверяются по обязательным полям ответа. Передача обзора и поиск выбранного
репозитория сверяются с фактическими результатами предыдущих инструментов.

`schedule_repository` создаёт постоянное локальное задание. Если ответ потерялся
по тайм-ауту, приложение не повторяет его автоматически; сначала проверьте
существующие задания в `list_schedules` или на странице `http://127.0.0.1:8002/`.
Планировщик выполнит проверку, когда сервер работает в момент срока запуска.

(`docs/day-21/corpus/agentic-design-patterns-ru.epub`). Исходный SHA-256:

```bash
ollama pull embeddinggemma
```

```bash
python3 deepseek-api/document_index.py build
python3 deepseek-api/document_index.py compare
python3 deepseek-api/document_index.py search "Как агенту хранить память проекта?" --strategy fixed
python3 deepseek-api/document_index.py search "Как агенту хранить память проекта?" --strategy structural
python3 deepseek-api/document_index.py search "Как проверять изменения перед коммитом?" --strategy structural --top-k 3
```

EPUB записываются в SQLite вместе с документами и чанками. Для обеих стратегий
используется лимит 250 слов и перекрытие 40 слов; заголовок главы и путь раздела
передаются модели отдельно от основного текста. `fixed` может пересечь
границу H1–H3; `structural` начинает новый чанк на этой границе. `compare`
записывает реальные показатели и результаты одинаковых запросов в
`docs/day-21/comparison.md`. `search` печатает оценку косинусного сходства,
главу, раздел, источник, ID и фрагмент. Изменить адрес Ollama можно общим
аргументом `--ollama-url` перед именем команды.

## День 22 — первый RAG-запрос

CLI сравнивает обычный ответ и ответ с пятью структурными фрагментами из
`docs/day-21/index.sqlite3`. По умолчанию оба режима вызывают `glm-4.7-flash`
через Z.AI с температурой 0 и одной системной инструкцией. В обычном режиме Ollama и индекс
не нужны. Для RAG нужны готовый индекс и локальная Ollama с моделью, указанной
в метаданных индекса (сейчас `embeddinggemma`); индекс не пересобирается.

Установите зависимости из `deepseek-api/requirements.txt`, задайте
`ZAI_API_KEY` и при необходимости запустите `ollama serve`. Из корня репозитория:

```bash
python3 deepseek-api/rag_agent.py ask "Что включить в документ передачи сессии?" --mode plain
python3 deepseek-api/rag_agent.py ask "Что включить в документ передачи сессии?" --mode rag
python3 deepseek-api/rag_agent.py evaluate
python3 deepseek-api/rag_agent.py evaluate --model deepseek-v4-flash
```

Адрес Ollama и путь индекса можно задать через `--ollama-url` и `--index`
**перед** именем команды. `evaluate` читает десять вопросов и ожидаемые главы
из `docs/day-22/control_questions.json`, выполняет 20 успешных запросов к
выбранному провайдеру (или к двум при смене модели) и 10 поисков через
Ollama, затем сохраняет полные ответы и найденные чанки в
`docs/day-22/results.json`, а сводку — в `docs/day-22/comparison.md`.
Пути можно изменить флагами `--questions`, `--results` и `--report` после
`evaluate`. Если любой запрос не завершится, новый результат не записывается.
После каждой полной пары ответов прогресс сохраняется отдельно в
`results.json.partial`; повторный запуск с тем же индексом продолжает
с первого незавершённого вопроса. Частичный файл не является отчётом.
При возобновлении проверяются хеши полного набора вопросов и файла индекса.
Если итоговый JSON или отчёт уже существует, новый прогон требует других
путей вывода либо явного `--overwrite`; это защищает внесённые вручную оценки.
Если Z.AI временно недоступна, оставшиеся вопросы можно выполнить с
`--model deepseek-v4-flash` и `DEEPSEEK_API_KEY`. Оба режима одного вопроса
всегда используют одну модель. Отчёт отмечает модель каждого вопроса и
предупреждает, если итоговый прогон использовал разные модели.

Отчёт показывает, попала ли ожидаемая глава в Top-5. Полноту ответов по шкале
0–2 и подтверждение их утверждений фрагментами нужно оценивать вручную:
автоматическое совпадение слов не доказывает смысловую верность. Это один
прогон на выбранных вопросах, а не оценка общей точности RAG.

## День 23 — reranking и query rewrite

Новый CLI использует тот же структурный индекс дня 21 и промпт ответа дня 22.
Сначала `embeddinggemma` через локальную Ollama находит до 20 чанков по
**исходному** вопросу. Режим `baseline` передаёт первые пять по cosine в модель
ответа. `reranked` локально оценивает пары «исходный вопрос + чанк» моделью
`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`, применяет порог и передаёт до
пяти чанков. В `rewritten` модель ответа сначала формулирует одну поисковую
строку по кратким карточкам найденных чанков; cross-encoder оценивает **те же**
20 кандидатов с этой строкой. Новый поиск не выполняется, а финальный ответ
всегда отвечает на исходный вопрос.
При вызове внешней модели `rewritten` передаёт ей короткие карточки до 20
кандидатов, а каждый режим ответа — текст выбранных фрагментов книги.

Зависимости reranker устанавливаются отдельно в окружение Python 3.12 или
новее:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r deepseek-api/requirements-rerank.txt
ollama pull embeddinggemma
```

При первом использовании `CrossEncoder` загрузит веса модели с Hugging Face;
после загрузки вычисление выполняется локально. Для ответа нужен `ZAI_API_KEY`
(`glm-4.7-flash`) либо `DEEPSEEK_API_KEY` (`deepseek-v4-flash`). Ollama должна
работать, а `docs/day-21/index.sqlite3` должен соответствовать её
embedding-модели. Из корня проекта:

```bash
.venv/bin/python deepseek-api/rag_day23.py ask "Как агенту искать причину ошибки до правки кода?" --mode baseline
.venv/bin/python deepseek-api/rag_day23.py ask "Как агенту искать причину ошибки до правки кода?" --mode reranked
.venv/bin/python deepseek-api/rag_day23.py ask "Как агенту искать причину ошибки до правки кода?" --mode rewritten
.venv/bin/python deepseek-api/rag_day23.py ask "Как агенту искать причину ошибки до правки кода?" --mode reranked --top-k-before 20 --top-k-after 5 --min-rerank-score 1.0
.venv/bin/python deepseek-api/rag_day23.py evaluate --model glm-4.7-flash
```

`--index` и `--ollama-url` указываются **перед** `ask` или `evaluate`;
`--model`, `--top-k-before`, `--top-k-after`, `--min-rerank-score` и
`--reranker-model` — после. Cross-encoder score лежит в `[0, 1]`, но это не
калиброванная вероятность. Значение порога по умолчанию — `0.50`; при пустой
выдаче после отсечения ответ о недостатке сведений возвращается без вызова
модели ответа. Cross-encoder обрезает длинные пары токенизатором до 512
токенов. Вывод `ask` показывает оба ранга и score каждого кандидата, а также
выбранный контекст.

`evaluate` сравнивает три режима на десяти вопросах дня 22, сохраняет ответы,
кандидатов и настройки в `docs/day-23/results.json`, а черновую таблицу — в
`docs/day-23/comparison.md`. После каждого завершённого вопроса сохраняется
`results.json.partial`; повторный запуск с теми же настройками продолжает
прогон. Если новый прогон начат с `--overwrite`, при возобновлении укажите
его снова. Для нового прогона поверх существующего результата требуется
`--overwrite`. Полнота ответов и опора на найденные фрагменты оцениваются
вручную после сверки с текстом книги. Изменение порядка само по себе не
доказывает улучшение ответа.

## День 24 — проверенные цитаты и отказ

Отдельный CLI использует структурный индекс дня 21 и локальный reranker дня 23.
Нужны работающая Ollama с `embeddinggemma`, зависимости из
`deepseek-api/requirements-rerank.txt` и `ZAI_API_KEY` для модели
`glm-4.7-flash` (либо `DEEPSEEK_API_KEY` для моделей DeepSeek). Индекс и модели
настраиваются так же, как для дня 23. Из корня проекта:

```bash
.venv/bin/python deepseek-api/rag_day24.py ask "Как агенту искать причину ошибки до правки кода?" --model glm-4.7-flash
.venv/bin/python deepseek-api/rag_day24.py evaluate --model glm-4.7-flash
```

Общие `--index` и `--ollama-url` ставятся перед `ask` или `evaluate`.
`--model`, `--top-k-before`, `--top-k-after`, `--min-rerank-score` и
`--reranker-model` — после команды. `evaluate` также принимает `--questions`,
`--results`, `--report`, `--overwrite`. По умолчанию используются десять
вопросов дня 22, `docs/day-24/results.json` и `docs/day-24/evaluation.md`.
После каждого ответа записывается `results.json.partial`; запуск с теми же
параметрами продолжает прогон. Существующие результаты не заменяются без
`--overwrite`, а правки отчёта при восстановлении сохраняются.

Поиск берёт до 20 чанков, reranker выбирает до пяти с score не ниже `0.50`.
Это нормализованный score, а не вероятность. Если контекст пуст после
отсечения, модель ответа не вызывается: CLI выводит «Не знаю» и просьбу
уточнить вопрос, а списки источников и цитат пусты. Модель может отказаться
и при найденных чанках, если в них нет достаточного ответа.

Содержательный ответ принимается только как JSON с маркерами `[1]`, `[2]` и
цитатами из выбранных чанков. Для каждой цитаты приложение проверяет
`chunk_id`, дословное вхождение `quote` в переданные модели первые 1800
символов чанка и ограничение 400 символов. Поля `source` и `section` берутся
из индекса, а не из ответа модели. В результате сохраняются `answer`,
`sources` (`source`, `section`, `chunk_id`), `citations` (те же поля, `ref`,
`quote`), score, параметры и выбранные чанки без векторов. Проверка
дословности подтверждает происхождение цитаты; смысловую опору каждого
утверждения на цитаты оценивают вручную в отчёте.

## День 25 — отдельный RAG-чат с памятью задачи

Из корня проекта запустите CLI (он не связан с веб-чатом):

```bash
.venv/bin/python deepseek-api/rag_chat.py chat --session моя-задача
```

`--session` создаёт или продолжает именованную сессию. По умолчанию история и
состояние находятся в игнорируемом Git файле `deepseek-api/data/rag_chat.sqlite3`;
`--db` задаёт другой путь. Можно также передать `--index`, `--ollama-url` и
`--model`. Для ответа нужны индекс дня 21, Ollama с `embeddinggemma`,
reranker дня 23 и ключ `ZAI_API_KEY` или `DEEPSEEK_API_KEY` для выбранной модели.
По умолчанию чат и сценарный прогон используют `deepseek-v4-flash` и
`DEEPSEEK_API_KEY`; модель дня 24 остаётся прежней.

В чате доступны `/state` (цель, уточнения, ограничения и термины с номерами
реплик-источников), `/history` и `/exit`. Выход сохраняет сессию. Каждая
обычная реплика формирует самостоятельный запрос по контексту диалога и
запускает новый структурный поиск Top-20 и reranking до пяти чанков. Память
обновляется только на основании дословного фрагмента новой реплики;
текст нового факта и название термина тоже должны встречаться в реплике.
Исправления удаляют прежний факт. Последние четыре хода помогают разрешать
ссылки вроде «а как это проверить?», но предыдущие ответы не считаются
источниками книги.

После ответа CLI всегда печатает `Ответ`, `Источники` и `Цитаты`. Цитаты
проверяются механизмом дня 24 только против текущих найденных чанков. При
недостатке данных выводится «Не знаю», `Источники: нет`, `Цитаты: нет`.
Ошибки поиска, модели и сохранения показываются отдельно; неудачный ход не
меняет состояние. Сценарии и фактические результаты находятся в
`docs/day-25/`; воспроизвести новый прогон можно через
`deepseek-api/rag_chat_eval.py --scenarios ... --results ... --db ...`.
При ошибке сценарный прогон сохраняет `.partial` и базу; повтор с теми же
сценарием, моделью, индексом и Ollama возобновляет ход. Имена входного файла,
результата, `.partial`, базы и индекса должны различаться.
